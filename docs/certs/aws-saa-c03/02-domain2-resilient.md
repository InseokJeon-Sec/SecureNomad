# Domain 2 — 복원력 아키텍처 설계 (26%)

:::tip 모르는 서비스·용어가 나오면
처음 나오는 서비스·모델·약어는 괄호로 짧게 설명을 달았다. 전체 목록과 한 줄 뜻은 **[한 줄 사전](./07-glossary.md)** 에서 한 번에 찾을 수 있다.
:::

두 번째로 비중이 큰 도메인이다. 핵심 질문은 둘이다. **"부하가 늘거나 줄 때 자동으로 견디게 하려면?"(확장성·느슨한 결합)** 과 **"한 부분이 죽어도 서비스가 계속되게 하려면?"(고가용성·내결함성)**. 서비스 이름을 외우는 게 아니라, **요구사항(RTO/RPO, 동기/비동기, 상태유무)** 에 맞는 구성을 고르는 힘을 묻는다.

:::note 이 문서의 구성
**2.1 확장 가능하고 느슨하게 결합된 설계 → 2.2 고가용성·내결함성 설계** 를 다루고, 마지막에 **연습문제 32개(해설 포함)** 로 자가 점검한다. 이 문서 하나로 Domain 2를 커버하는 것을 목표로 한다.
:::

## 2.1 확장 가능하고 느슨하게 결합된 아키텍처

### 왜 "느슨한 결합"인가
구성요소가 서로 직접 호출하면(강결합), 하나가 느려지거나 죽을 때 전체가 함께 무너진다. 사이에 **큐·토픽·이벤트 버스**를 두면(느슨한 결합), 한쪽이 밀려도 다른 쪽은 자기 속도로 처리한다. 시험은 "컴포넌트 간 의존을 끊어라 / 트래픽 급증을 흡수하라"는 요구에 메시징 서비스를 연결하도록 유도한다.

### 메시징 3종 — 무엇이 어떻게 다른가

| 서비스 | 모델 | 쓰는 상황 | 핵심 특징 |
|---|---|---|---|
| **SQS** | 큐(1:1, 당겨가기) | 작업을 버퍼링해 비동기 처리, 생산·소비 속도 분리 | 소비자가 polling, 처리 후 삭제. 자동 확장 버퍼 |
| **SNS** | 발행/구독(1:N, 밀어주기) | 하나의 이벤트를 여러 구독자에게 **팬아웃** | 푸시. 구독자=SQS·Lambda·HTTP·이메일 |
| **EventBridge** | 이벤트 버스(규칙 기반 라우팅) | SaaS·AWS 서비스 이벤트를 **내용으로 필터링**해 라우팅 | 스키마·규칙·스케줄러. 서비스 간 연동에 강함 |

- **SQS 표준 vs FIFO**: 표준은 **거의 무한 처리량·최소 1회 전달(중복 가능)·순서 보장 안 됨**. FIFO는 **순서 보장·정확히 1회**지만 처리량 제한(배치로 상향). "순서/중복 제거가 중요" → FIFO.
- **SNS + SQS 팬아웃**: SNS 토픽 하나에 여러 SQS 큐를 구독시키면, 한 이벤트를 여러 작업 파이프라인이 각자 버퍼링해 처리한다. 단골 패턴.
- **DLQ(Dead Letter Queue)**: 지정 횟수만큼 처리 실패한 메시지를 따로 모아 유실을 막는다.
- **가시성 제한시간(visibility timeout)**: 한 소비자가 메시지를 가져가면 그 시간 동안 다른 소비자에게 안 보인다. 처리 시간보다 짧으면 중복 처리가 생긴다.

### 오케스트레이션 — Step Functions
여러 단계를 **순서·분기·재시도·병렬**로 묶어야 하면 **Step Functions**(상태 머신)를 쓴다. Lambda를 코드로 서로 호출해 엮는 대신, 워크플로를 선언적으로 관리한다. "장기 실행·사람 승인 포함·복잡한 분기" → Step Functions.

### 컴퓨팅 결합 — 서버리스와 컨테이너

| 선택 | 언제 |
|---|---|
| **Lambda** | 이벤트 기반·짧은 실행(최대 15분)·서버 관리 없이, 요청당 과금 |
| **ECS on Fargate** | 컨테이너를 서버(EC2) 관리 없이 실행 |
| **ECS on EC2** | 인스턴스를 직접 제어/비용 최적화하고 싶을 때 |
| **EKS** | 쿠버네티스 표준·멀티클라우드 호환이 필요할 때 |

요지: **"서버 관리를 없애라"** → Fargate/Lambda. **"K8s 생태계"** → EKS.

### 로드 밸런서 — 3종 구분 (자주 나온다)

| LB | 계층 | 라우팅 기준 | 쓰는 상황 |
|---|---|---|---|
| **ALB** | L7(HTTP/S) | 경로·호스트·헤더 기반 | 웹/마이크로서비스, 컨테이너 |
| **NLB** | L4(TCP/UDP) | IP·포트, 초고성능·고정 IP | 극한 성능, TCP, 정적 IP 필요 |
| **GWLB** | L3 | 트래픽을 보안 어플라이언스로 | 방화벽·IDS 등 가상 어플라이언스 체인 |

- **대상 그룹(target group)**: LB가 트래픽을 보내는 대상 묶음(EC2·IP·Lambda). 상태 확인이 여기 붙는다.
- **스티키 세션**: 같은 클라이언트를 같은 대상에 고정. 상태를 서버에 두는 앱의 임시 대안이지만, 본질 해법은 **상태 외부화**(아래).

### Auto Scaling
- **대상 추적(target tracking)**: "CPU 50% 유지"처럼 지표 목표를 정하면 자동으로 인스턴스 수를 조절. 가장 흔한 권장 방식.
- **단계/예약 조정**: 임계치 단계별, 혹은 예측 가능한 시간대(예: 매일 9시 급증)에 미리 늘림.
- LB + Auto Scaling Group을 **여러 AZ**에 걸치면 확장성과 가용성을 동시에 얻는다.

### 상태(state)를 밖으로 빼라 — 수평 확장의 전제
인스턴스를 자유롭게 늘리고 줄이려면, 서버가 **무상태(stateless)** 여야 한다. 세션·파일을 서버 디스크에 두면 그 서버가 죽을 때 사라진다. 그래서 상태를 외부로 분리한다.

- 세션 → **ElastiCache(Redis)**(관리형 인메모리 캐시) 또는 DynamoDB
- 공유 파일 → **EFS**(여러 EC2 동시 마운트) / 정적 자산 → **S3**
- 업로드/작업 큐 → **SQS**

## 2.2 고가용성·내결함성 아키텍처

### 먼저 용어: 가용성 vs 내구성 vs 복원력
- **가용성(Availability)**: 지금 쓸 수 있는가(다운타임이 짧은가).
- **내구성(Durability)**: 저장한 데이터가 유실되지 않는가(S3 11 9's).
- **내결함성(Fault Tolerance)**: 일부가 고장 나도 서비스가 계속되는가.

### 다중 AZ vs 다중 리전

| | 다중 AZ | 다중 리전 |
|---|---|---|
| 막는 장애 | 한 데이터센터(AZ) 장애 | 리전 전체 장애·지역 분산 |
| 지연 | 낮음(같은 리전) | 리전 간 지연 발생 |
| 복잡도·비용 | 보통 | 높음 |
| 대표 용도 | 대부분의 HA 요구 | 재해 복구·글로벌 저지연·규제 |

원칙: **기본은 다중 AZ로 HA를 만들고, 리전 장애/글로벌 요구가 명시되면 다중 리전**으로 올린다.

### 데이터베이스 가용성 — 구분이 시험 포인트

- **RDS Multi-AZ**: **동기 복제**된 **대기(standby)** 를 다른 AZ에 둔다. 장애 시 자동 장애 조치. **가용성용이지 성능 확장용이 아니다**(대기본엔 읽기도 못 함, Aurora 제외).
- **RDS 읽기 전용 복제본(Read Replica)**: **비동기 복제**. **읽기 부하 분산(확장)** 용. 재해 대비로 다른 리전에도 둘 수 있고 승격 가능하지만 자동 장애 조치는 아니다.
- **Aurora**: 스토리지를 3개 AZ에 6벌 복제. 복제본을 **장애 조치 대상 겸 읽기 확장**으로 동시에 활용. **Global Database** = 리전 간 저지연 복제·DR.
- **DynamoDB**: 기본이 리전 내 3 AZ 복제(관리형 HA). **Global Tables** = 다중 리전 **활성-활성** 복제.

한 줄 정리: **Multi-AZ = 가용성(동기·대기), Read Replica = 읽기 확장(비동기).** 둘을 바꿔 쓰면 오답.

### Route 53 — 라우팅 정책과 상태 확인
DNS 레벨에서 트래픽을 어디로 보낼지 정한다.

| 정책 | 용도 |
|---|---|
| **단순(Simple)** | 고정 레코드 하나 |
| **장애 조치(Failover)** | 주 리소스가 상태 확인 실패 시 보조로 전환 (액티브-패시브 DR) |
| **지연 시간(Latency)** | 사용자에게 가장 빠른 리전으로 |
| **가중치(Weighted)** | 비율로 분배 (카나리·A/B) |
| **지리(Geolocation)** | 사용자 위치 기준(규제·언어) |
| **지리근접(Geoproximity)** | 위치 + 바이어스로 트래픽 이동 |
| **다중값(Multivalue)** | 여러 IP 반환 + 상태 확인(간이 부하 분산) |

**상태 확인(Health Check)** 을 Failover/Multivalue와 묶어야 죽은 대상으로 보내지 않는다.

### S3 내구성·가용성 기능
- **버전 관리(Versioning)**: 덮어쓰기·삭제로부터 보호(이전 버전 보존). 삭제 마커.
- **복제**: **CRR**(교차 리전, DR·저지연) / **SRR**(동일 리전, 로그 집계·규정). 버전 관리 필수.
- **S3 스토리지 클래스**는 Domain 3·4에서 다루지만, "자주 안 쓰는 데이터 비용↓ + 가용성 유지"는 여기서도 연결될 수 있다.
- **EFS**: 다중 AZ에서 여러 EC2가 공유하는 관리형 NFS. One Zone 옵션은 단일 AZ(저비용, 가용성↓).

### 백업과 복구
- **AWS Backup**: EBS·RDS·DynamoDB·EFS 등 **중앙 집중 백업 정책**(스케줄·보존·교차 리전 복사)을 한 곳에서.
- **스냅샷**: EBS/RDS의 시점 백업. S3에 저장되고 증분.

### 재해 복구(DR) 전략 — RTO/RPO로 고른다
- **RTO(복구 목표 시간)**: 얼마나 빨리 복구되어야 하나.
- **RPO(복구 목표 시점)**: 데이터 손실을 얼마까지 허용하나.

| 전략 | 비용 | RTO/RPO | 개념 |
|---|---|---|---|
| **Backup & Restore** | 최저 | 길다(시간) | 백업만 보관, 장애 시 복구 구축 |
| **Pilot Light** | 낮음 | 중간 | 핵심(DB 등)만 켜두고 나머지는 꺼둠, 장애 시 확장 |
| **Warm Standby** | 중간 | 짧다 | 축소판 전체를 상시 가동, 장애 시 증설 |
| **Multi-Site (Active-Active)** | 최고 | 거의 0 | 두 리전 동시 운영 |

원칙: **RTO/RPO가 빡빡할수록 오른쪽(비싸고 빠른) 전략.** 비용만 중요하면 Backup & Restore.

### 복원력 설계 체크 — 한눈에
- 단일 장애점(SPOF) 제거: 다중 AZ, LB 뒤 ASG, Multi-AZ DB
- 비동기·버퍼링: SQS로 급증 흡수, 재시도·DLQ
- 상태 외부화: ElastiCache·EFS·S3·DynamoDB
- 자동 복구: ASG 상태 확인 교체, Route 53 Failover
- 데이터 보호: 버전 관리·복제·AWS Backup, RTO/RPO 맞춘 DR

## 연습문제 (Domain 2)

실제 시험처럼 "요구사항 → 적합한 구성"을 고르는 연습이다. 먼저 스스로 답을 정한 뒤 해설을 펼쳐 확인한다.

**Q1.** 주문 처리 시스템에서 생산자(웹)와 소비자(워커)의 처리 속도 차이로 트래픽 급증 때 요청이 유실된다. 가장 적합한 완충 장치는?

<details>
<summary>정답·해설</summary>

**SQS 큐**를 사이에 둔다. 웹은 큐에 넣기만 하고 워커가 자기 속도로 당겨 처리하므로, 급증분을 큐가 흡수한다. 생산·소비 속도를 분리하는 전형적 디커플링.
</details>

**Q2.** 하나의 "결제 완료" 이벤트로 **이메일 발송·재고 차감·분석 적재**를 동시에 트리거해야 한다. 각 작업은 독립적으로 버퍼링되어야 한다.

<details>
<summary>정답·해설</summary>

**SNS 팬아웃 + 각 작업별 SQS 구독.** SNS 토픽에 여러 SQS 큐를 구독시키면 한 이벤트가 여러 파이프라인으로 퍼지고, 각 큐가 독립적으로 버퍼링한다.
</details>

**Q3.** 금융 거래 메시지는 **순서가 보장**되고 **중복 처리되면 안 된다.** 어떤 큐를 쓰나?

<details>
<summary>정답·해설</summary>

**SQS FIFO 큐.** 순서 보장 + 정확히 1회 처리를 제공한다. 표준 큐는 처리량은 크지만 순서 보장이 없고 중복이 생길 수 있다.
</details>

**Q4.** 결제 → 배송 지시 → 알림으로 이어지는 다단계 워크플로에 **재시도와 분기, 사람 승인**이 필요하다.

<details>
<summary>정답·해설</summary>

**Step Functions.** 상태 머신으로 순서·분기·재시도·대기(사람 승인 포함)를 선언적으로 관리한다. Lambda끼리 코드로 엮는 것보다 견고하다.
</details>

**Q5.** HTTP 경로(`/api`, `/img`)에 따라 서로 다른 컨테이너 서비스로 트래픽을 보내야 한다.

<details>
<summary>정답·해설</summary>

**ALB(Application Load Balancer).** L7에서 경로·호스트·헤더 기반 라우팅을 하며 컨테이너/마이크로서비스에 적합하다.
</details>

**Q6.** 초고성능 TCP 처리와 **고정(정적) IP**가 필요한 게임 백엔드.

<details>
<summary>정답·해설</summary>

**NLB(Network Load Balancer).** L4에서 초고성능·초저지연을 제공하고 AZ당 고정 IP를 가진다. HTTP 라우팅 기능은 없다.
</details>

**Q7.** 웹 계층의 CPU를 평균 50%로 유지하도록 EC2 수를 자동 조절하고 싶다.

<details>
<summary>정답·해설</summary>

**Auto Scaling의 대상 추적(target tracking) 정책**으로 "평균 CPU 50%"를 목표로 설정한다. 지표 목표에 맞춰 자동 증감한다.
</details>

**Q8.** 매일 오전 9시에 트래픽이 예측 가능하게 급증한다. 급증 직전에 용량을 미리 확보하려면?

<details>
<summary>정답·해설</summary>

**예약(scheduled) 조정.** 시간 기반으로 미리 인스턴스를 늘려 둔다. 반응형(대상 추적)만으로는 급증 초반 지연이 생길 수 있다.
</details>

**Q9.** Auto Scaling으로 EC2를 자유롭게 늘리고 줄이려는데, 사용자 세션이 특정 서버에만 저장돼 그 서버가 종료되면 로그인이 풀린다.

<details>
<summary>정답·해설</summary>

**세션을 외부화**한다 — **ElastiCache(Redis)** 또는 DynamoDB에 저장해 서버를 무상태로 만든다. 스티키 세션은 임시방편일 뿐 수평 확장의 근본 해법은 상태 외부화다.
</details>

**Q10.** 여러 EC2 인스턴스가 **같은 파일 시스템을 동시에 읽고 써야** 한다.

<details>
<summary>정답·해설</summary>

**EFS.** 다중 AZ에서 여러 인스턴스가 동시 마운트하는 관리형 NFS. EBS는 기본적으로 한 인스턴스에 붙는 블록 스토리지라 부적합하다.
</details>

**Q11.** RDS 데이터베이스의 **가용성**을 높여 AZ 장애 시 자동 전환되게 하려 한다.

<details>
<summary>정답·해설</summary>

**RDS Multi-AZ.** 다른 AZ에 동기 복제된 대기본을 두고 장애 시 자동 장애 조치한다. 가용성 목적이며, 대기본으로 읽기 부하를 나누는 용도가 아니다.
</details>

**Q12.** 읽기 트래픽이 많아 DB 읽기 성능이 병목이다. 쓰기는 문제없다.

<details>
<summary>정답·해설</summary>

**읽기 전용 복제본(Read Replica)** 을 추가해 읽기를 분산한다. 비동기 복제이며 읽기 확장용이다. (Multi-AZ와 혼동 주의 — 그건 가용성용.)
</details>

**Q13.** 글로벌 사용자에게 **쓰기도 각 리전에서 저지연**으로 처리되는 키-값 저장소가 필요하다.

<details>
<summary>정답·해설</summary>

**DynamoDB Global Tables(다중 리전 활성-활성).** 각 리전에서 읽고 쓰며 리전 간 자동 복제된다.
</details>

**Q14.** 관계형 DB에서 **리전 간 재해 복구**와 리전 로컬 읽기를 모두 원한다.

<details>
<summary>정답·해설</summary>

**Aurora Global Database.** 주 리전에서 쓰고 보조 리전에 저지연 복제, 리전 장애 시 승격한다. 리전 로컬 읽기도 가능하다.
</details>

**Q15.** 주 사이트가 죽으면 DNS 레벨에서 대기 사이트로 자동 전환하고 싶다.

<details>
<summary>정답·해설</summary>

**Route 53 장애 조치(Failover) 라우팅 + 상태 확인.** 주 리소스가 상태 확인에 실패하면 보조로 넘긴다(액티브-패시브).
</details>

**Q16.** 사용자를 **가장 지연이 낮은 리전**의 엔드포인트로 보내려 한다.

<details>
<summary>정답·해설</summary>

**Route 53 지연 시간(Latency) 라우팅.** 사용자에게 응답이 가장 빠른 리전으로 보낸다. (지리 라우팅은 "위치"를, 지연 라우팅은 "속도"를 기준으로 한다.)
</details>

**Q17.** 신규 버전으로 트래픽의 **10%만** 보내 검증(카나리)하려 한다.

<details>
<summary>정답·해설</summary>

**Route 53 가중치(Weighted) 라우팅.** 레코드에 비율을 부여해 10:90으로 분배한다.
</details>

**Q18.** 규정상 특정 국가 사용자는 반드시 해당 국가 내 엔드포인트로만 접속해야 한다.

<details>
<summary>정답·해설</summary>

**Route 53 지리(Geolocation) 라우팅.** 사용자 위치에 따라 대상 엔드포인트를 지정한다.
</details>

**Q19.** S3 객체가 실수로 덮어써지거나 삭제돼도 이전 상태로 되돌릴 수 있어야 한다.

<details>
<summary>정답·해설</summary>

**버전 관리(Versioning) 활성화.** 이전 버전이 보존되고 삭제 시 삭제 마커가 생겨 복구할 수 있다. (복제·객체 잠금과 함께 자주 출제.)
</details>

**Q20.** 재해 대비로 S3 데이터를 **다른 리전**에 자동 복제하려 한다.

<details>
<summary>정답·해설</summary>

**교차 리전 복제(CRR).** 버전 관리를 켠 뒤 설정한다. 같은 리전 복제는 SRR(로그 집계·규정 용도).
</details>

**Q21.** EBS·RDS·DynamoDB·EFS 백업을 **한 곳에서 정책으로** 스케줄·보존·교차 리전 복사하고 싶다.

<details>
<summary>정답·해설</summary>

**AWS Backup.** 여러 서비스의 백업을 중앙에서 정책 기반으로 관리한다.
</details>

**Q22.** 예산이 매우 제한적이고 복구에 몇 시간이 걸려도 되는 비핵심 시스템의 DR 전략은?

<details>
<summary>정답·해설</summary>

**Backup & Restore.** 가장 저렴하며 RTO/RPO가 길다. 평소엔 백업만 보관하고 장애 시 환경을 복구한다.
</details>

**Q23.** RTO/RPO를 수 분 이내로 강하게 요구하지만 Active-Active만큼 비용을 쓰긴 어렵다.

<details>
<summary>정답·해설</summary>

**Warm Standby.** 축소판 전체 환경을 상시 가동하다 장애 시 증설한다. Pilot Light보다 빠르고 Multi-Site보다 저렴하다.
</details>

**Q24.** 핵심 DB만 보조 리전에서 복제·가동해 두고 나머지 리소스는 꺼 두었다가 장애 시 켜 올리는 전략은?

<details>
<summary>정답·해설</summary>

**Pilot Light.** 최소한의 핵심(주로 데이터 계층)만 켜두고, 장애 시 나머지를 확장한다.
</details>

**Q25.** 메시지 소비자가 반복 실패하는 메시지 때문에 큐가 막힌다. 유실 없이 격리하려면?

<details>
<summary>정답·해설</summary>

**DLQ(Dead Letter Queue).** 지정 횟수 이상 실패한 메시지를 별도 큐로 보내 격리하고, 정상 처리 흐름을 막지 않는다.
</details>

**Q26.** SQS에서 한 소비자가 처리 중인 메시지를 다른 소비자가 중복 처리한다. 원인은?

<details>
<summary>정답·해설</summary>

**가시성 제한시간(visibility timeout)이 실제 처리 시간보다 짧다.** 처리 중 메시지가 다시 보여 다른 소비자가 가져간다. 타임아웃을 처리 시간보다 길게 설정한다.
</details>

**Q27.** 컨테이너 워크로드를 운영하되 **서버(EC2) 관리를 하고 싶지 않다.**

<details>
<summary>정답·해설</summary>

**ECS/EKS on Fargate.** 서버리스 컨테이너 실행으로 인스턴스 패치·스케일을 AWS가 관리한다.
</details>

**Q28.** 트래픽을 받아 **서드파티 방화벽 어플라이언스**를 거쳐 검사한 뒤 통과시키는 구성이 필요하다.

<details>
<summary>정답·해설</summary>

**Gateway Load Balancer(GWLB).** 가상 보안 어플라이언스로 트래픽을 투명하게 삽입·체인한다.
</details>

**Q29.** 단일 AZ에만 있는 웹 서버가 그 AZ 장애 때 전체 중단된다. 최소한의 변경으로 가용성을 높이려면?

<details>
<summary>정답·해설</summary>

**여러 AZ에 걸친 Auto Scaling Group + 로드 밸런서.** 한 AZ가 죽어도 다른 AZ 인스턴스로 서비스가 이어지고, 죽은 인스턴스는 자동 교체된다.
</details>

**Q30.** DynamoDB는 이미 리전 내에서 고가용인데, 추가 설정 없이 그런 이유는?

<details>
<summary>정답·해설</summary>

**DynamoDB는 기본적으로 한 리전 내 3개 AZ에 데이터를 복제**하는 관리형 서비스이기 때문이다. 다중 리전까지 원하면 Global Tables를 켠다.
</details>

**Q31.** 읽기 전용 복제본을 리전 간에 두었다. 주 DB가 속한 리전 전체가 장애일 때 할 수 있는 조치는?

<details>
<summary>정답·해설</summary>

**다른 리전의 읽기 복제본을 독립 DB로 승격(promote)** 해 쓰기를 받게 한다. 단, 비동기 복제라 약간의 데이터 손실(RPO)이 있을 수 있다.
</details>

**Q32.** "가용성"과 "내구성"을 혼동하기 쉽다. S3가 11 9's라고 할 때 이는 무엇을 뜻하나?

<details>
<summary>정답·해설</summary>

**내구성(Durability)** — 저장된 객체가 유실되지 않을 확률이다. 지금 접근 가능한지(가용성)와는 다른 축이다. 시험은 둘을 바꿔 묻는 함정을 낸다.
</details>
