# Domain 1 — 보안 아키텍처 설계 (30%)

시험 비중이 가장 큰 도메인이다. 외우기보다 **"이 요구사항에는 어떤 서비스/구성이 맞는가"** 를 연결하는 힘을 묻는다. 그래서 각 서비스가 **무슨 문제를 푸는지**, 그리고 **비슷한 서비스와 어떻게 갈리는지**를 이해하는 게 핵심이다.

:::note 이 문서의 구성
**1.1 IAM → 1.2 네트워크·보안 서비스 → 1.3 데이터 보호(암호화)** 를 모두 다루고, 마지막에 **연습문제(해설 포함)** 로 자가 점검한다. 이 문서 하나로 Domain 1을 커버하는 것을 목표로 한다.
:::

## 1.1 안전한 접근 설계 — IAM

### IAM이 푸는 문제

AWS의 모든 요청은 "**누가(Principal)** 무엇을(Action) 어떤 리소스에(Resource) 할 수 있는가"로 판단된다. IAM은 이 질문에 답하는 **인증·인가 체계**다. 시험에서 보안 문제의 절반 이상이 결국 IAM 설계로 귀결된다.

### 구성요소 — 언제 무엇을 쓰나

- **사용자(User)**: 사람 한 명, 또는 장기 자격 증명이 꼭 필요한 대상. 콘솔 로그인용 비밀번호나 프로그램용 액세스 키를 가질 수 있다. 다만 **액세스 키를 코드·AMI에 넣는 것은 금물**이다. 유출되면 그대로 계정이 털린다.
- **그룹(Group)**: 사용자들의 묶음. 권한은 사용자 하나하나가 아니라 "개발자 그룹", "운영 그룹"처럼 그룹에 정책을 붙여 관리한다. 사람이 바뀌어도 그룹 소속만 조정하면 된다. (그룹 안에 그룹을 넣거나, 그룹에 역할을 붙일 수는 없다.)
- **역할(Role)**: 특정 신원에 **묶이지 않은** 권한 꾸러미. 필요할 때 **임시 자격 증명**을 발급받아 "빌려 쓴다". EC2·Lambda 같은 서비스가 다른 리소스에 접근할 때, 또 다른 계정의 사용자가 내 계정에 들어올 때 쓴다. **역할이 IAM의 핵심**이라고 봐도 된다.
- **정책(Policy)**: 권한을 적은 JSON 문서. 핵심 요소는 `Effect`(Allow/Deny), `Action`(예: s3:GetObject), `Resource`(대상 ARN), `Condition`(조건: 특정 IP·MFA·태그 등)이다.

### 정책의 종류 — 5가지를 구분하라

여기서 문제가 많이 나온다. 각자 "**허용을 주는가, 한계를 긋는가**"가 다르다.

| 종류 | 붙는 대상 | 성격 |
| --- | --- | --- |
| **Identity-based** | 사용자·그룹·역할 | "이 신원이 무엇을 할 수 있나"를 **부여** |
| **Resource-based** | S3 버킷·KMS 키·SQS·SNS 등 | "이 리소스에 누가 접근 가능한가". **교차 계정 허용**에 유용 |
| **SCP** (Organizations) | 계정·OU | 계정 전체의 **권한 상한선(가드레일)**. 권한을 **주지는 않고** 최대 범위만 제한 |
| **Permission Boundary** | 사용자·역할 | 그 신원이 **가질 수 있는 최대 권한**을 제한 |
| **Session Policy** | AssumeRole 시 전달 | 그 세션 동안만 추가로 좁힘 |

핵심은 **SCP와 Permission Boundary는 권한을 "주는" 게 아니라 "상한을 긋는다"** 는 점이다. 실제 허용은 Identity-based(또는 Resource-based) 정책이 하고, SCP·Boundary는 그 허용이 넘을 수 없는 천장을 정한다. 최종 권한은 이 둘의 **교집합**이다.

> 예: 개발자에게 AdministratorAccess를 붙여도, 그 계정에 "us-east-1 외 리전 금지" SCP가 있으면 다른 리전에서는 아무것도 못 한다.

### 정책 평가 로직 (순서가 중요)

요청이 들어오면 AWS는 이렇게 판단한다.

1. 기본값은 **암묵적 거부(implicit deny)** — 아무 정책도 허용하지 않으면 거부.
2. 적용되는 정책들 가운데 **명시적 Allow**가 있으면 허용 후보가 된다.
3. 그런데 **명시적 Deny가 하나라도 있으면 무조건 거부** — Deny가 Allow를 이긴다.
4. SCP·Permission Boundary·Session Policy가 있으면, 그 범위를 벗어나는 요청은 거부된다.

> 한 줄 요약: **명시적 Deny > 명시적 Allow > 암묵적 Deny**. "분명히 권한을 줬는데 안 된다"는 문제는 대개 상위의 SCP나 어딘가의 Deny 때문이다.

### 역할과 STS — 임시 자격 증명의 원리

- **STS(Security Token Service)** 가 `AssumeRole` 요청을 받아 **유효 기간이 있는 임시 키**(액세스 키 + 세션 토큰)를 내준다. 만료되면 자동으로 무효가 되므로 장기 키보다 안전하다.
- **EC2 → 인스턴스 프로파일**: EC2에 역할을 붙이면, 인스턴스 안의 앱은 **키 없이** 자동으로 그 역할의 임시 자격 증명을 받아 S3·DynamoDB 등에 접근한다. "EC2의 앱이 S3에 접근해야 한다"는 문제의 정답은 거의 항상 **역할**이고, 액세스 키를 넣는 보기는 오답이다.
- **교차 계정 접근**: 접근받을 계정(B)에 역할을 만들고, 그 역할의 **신뢰 정책(Trust Policy)** 에 접근할 계정(A)을 신뢰 대상으로 넣는다. 그러면 A의 사용자가 B의 역할을 AssumeRole 할 수 있다.
- **서비스 역할**: Lambda 실행 역할처럼, AWS 서비스가 사용자를 대신해 다른 리소스를 다룰 때 쓰는 역할.

### 연합(Federation) — 외부 신원을 끌어오기

사용자를 IAM에 일일이 만들지 않고, 이미 있는 신원 체계로 로그인시키는 방법이다. 시나리오별로 정답이 갈린다.

- **기업 직원(사내 AD/IdP)** → **SAML 2.0 연합** 또는 **IAM Identity Center**(구 AWS SSO). 여러 계정·앱에 한 번 로그인으로 접근.
- **모바일·웹 앱의 일반 사용자(수백만 명)** → **Amazon Cognito**. Google·Apple 같은 소셜 로그인(OIDC/Web Identity)을 받아 임시 AWS 자격 증명으로 바꿔 준다. "앱 사용자에게 S3 임시 접근" 류 문제의 정답.
- **온프렘 AD 연계** → **AWS Managed Microsoft AD** 또는 **AD Connector**.

### Organizations와 SCP

여러 AWS 계정을 쓸 때 **AWS Organizations**로 묶어 관리한다. 계정을 **OU(조직 단위)** 로 묶고, **SCP**로 "이 OU의 계정들은 무엇까지만 할 수 있다"는 상한을 일괄 적용한다. 예를 들어 "운영 OU는 특정 리전만", "모든 계정에서 루트 사용자 특정 작업 금지" 같은 거버넌스를 중앙에서 건다. 통합 결제, 계정 자동 생성도 Organizations의 기능이다.

### 자격 증명 보호 모범 사례

- **루트 계정**: 일상 사용 금지. **MFA 활성화**, 액세스 키 삭제, 최초 설정 이후 거의 쓰지 않는다.
- **최소 권한 원칙**: 필요한 만큼만. 넓게 주고 줄이기보다, 좁게 주고 필요 시 늘린다.
- **사람은 역할·연합으로**: 장기 사용자·키를 늘리지 말고, 가능하면 Identity Center나 역할로 임시 자격 증명을 쓴다.
- **점검 도구**: **IAM Access Analyzer**(외부·교차 계정에 노출된 리소스 탐지), **Credential Report**(계정 자격 증명 현황), **Access Advisor**(마지막 사용 시점으로 과잉 권한 정리).

:::tip 1.1 시험 포인트
- EC2/서비스가 다른 리소스 접근 → **역할**. 키 하드코딩 보기는 오답.
- **명시적 Deny가 최우선**. SCP·Boundary는 권한 부여가 아니라 상한.
- 교차 계정 → **역할 + 신뢰 정책**. 리소스 공유만이면 **리소스 기반 정책**도 가능.
- 앱 사용자 대량 로그인 → **Cognito**. 기업 직원 SSO → **Identity Center/SAML**.
:::

## 1.2 안전한 네트워크·워크로드 설계

### VPC 기본 복습

**VPC**는 내 전용 가상 네트워크다. 그 안을 **서브넷**으로 나눈다.

- **퍼블릭 서브넷**: 라우팅이 **인터넷 게이트웨이(IGW)** 로 향해, 인터넷과 직접 통신 가능. 로드 밸런서·배스천 등을 둔다.
- **프라이빗 서브넷**: 인터넷과 직접 통신 불가. DB·앱 서버를 둔다.
- **NAT 게이트웨이**: 프라이빗 서브넷이 **아웃바운드만**(패치 다운로드 등) 인터넷에 나가게 해준다. 외부에서 들어오는 인바운드는 열어 주지 않는다.

### 보안 그룹 vs 네트워크 ACL — 가장 자주 나온다

| 구분 | 보안 그룹(SG) | 네트워크 ACL(NACL) |
| --- | --- | --- |
| 적용 단위 | 인스턴스(ENI) | 서브넷 |
| 상태 | **Stateful** | **Stateless** |
| 규칙 | **Allow만** | Allow·**Deny 모두** |
| 평가 | 전체 규칙 종합 | **번호 순서**대로, 먼저 맞는 규칙 적용 |

- **Stateful(SG)**: 들어오는 요청을 허용하면, 그에 대한 **응답은 규칙 없이 자동 허용**된다. 그래서 보통 인바운드만 신경 쓰면 된다.
- **Stateless(NACL)**: 들어옴과 나감을 **따로** 허용해야 한다. 응답 트래픽을 위한 아웃바운드 규칙(임시 포트 범위)을 깜빡하면 통신이 막힌다.
- **특정 IP를 차단**해야 하면 SG로는 불가능하다(SG는 Allow만). 이때는 **NACL의 Deny 규칙**을 쓴다. 이게 전형적인 함정 문제다.

### VPC 엔드포인트 — 인터넷 없이 AWS 서비스 접근

프라이빗 서브넷에서 S3 같은 서비스에 **인터넷을 거치지 않고** 접근하고 싶을 때 쓴다.

- **게이트웨이 엔드포인트**: **S3와 DynamoDB 전용**. 라우팅 테이블에 경로를 추가하는 방식. **무료**.
- **인터페이스 엔드포인트(PrivateLink)**: 그 외 대부분 서비스. 서브넷에 **ENI(프라이빗 IP)** 를 만들어 연결. **시간당 과금**.

> "프라이빗 서브넷에서 S3 접근, NAT 비용 없이" → **게이트웨이 엔드포인트**. 그 외 서비스면 인터페이스 엔드포인트.

### 운영 접근 — 배스천 대신 Session Manager

예전에는 프라이빗 서버에 들어가려고 퍼블릭 서브넷에 **배스천 호스트**를 두고 SSH로 거쳐 갔다. 지금은 **SSM Session Manager**가 권장된다. **포트(22)를 열지 않고**, 키 관리 없이, IAM 권한으로 접속하며, 접속 기록이 로깅된다. "SSH 포트를 열지 않고 안전하게 접속" 문제의 정답.

### 보안 서비스 지도 — 무엇을 하는지 구분

이름이 비슷해 헷갈리므로 **역할**로 외운다.

- **WAF**: L7(HTTP) **웹 공격 필터**. SQL 인젝션·XSS·봇 등을 룰로 차단. CloudFront·ALB·API Gateway 앞단에 붙인다.
- **Shield**: **DDoS 방어**. Standard는 자동·무료, **Advanced**는 유료로 대규모 공격 대응·비용 보호·전문 지원.
- **GuardDuty**: 로그(VPC Flow·CloudTrail·DNS)를 분석해 **이상 행위·위협을 탐지**. 에이전트 없이 켜기만 하면 된다.
- **Inspector**: EC2·컨테이너 이미지·Lambda의 **취약점(CVE)·구성 점검**.
- **Macie**: **S3의 민감정보(개인정보 등) 탐지·분류**.
- **Security Hub**: 여러 보안 서비스 결과와 표준 점검을 **한 대시보드로 통합**.
- **Detective**: 탐지된 사건의 **원인·연관 관계 분석**(조사용).
- **Network Firewall**: VPC 레벨의 **상태 기반 방화벽/IPS**.
- **Firewall Manager**: 여러 계정의 WAF·SG·Shield 규칙을 **중앙에서 일괄 관리**.

> 구분 요령: **위협 탐지=GuardDuty, 취약점=Inspector, 민감정보=Macie, 통합=Security Hub, 조사=Detective**.

### 비밀 관리 — Secrets Manager vs Parameter Store

| 구분 | Secrets Manager | Parameter Store(SSM) |
| --- | --- | --- |
| **자동 교체(rotation)** | **지원**(RDS 등과 연동) | 기본 미지원 |
| 비용 | 유료 | 표준 등급 무료 |
| 용도 | DB 비밀번호·API 키 등 **교체가 필요한 비밀** | 설정값·일반 파라미터, 가끔 비밀 |

> "DB 자격 증명을 **주기적으로 자동 교체**" → **Secrets Manager**. 단순 설정값·환경값 → Parameter Store.

:::tip 1.2 시험 포인트
- **IP 차단은 NACL(Deny)**, 세밀한 허용은 SG(Stateful).
- **S3·DynamoDB는 게이트웨이 엔드포인트**(무료), 나머지는 인터페이스(PrivateLink).
- **SSH 포트 안 열고 접속 → SSM Session Manager**.
- 서비스 역할 구분: 탐지 GuardDuty / 취약점 Inspector / 민감정보 Macie / 통합 Security Hub.
- **자동 교체 비밀 → Secrets Manager**.
:::

## 1.3 데이터 보호 — 암호화

### 두 가지 축: 전송 중 vs 저장 시

- **전송 중 암호화(in transit)**: 네트워크를 지나는 데이터를 TLS로 보호. 인증서는 **ACM**으로 발급·자동 갱신한다.
- **저장 시 암호화(at rest)**: 디스크·스토리지에 저장된 데이터를 암호화. 대부분 **KMS** 기반이다.

### 봉투 암호화(envelope encryption)

KMS의 핵심 개념이다. 데이터를 **데이터 키(DEK)** 로 암호화하고, 그 데이터 키를 다시 **KMS의 마스터 키(CMK)** 로 암호화해 함께 저장한다. 큰 데이터를 KMS에 매번 보내지 않고 로컬에서 빠르게 암·복호화하면서도, 마스터 키는 KMS 밖으로 절대 나가지 않는다. 복호화할 때만 KMS에 "이 암호화된 데이터 키를 풀어 달라"고 요청한다.

### KMS 키 종류

| 종류 | 생성·통제 | 특징 |
| --- | --- | --- |
| **AWS 관리형 키** | AWS가 생성(`aws/s3` 등) | 키 정책·교체를 사용자가 거의 못 바꿈. 무료 |
| **고객 관리형 키(CMK)** | 사용자가 생성 | **키 정책 제어 · 교체 설정 · 삭제 · 감사** 가능. 세밀한 제어가 필요하면 이것 |
| **AWS 소유 키** | AWS 소유 | 사용자에게 보이지 않음 |

- **키 정책(Key Policy)** 이 KMS 접근의 1차 기준이다. IAM 정책만으로는 부족하고, 키 정책에서 그 주체를 허용해야 한다.
- **키 교체**: 고객 관리형 키는 **자동 교체(기본 1년)** 를 켤 수 있다. 수동 교체도 가능.
- **키 삭제**: 즉시 삭제가 아니라 **7~30일 대기 기간** 후 삭제된다(실수 방지).
- **멀티 리전 키**: 여러 리전에 같은 키를 복제해 교차 리전 암호화에 사용.

### KMS vs CloudHSM

| 구분 | KMS | CloudHSM |
| --- | --- | --- |
| 형태 | 완전관리형(멀티테넌트) | **전용 하드웨어 HSM**(단일 테넌트) |
| 키 통제 | AWS와 공유 책임 | **고객이 완전 통제**(AWS도 접근 불가) |
| 규정 | 일반 | **FIPS 140-2 Level 3**, 전용 HSM이 요구될 때 |

> "키를 **고객이 완전히 통제**해야 한다 / 전용 HSM 규정" → **CloudHSM**. 그 외 일반 암호화는 KMS.

### S3 암호화 옵션

| 방식 | 키 관리 | 포인트 |
| --- | --- | --- |
| **SSE-S3** | S3가 관리(AES-256) | 가장 단순. 기본값 |
| **SSE-KMS** | KMS 키 사용 | 접근 **감사·키 제어** 가능. **버킷 키**로 KMS 호출 비용 절감 |
| **SSE-C** | **고객이 키 제공** | AWS는 키를 저장하지 않음. 요청마다 키 전달 |
| **DSSE-KMS** | KMS(이중 암호화) | 규정상 이중 레이어가 필요할 때 |

- **암호화 강제**: 버킷 정책에서 `s3:x-amz-server-side-encryption` 조건으로, 암호화 헤더 없는 PUT을 **거부**한다.
- **전송 암호화 강제**: 버킷 정책 `aws:SecureTransport=false` 거부로 HTTP(비TLS) 접근을 막는다.

### 다른 서비스의 저장 암호화

- **EBS**: KMS로 볼륨 암호화. **계정 기본 암호화**를 켜면 새 볼륨이 자동 암호화. 암호화 볼륨의 스냅샷·복제본도 암호화된다.
- **RDS**: **생성 시에만** 암호화 설정 가능. 기존 비암호화 DB를 암호화하려면 **스냅샷을 암호화 복사 → 복원**한다. (시험 단골)
- **DynamoDB**: 기본적으로 저장 암호화됨.

### ACM (Certificate Manager)

- TLS 인증서를 **무료로 발급·자동 갱신**한다.
- **ALB · CloudFront · API Gateway** 등 통합 서비스에 붙여 쓴다.
- 주의: **EC2 인스턴스에 ACM 공인 인증서를 직접 설치할 수는 없다**(통합 서비스에서만 사용). EC2에서 TLS 종료가 필요하면 앞단에 ALB/CloudFront를 둔다.

:::tip 1.3 시험 포인트
- **키 완전 통제·전용 HSM → CloudHSM**, 일반 관리형 → KMS.
- **접근 감사·키 제어가 필요한 S3 암호화 → SSE-KMS**, 가장 단순하면 SSE-S3.
- **암호화 없는 업로드 차단 → 버킷 정책 조건**. HTTP 차단 → `aws:SecureTransport`.
- **기존 RDS 암호화 전환 → 스냅샷 암호화 복사 후 복원**.
- **ACM은 ALB/CloudFront용**. EC2 직접 설치 불가.
- **봉투 암호화**: 데이터 키로 데이터를, CMK로 데이터 키를 암호화.
:::

## 연습문제 (Domain 1)

실제 시험처럼 "요구사항 → 적합한 구성"을 고르는 연습이다. 먼저 스스로 답을 정한 뒤 해설을 펼쳐 확인한다.

**Q1.** EC2 인스턴스의 애플리케이션이 S3 버킷에 접근해야 한다. 가장 안전한 방법은?

<details>
<summary>정답·해설</summary>

**IAM 역할을 만들어 EC2 인스턴스 프로파일로 연결한다.** 액세스 키를 코드·환경변수·AMI에 넣는 방식은 유출 위험 때문에 오답이다. 역할을 쓰면 임시 자격 증명이 자동 교체된다.
</details>

**Q2.** 회사가 여러 AWS 계정을 Organizations로 운영한다. 특정 OU의 모든 계정에서 "us-east-1 외 리전 사용"을 전면 금지하고 싶다. 무엇을 쓰나?

<details>
<summary>정답·해설</summary>

**SCP(서비스 제어 정책)** 를 해당 OU에 적용한다. SCP는 권한을 부여하지 않고 **상한선**을 긋는다. 계정 내 사용자가 Admin 권한이어도 SCP가 막으면 불가능하다.
</details>

**Q3.** 개발자에게 넓은 권한을 주되, 그가 만드는 IAM 역할·사용자가 가질 수 있는 권한의 상한을 제한하고 싶다.

<details>
<summary>정답·해설</summary>

**Permission Boundary**를 사용한다. 그 신원이 가질 수 있는 최대 권한을 제한하는 용도다. 최종 권한은 부여된 정책과 Boundary의 **교집합**이다.
</details>

**Q4.** 특정 악성 IP 대역에서 오는 트래픽만 차단해야 한다. EC2 앞단에서 어떻게?

<details>
<summary>정답·해설</summary>

**네트워크 ACL의 Deny 규칙**을 사용한다. 보안 그룹은 **Allow만** 가능하므로 "차단"을 표현할 수 없다. NACL은 서브넷 단위이며 Deny를 쓸 수 있다.
</details>

**Q5.** 프라이빗 서브넷의 EC2가 **S3**에 접근해야 하는데, NAT 게이트웨이 비용을 피하고 인터넷을 거치지 않으려 한다.

<details>
<summary>정답·해설</summary>

**게이트웨이 VPC 엔드포인트**를 만든다. S3와 DynamoDB 전용이며 무료이고, 라우팅 테이블에 경로를 추가한다. (그 외 서비스는 인터페이스 엔드포인트/PrivateLink, 시간당 과금.)
</details>

**Q6.** 프라이빗 서브넷의 리눅스 서버에 SSH 포트(22)를 열지 않고 안전하게 접속·명령 실행하고 싶다.

<details>
<summary>정답·해설</summary>

**AWS Systems Manager Session Manager**를 사용한다. 포트 개방·키 관리 없이 IAM 권한으로 접속하고, 접속 기록이 로깅된다. 배스천 호스트보다 권장된다.
</details>

**Q7.** 계정 전반의 위협(비정상 API 호출, 악성 IP 통신 등)을 로그 기반으로 자동 탐지하고 싶다. 에이전트 설치는 피한다.

<details>
<summary>정답·해설</summary>

**GuardDuty.** VPC Flow Logs·CloudTrail·DNS 로그를 분석해 위협을 탐지한다. 에이전트가 필요 없다. (취약점 스캔은 Inspector, 민감정보 탐지는 Macie.)
</details>

**Q8.** EC2·컨테이너 이미지의 **소프트웨어 취약점(CVE)** 을 점검하려 한다.

<details>
<summary>정답·해설</summary>

**Amazon Inspector.** 취약점·구성 점검 도구다. 위협 행위 탐지(GuardDuty)와 혼동하지 말 것.
</details>

**Q9.** S3 버킷들에 **개인정보(PII)** 가 저장돼 있는지 자동으로 탐지·분류하고 싶다.

<details>
<summary>정답·해설</summary>

**Amazon Macie.** S3의 민감정보를 머신러닝으로 탐지·분류한다.
</details>

**Q10.** RDS 데이터베이스 **비밀번호를 주기적으로 자동 교체**하고 애플리케이션이 안전하게 가져가게 하려 한다.

<details>
<summary>정답·해설</summary>

**AWS Secrets Manager.** 자동 교체(rotation)를 지원하고 RDS와 연동된다. 단순 설정값은 Parameter Store로도 되지만 자동 교체가 핵심 요구면 Secrets Manager.
</details>

**Q11.** 다른 AWS 계정(B)의 사용자가 내 계정(A)의 역할을 사용해 리소스에 접근하게 하려면?

<details>
<summary>정답·해설</summary>

내 계정(A)에 역할을 만들고 그 역할의 **신뢰 정책(Trust Policy)** 에 계정 B를 신뢰 대상으로 넣는다. 그러면 B의 사용자가 `sts:AssumeRole`로 그 역할을 맡는다.
</details>

**Q12.** 수백만 명의 모바일 앱 사용자가 각자 자기 S3 폴더에만 임시로 접근하게 하려 한다.

<details>
<summary>정답·해설</summary>

**Amazon Cognito.** 소셜/OIDC 로그인을 받아 임시 AWS 자격 증명으로 바꿔 준다. 사용자마다 IAM 사용자를 만드는 것은 확장성 없는 오답.
</details>

**Q13.** 기업 직원들이 기존 사내 Active Directory 계정으로 여러 AWS 계정에 SSO 하게 하려 한다.

<details>
<summary>정답·해설</summary>

**IAM Identity Center**(구 AWS SSO), 또는 **SAML 2.0 연합**. 기업 직원·다계정 SSO 시나리오다. (대량 앱 사용자는 Cognito와 구분.)
</details>

**Q14.** 저장되는 S3 객체를 KMS로 암호화하되, **누가 언제 복호화했는지 감사**하고 키를 직접 통제하고 싶다.

<details>
<summary>정답·해설</summary>

**SSE-KMS.** KMS를 통해 접근이 CloudTrail에 남아 감사 가능하고, 고객 관리형 키로 제어할 수 있다. SSE-S3는 감사·키 제어가 약하다.
</details>

**Q15.** 버킷에 올라오는 모든 객체가 반드시 서버 측 암호화되도록 **강제**하려 한다.

<details>
<summary>정답·해설</summary>

**버킷 정책**에서 `s3:x-amz-server-side-encryption` 헤더가 없는 PUT 요청을 **Deny**한다. (기본 암호화 설정과 함께 쓰면 더 안전.)
</details>

**Q16.** 규정상 **암호화 키를 고객이 완전히 소유·통제**해야 하고 FIPS 140-2 Level 3 전용 HSM이 필요하다.

<details>
<summary>정답·해설</summary>

**AWS CloudHSM.** 전용 하드웨어 HSM으로 고객이 키를 완전 통제한다. KMS는 AWS와 공유 책임이라 이 요구를 충족하지 못한다.
</details>

**Q17.** 기존에 **암호화하지 않고 만든 RDS** 인스턴스를 암호화된 상태로 바꾸려 한다.

<details>
<summary>정답·해설</summary>

스냅샷을 만든 뒤 **암호화 옵션으로 스냅샷을 복사**하고, 그 암호화 스냅샷에서 **복원**한다. RDS는 생성 시에만 암호화를 켤 수 있어 직접 전환은 불가능하다.
</details>

**Q18.** ALB 뒤의 웹 애플리케이션에 **SQL 인젝션·XSS** 같은 L7 공격을 막으려 한다.

<details>
<summary>정답·해설</summary>

**AWS WAF**를 ALB(또는 CloudFront/API Gateway)에 붙인다. L7 HTTP 요청을 룰로 필터링한다. (대규모 DDoS는 Shield.)
</details>

**Q19.** EC2에서 직접 HTTPS를 제공하려고 ACM 공인 인증서를 설치하려는데 안 된다. 왜, 그리고 대안은?

<details>
<summary>정답·해설</summary>

**ACM 공인 인증서는 EC2에 직접 설치할 수 없다.** ACM은 ALB·CloudFront·API Gateway 같은 통합 서비스에서만 쓰인다. 대안은 앞단에 **ALB/CloudFront를 두고 거기서 TLS 종료**하는 것.
</details>

**Q20.** "분명히 IAM 정책으로 S3 권한을 Allow 했는데" 특정 사용자가 접근을 못 한다. 가장 가능성 높은 원인은?

<details>
<summary>정답·해설</summary>

어딘가에 **명시적 Deny**가 있거나(SCP·버킷 정책·Permission Boundary 포함), 상위 **SCP가 범위를 막고** 있을 가능성이 높다. 평가 로직상 **명시적 Deny는 어떤 Allow보다 우선**한다.
</details>

> 20문항을 막힘없이 설명할 수 있으면 Domain 1은 충분히 준비된 것이다. 틀린 문항은 위 본문의 해당 절로 돌아가 다시 본다.
