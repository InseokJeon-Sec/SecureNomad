# 고급 검색 패턴

기본을 넘어, 프로덕션 RAG 시스템은 복잡한 쿼리-문서 간극을 다루는 전문 패턴을 쓴다. 이 패턴들은 고정밀 검색의 "비밀 소스"이며 점점 관리형 RAG 제공에 번들된다.

## 쿼리 분해(멀티 쿼리)

복잡한 사용자 쿼리는 흔히 "복합 쿼리"다.
- **사용자**: "우리 Q3 vs Q4 매출을 비교하고 하락을 설명해."
- **분해**:
  1. "Q3 매출"
  2. "Q4 매출"
  3. "Q4 매출 변동 이유"
- **구현**: LLM으로 이 3 하위 쿼리 생성, 모두를 DB 검색, 문맥 집계.

---

## 가설 문서 임베딩(HyDE)

쿼리는 짧고 문서는 길다. 이 "비대칭"이 검색 실패를 유발.
- **패턴**:
  1. 사용자 쿼리를 받음.
  2. LLM에 요청: "이에 대한 1문단 가설 답을 써."
  3. 쿼리 대신 **가설 답을 임베딩**.
- **왜?**: 가설 답이 실제 문서와 같은 "벡터 이웃"에 있어 훨씬 높은 재현율.

---

## 문맥 검색(Anthropic 패턴)

Anthropic이 2024년 9월 발표, 이 패턴은 **문맥 희석**을 해결.

- **문제**: 청크가 "$200 든다"라 해도 헤더 없이는 "그것"이 "Widget-X"인지 모름.
- **패턴**: 수집 중 300토큰 청크마다 LLM이 50-100토큰 문맥 문자열(예: "이 청크는 북미 시장 Widget-X 가격에 관함")을 써 임베딩·BM25 인덱싱 전 접두.
- **이점**: Anthropic은 문맥 임베딩만으로 top-20 검색 실패 35% 감소, 문맥 BM25 추가로 49%, 재순위까지 67% 측정.
- **2026 대안**: 문맥화 청크 임베딩 모델(voyage-context-4)이 청크당 LLM 호출 없이 문서 인식 청크 벡터를 내나 dense 쪽만 도움. 전체는 [문맥 검색](10-contextual-retrieval.md).

## 반복 문서 강화

원시 문서만 저장하는 대신 "강화된" 메타데이터를 저장.
- **요약**: 문서의 1문단 요약 저장.
- **Q&A 생성**: 이 문서가 답하는 질문 5개 생성, 문서와 *함께* 임베딩.
- **상태**: 많은 고급 RAG가 생성 **"질문"** 을 청크 텍스트와 나란히 임베딩해, 짧은 사용자 질문이 긴 답 단락 대신 저장된 질문과 매치.

---

## 인컨텍스트 재순위

프런티어 모델에 1M 토큰 윈도가 표준이 된 지금(Claude Opus 5.5·Sonnet 5.5, GPT-6 계열 1.05M, Gemini 3.8 Flash), **문맥으로 순위**가 가능한 패턴.
1. Top 100 문서 검색.
2. 100개 전부를 문맥 윈도에.
3. 모델에 요청: "이 100 문서를 읽고 가장 관련된 5개 식별. 그 5개로 답."
- **승리**: 별도 크로스 인코더 없이 모델의 **장문맥 추론**으로 재순위 수행.
- **비용 검사**: 500토큰 100문서는 쿼리당 5만 입력 토큰: Claude Sonnet 5.5·GPT-6 Sol 같은 1M당 $2 모델에 약 $0.10, 같은 토큰이 Voyage rerank-3($0.05/1M)엔 약 $0.0025, 출력 토큰 전 40배 격차. 저볼륨·추론 중심 쿼리에 예약하고 프롬프트를 장문맥 가격 절벽(OpenAI 272K, xAI 200K) 아래로.

## 면접 질문

### Q: HyDE(가설 문서 임베딩)가 일부 애플리케이션에 위험한 이유는?

**좋은 답변:**
HyDE는 실제 데이터를 찾으려 기준 답을 "환각"하는 데 의존. 사용자 쿼리가 존재하지 않거나 논리적으로 불가능한 걸 기술하면 LLM이 여전히 가설 답을 생성. 이는 DB에서 "부정확하나 의미적으로 유사한" 데이터를 끌어와 모델 초기 환각을 강화할 수 있다. 표준 완화는 **하이브리드 접근**: 실제 쿼리(키워드)로 한 번, HyDE 쿼리로 한 번 검색 후 **RRF**로 결합.

### Q: "비대칭 검색" 문제란?

**좋은 답변:**
비대칭 검색은 사용자 쿼리가 보통 짧고(3-10 단어) 문서 청크가 긴(300-500 단어) 사실을 가리킨다. 이들은 벡터 공간에서 다른 통계 분포에 살아 "거리 편향"을 낳는다. 고성능 시스템은 **비대칭 인코더**(별도 쿼리·문서 프리픽스·모델)나 **쿼리 확장**(HyDE)으로 쿼리를 문서 같은 분포로 "부풀려" 해결.

비대칭은 이제 비용 레버이기도. Voyage 4와 Cohere Embed 5가 한 공유 공간의 모델 계열을 출시해, 큰 모델로 문서 인덱싱, 작은 모델로 쿼리 인코딩 가능. Qdrant Constella 연구 프리뷰는 더 나아감: 고정 400M Stella 문서 인덱스 + 34.5M 쿼리 인코더가 BEIR-15 nDCG@10의 약 91%를 12배 낮은 CPU 지연으로(벤더). 고 QPS에선 쿼리 인코딩이 핫 패스, 문서 인코딩은 아니니, 모델 예산을 문서 쪽에 쓰라.
