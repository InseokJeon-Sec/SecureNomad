# 청킹 전략

청킹은 검색을 위해 문서를 개별 세그먼트로 나누는 과정이다. 프로덕션 파이프라인은 맹목적 고정 크기 분할을 넘어 **구조 인식·의미 세그먼트**로 옮겨갔고, 레이트 청킹·문맥 접두 같은 신기법이 이제 주류 도구에 들어왔다.

## 검색-문맥 긴장

| 측면 | 작은 청크(100t) | 큰 청크(1000t) |
|--------|---------------------|----------------------|
| **정밀도** | 높음(정확 일치) | 낮음(희석) |
| **문맥** | 빈약(끊긴 문장) | 풍부(주변 정보) |
| **저장** | 많음(더 많은 벡터) | 적음(더 적은 벡터) |
| **지연** | 낮음(빠른 검색) | 높음(무거운 검색) |

**규칙**: *찾기*엔 작을수록 좋고 *사고*엔 클수록 좋다. **계층 청킹**으로 둘 다 얻어라.

---

## 재귀 구조 분할

500자마다 자르는 대신 논리 경계에서 분할한다:
`[이중 줄바꿈] > [단일 줄바꿈] > [마침표] > [공백]`.

**베스트 프랙티스**: **마크다운 인식 분할** 사용. 문서에 `#` 헤더가 있으면 문맥 보존을 위해 헤더를 *모든* 자식 청크에 접두(문맥 청킹).

---

## 의미 청킹

의미 청킹은 임베딩 모델로 "주제 전환"을 탐지한다.

1. 텍스트를 개별 문장으로 분할.
2. 임베딩 유사도가 임계(예: 0.82) 이상인 한 문장을 묶음.
3. 유사도가 떨어지면 새 청크 시작.

**뉘앙스**: 일부 파이프라인은 임계를 **학습된 세그먼터**로 대체 — 작은 모델이 텍스트를 훑어 모든 의미 경계에서 구분자를 예측. 코퍼스별 코사인 컷오프 수동 튜닝을 피하나, 발표된 청킹 벤치마크가 고정 크기·재귀·의미 전략 간 크게 흔들리니, 추가 모델에 돈을 쓰기 전 자신의 문서에서 재현율을 측정하라.

## 계층(부모-자식) 청킹

프로덕션 RAG의 업계 표준이다.

- **과정**:
  1. 1,500 토큰의 "부모" 청크 생성.
  2. 각 부모를 300 토큰의 "자식" 5개로 세분.
  3. **자식만 인덱싱**.
  4. 검색 시 자식이 매치되면 **전체 부모 문맥을 LLM에 반환**.
- **왜?**: 자식은 작아 벡터 DB가 매치하기 쉽다. 부모는 "끊긴 문맥" 환각 없이 LLM이 실제로 올바르게 추론할 충분한 문맥을 준다.

---

## 레이트 청킹과 문맥화 청크 임베딩

계층 청킹은 *읽기* 시점에 문맥을 고친다. 대안은 *임베딩* 시점에 고쳐 각 청크 벡터가 어느 문서에서 왔는지 이미 알게 하는 것.

- **레이트 청킹**(Jina, 2024): 전체 문서에 장문맥 임베딩 모델을 돌린 뒤 청크 스팬별로 토큰 임베딩을 풀링. 모든 청크 벡터가 추가 LLM 호출 없이 전체 문서에 조건부.
- **문맥화 청크 임베딩 모델**은 이를 API로 패키징. **voyage-context-4**(GA 2026-06-29; 1M 토큰당 $0.12, 32K 윈도, 내장 자동 청킹)는 청크당 문서 인식 벡터 하나를 반환; Voyage는 voyage-context-3 대비 청크 수준 +2.08%·문서 수준 +1.4% 검색 보고(벤더). Perplexity **pplx-embed-v2-context-9b-preview**(2026-09-25)는 문서 청크를 함께 인코딩하나, 벡터를 이후 릴리스와 섞으면 안 되는 명시적 프리뷰.

Anthropic 식 문맥 접두와의 트레이드오프: 임베더 측 문맥은 청크당 LLM 호출이 없으나 dense 쪽만 돕는다. BM25는 여전히 맨 청크 텍스트를 보므로 희소 인덱스엔 헤더 접두를 유지하라. 전체 비용 비교는 [문맥 검색](10-contextual-retrieval.md)에 있다.

## 콘텐츠별 전략

### 1. 코드 청킹
- **전략**: AST(추상 구문 트리) 파싱 사용.
- **규칙**: 함수를 본문 중간에 자르지 말 것. 임포트·클래스 선언을 메서드와 함께 유지.

### 2. 표 청킹
- **전략**: 표에 마크다운 포맷 사용.
- **현대 패턴**: "요약 표." 표의 자연어 요약을 벡터 DB에 저장하되, 전체 마크다운 표를 LLM에 반환.

### 3. PDF/레이아웃 청킹
- **전략 A, 파싱 후 청킹**: 레이아웃 인식 파서(Docling, MinerU, Cohere Parse, 또는 오픈 파싱 VLM)로 읽기 순서 블록을 내되 표·그림·사이드바를 별도 타입 요소로. 그 블록 경계에서 청킹해 차트·사이드바가 본문에 섞이지 않게.
- **전략 B, 텍스트 청킹 건너뛰기**: 각 페이지 이미지를 레이트 인터랙션 모델(ColPali 계열)로 직접 임베딩. 페이지 *자체*가 단위라 레이아웃이 보존됨. [멀티모달 RAG](12-multimodal-rag.md) 참고.
- **에이전트 지향 패턴**: 에이전트 RAG엔 미리 자른 청크 대신 안정 블록 로케이터를 주는 것을 고려. MinerU 4.0(2026-09-16)은 `doc:{id}/tier:{tier}/page:{page}/block:{block}` 형식 로케이터를 반환하고 긴 문서를 점진적으로 읽어(첫 10페이지 + 연속), 에이전트가 문서를 탐색하고 인용이 검증 가능한 블록을 가리킴.

## 면접 질문

### Q: 오버랩 있는 고정 크기 청킹이 프로덕션에 문제인 이유는?

**좋은 답변:**
고정 크기 청킹은 "콘텐츠 맹목적"이다. 문장을 생각 중간에 자르고, 수식을 깨고, 헤더를 설명 텍스트에서 분리하기 일쑤다. "오버랩"(예: 10%)이 청크 간 10% 텍스트를 중복해 완화하나 핵심 문제를 해결 못 한다: 모델 주의가 파편 문자열에서 의미를 재구성하도록 강제된다. 현대 파이프라인은 각 벡터가 "완전한 의미 단위"를 나타내게 보장해 검색 정밀도를 크게 높이는 **의미·논리 청킹**을 선호한다.

### Q: "문맥 검색"(Anthropic 패턴)이란?

**좋은 답변:**
문맥 검색은 임베딩·BM25 인덱싱 전 모든 청크에 LLM이 쓴 짧은 문맥을 접두하는 것. 예로 청크가 "배터리 수명"에 관한데 "2025 Model X 드론" 매뉴얼에서 온 거라면, `이 청크는 Model X 드론 매뉴얼의 배터리 섹션에서:` 같은 줄을 더한다. 이로써 "배터리 수명" 벡터가 "드론" 문맥에 영향받아 "폰 배터리" 쿼리에 잘못 검색되지 않는다. Anthropic은 문맥 임베딩만으로 top-20 검색 실패 35% 감소, 문맥 BM25 추가 시 49%, 재순위까지 얹으면 67% 감소를 측정.

비용은 수집 시 청크당 LLM 호출 하나(원본 문서 프롬프트 캐싱으로 저렴). 2026 대안은 voyage-context-4 같은 문맥화 청크 임베딩 모델로, LLM 호출 없이 문서 인식 벡터를 얻으나 BM25엔 아무것도 안 함. 내 기본값: 두 인덱스 모두 헤더 접두, dense엔 임베더 측 문맥 모델, LLM 문맥화는 골든셋에서 여전히 실패하는 문서 유형에만.
