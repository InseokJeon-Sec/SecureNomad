# 계획과 분해

계획은 에이전트가 "방황" 없이 다단계 문제를 풀게 하는 "System 2" 구성요소다. 프로덕션 에이전트는 단순 "사고 사슬"에서 **재귀 분해**·**트리 탐색**으로 옮겨갔고, 추론 네이티브 모델(Claude Opus 5.5·Fable 5.1, GPT-6 Astra·GPT-6.1 Sol)이 설정한 노력 레벨로 무거운 계획을 내부에서 한다.

## 계획 스펙트럼

| 방법 | 전략 | 복잡도 | 적합 |
|--------|----------|------------|----------|
| **선형** | 한 번에 한 단계 | 낮음 | 단순 도구 |
| **분기** | If-Then-Else 로직 | 중간 | 조건 흐름 |
| **계층** | 마스터 계획 → 하위 계획 | 높음 | 소프트웨어 엔지니어링 |
| **탐색 기반** | 내부적으로 여러 경로 시도 | 최대 | 과학 연구 |

---

## 정적 vs 동적 계획

### 정적(Plan-and-Solve)
에이전트가 10단계 계획을 쓰고 엄격히 따름.
- **장점**: 고성능, 병렬화 쉬움.
- **단점**: 취약. 2단계 실패 시 3-10단계가 쓸모없음.

### 동적(적응형)
에이전트가 계획을 쓰나 매 도구 호출 후 **재평가**.
- **베스트 프랙티스**: **체크포인트 계획** 사용. 에이전트가 모든 주요 하위 목표 후 진행을 상태 스토어에 "커밋"하도록 강제해 복구와 계획 실패 시 "백트래킹" 허용.

---

## 분해 전 명확화하라

가장 비싼 계획 오류는 잘못된 목표를 분해하는 것이고, 2026 측정은 에이전트가 거의 안 묻는다고 말한다. Sierra hyper-tau-bench(2026-09)에서 개발자 에이전트가 비즈니스 기록·클라이언트 인터뷰에서 요구사항을 복구하고 고객 서비스 에이전트를 지어야 하는데, Claude Code의 Claude Opus 5 단독이 홀드아웃 테스트 23.9% 통과, 같은 급 모델에 깊은 문맥의 엔지니어가 짝지으면 82.2% 도달. 개발자 에이전트가 약 1,700개 가용 뱅킹 파일 중 80개 미만을 열고 클라이언트가 20-25개 요구사항을 쥐었을 때 최대 4개 클라이언트 질문만 함. 한 문장 아키텍처 조언이 텔레콤 점수를 31%→67%로 두 배. OSWorld 2.0 실패 분석이 데스크톱 에이전트에 같은 간극 명명: 누락 정보, 에이전트가 거의 명확화를 안 물어서.

설계 결과:
- **요구사항 도출을 명시적 계획 단계로** 자기 예산과 함께, 모델이 건너뛸 수 있는 게 아니라.
- **답이 계획을 바꾸는 곳에만 물어라.** OpenAI는 Codex의 GPT-6 Astra가 중대 결정에만 집중 질문하고 답에 안 의존하는 작업을 계속한다 기술. 그게 올바른 형태: 설문지가 아니라 분기당 차단 질문.
- **아키텍처 힌트를 넣어라.** 인간이 올바른 형태를 알면 계획 프롬프트의 한 문장이 어떤 에이전트 탐색보다 싸다.

## CoT와 추론 모델

모델의 내부 "사고" 윈도(추론 스케일링)가 **숨은 플래너** 역할.
- 별도 "플래너 LLM" 대신 추론 모델(Claude Opus 5.5, GPT-6 Astra)로 "정신 초안" 생성.
- 이 초안이 오케스트레이터가 실행하는 **과제 DAG(방향 비순환 그래프)**로 번역.
- **노력이 계획 예산.** 같은 모델에서 계획 호출을 높은 노력·실행 단계를 낮은 노력으로, 모델 전환이 아니라. 노력 명시 핀: 기본값이 버전마다 바뀜(Opus 5.5 `medium`, Opus 5 `high`).

## 재귀 과제 분해

거대 과제(예: "풀스택 앱 구축")엔 **서브에이전트 스폰** 사용.
1. **마스터 에이전트**: "프로젝트"를 "프런트엔드"·"백엔드"·"DB"로 분해.
2. **서브에이전트**: 각각 "하위 목표"를 받아 자체 분해 수행.
3. **통합**: 마스터 에이전트가 결과 병합.

**결정적 뉘앙스**: 각 서브에이전트에 토큰 부풀림·환각 방지를 위해 **최소 문맥**(필요한 것만) 제공.

**팬아웃을 프롬프트가 아니라 플랫폼에서 제한하라.** 코디네이터 제품이 이제 서브에이전트를 대규모 스폰(Cursor Projects 베타가 계획이 필요로 하는 만큼 병렬 서브에이전트에 위임)하니 상한이 모델 밖에 살아야: OpenAI Agents API가 `max_concurrent_subagents`(기본 6) 노출, 전체 트리 총 예산은 게이트웨이에.

## 트리 탐색(MCTS)

고위험 결정엔 에이전트 루프 내 **몬테카를로 트리 탐색(MCTS)** 사용.
- 에이전트가 가능한 도구 호출 10개 "시뮬레이션".
- **보상 모델**(또는 별도 LLM 프롬프트)이 각 시뮬레이션 점수.
- 에이전트가 최고 보상 경로 따름.

## 면접 질문

### Q: 과제 분해 중 에이전트의 "무한 재귀"를 어떻게 방지하나?

**좋은 답변:**
**분해 깊이 한계**(보통 3레벨)와 **입도 검사** 구현. 서브에이전트 스폰 전 수퍼바이저 모델에 질문: "이 과제가 단일 도구 호출로 풀 만큼 작나?" 예면 실행, 아니면 분해. API 예산을 고갈시킬 재귀 폭탄(포크 폭탄) 방지를 위해 총 "에이전트 수"를 추적하는 **전역 컨트롤러**도. 관리형 런타임엔 플랫폼 자체 동시성 상한(예: OpenAI Agents API `max_concurrent_subagents`)과 세션 지출 상한(Claude Managed Agents가 `budget_reached`로 일시정지) 설정 — 모델이 말로 넘을 수 있는 한계는 한계가 아니니.

### Q: "계획 수정"이 "계획 생성"보다 흔히 비싼 이유는?

**좋은 답변:**
계획 생성은 "새 시작". 계획 수정은 **문맥 재평가** 필요: 모델이 *이미 한 것*, *이전 단계가 왜 실패했는지*, 이전 성공을 되돌리지 않고 고치는 법을 이해해야. 훨씬 높은 "추론 밀도" 필요. 프로덕션에선 초기 계획보다 **수정** 단계에 더 씀: 더 강한 모델(예: Claude Opus 5.5·GPT-6 Astra), 또는 이제 더 흔히 같은 모델을 높은 노력으로 — 문맥·캐시를 온전히 유지하며 더 많은 사고를 삼.
