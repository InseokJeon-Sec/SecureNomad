# 에이전트 기초

에이전트는 "채팅"을 넘어 "자율 문제 해결"로 가는 LLM 기반 시스템이다. 정의가 단순 ReAct 루프에서 내장 "System 2" 사고를 쓰는 **폐루프 추론 시스템**으로 옮겨갔다: Claude Opus 5.5·Fable 5.1의 노력 다이얼 적응형 사고, GPT-6 Astra의 다섯 추론 노력 레벨(low~max), Gemini 3.8 Flash의 사고 레벨.

## 에이전트 공식

현대 에이전시는 흔히 이렇게 기술된다:
`에이전트 = 추론 모델 + 도구 사용 + 영속 메모리 + 환경 피드백`

**뉘앙스**: 2023년 에이전트는 챗 모델 둘레의 "래퍼"였다. 오늘날 에이전트는 점점 **통합**된다. 프런티어 모델(Claude Opus 5.5, GPT-6 Astra, Gemini 3.8 Flash)은 RL 사후 학습으로 "사고" 과정을 학습하고 도구 호출 사이에 끼워, 에이전트 루프를 더 안정적이고 "스톨"에 덜 취약하게 만든다.

---

## System 1 vs System 2 사고

에이전트 설계엔 올바른 "사고 모드" 선택이 필요하다:

| 모드 | 인지 유형 | 비유 | 현 스택(2026년 10월) |
|------|----------------|---------|---------------|
| **System 1** | 빠르고 직관적·반응적 | 반사 | `low` 사고의 Claude Haiku 4.5/GPT-6 Luna/Gemini 3.8 Flash |
| **System 2** | 느리고 논리적·계획적 | 숙고 | 높은 노력의 Claude Opus 5.5·Fable 5.1/높은 노력 이상의 GPT-6 Astra·GPT-6.1 Sol |

**설계 패턴**: "빠른 UI"·"라우팅"엔 System 1 모델. "결정 게이트"·"복잡 계획"엔 System 2 모델.

**선이 이제 모델 교체가 아니라 다이얼.** 최신 프런티어 모델에선 사고를 완전히 못 끔: Opus 5.5가 비활성 거부, Sonnet 5.5 최저 설정이 `between_tools`, GPT-6 Astra에 `none` 노력 없음. 노력 파라미터로 호출별 깊이 설정, 즉 노력이 에이전트 구성의 일부이고 핀해야. 기본값이 밑에서 움직임: Opus 5.5가 `medium` 기본(Opus 5는 `high`)이라 핀 안 한 마이그레이션이 지연·품질을 조용히 바꿈.

**하네스 기본값도 움직이고 모델 자체를 교체한다.** OpenAI Agents SDK 0.20.0이 `gpt-5.6-luna`를 암시 기본으로, Codex CLI가 9/29 기본을 GPT-6.1 Sol로 전환, Claude Code가 각 출시 며칠 내 기본 Opus·Sonnet을 5.5 모델로. 노력뿐 아니라 모델 ID도 핀하고 모든 SDK·하네스 업그레이드마다 평가 재실행.

## 에이전시 수준

모든 자율 시스템이 "에이전트"는 아니다. **에이전시 수준**으로 분류:

1. **L0: 스크립트 체인**: 고정 순서(예: 표준 LangChain).
2. **L1: 도구 가능**: 모델이 도구를 고르나 계획 안 함.
3. **L2: ReAct 에이전트**: "사고 → 행동 → 관찰" 단순 루프.
4. **L3: 자율 플래너**: 목표를 하위 과제 그래프로 분해.
5. **L4: 앰비언트 에이전트**: 백그라운드 실행, 필요할 때만 개입.

L4가 2026년 9월 제품 범주가 됨: OpenAI dots(9/29 발표)가 자체 클라우드 컴퓨터에 상시 실행되고 유휴 시 읽기 전용 리서치만, Meta Muse가 전용 클라우드 VM에 실행, Microsoft Copilot Autopilot(비공개 프리뷰)이 고객 테넌트 내 자기 신원·메모리·컴퓨터를 가짐. L4 설계 질문이 "과제를 끝낼 수 있나"에서 테넌시·에이전트 신원·승인 정책·과금으로 옮겨감.

## 핵심 구성요소

### 1. 추론 모델(집행관)
에이전트의 CPU. "성공 경로"를 결정.

### 2. 도구(팔다리)
에이전트가 세상에 영향을 주게 하는 인터페이스(API, 브라우저, DB).
> [!Note]
> **Model Context Protocol(MCP)** 이 이제 도구 상호운용의 업계 표준, Anthropic·OpenAI·Google·Microsoft·AWS 채택. 거버넌스가 2025년 12월 Linux Foundation의 Agentic AI Foundation으로 이동; 이 재단은 2026년 8월부터 A2A 에이전트 간 프로토콜도 호스팅.

### 3. 메모리(경험)
- **단기**: 문맥 윈도(KV 캐시).
- **장기**: 벡터 DB, 영속 상태(예: Mem0), 파일 기반 메모리(Letta git 백업 MemFS, Claude 메모리 도구).

---

## 에이전트 라이프사이클

1. **접수**: 사용자 목표 수신.
2. **분해**: 목표를 하위 단계로.
3. **실행**: 도구 호출·결과 처리.
4. **반성**: 관찰이 목표에 가까워지게 했는지 평가.
5. **완료**: 사용자에게 최종 증명 합성.

## 면접 질문

### Q: "추론 모델"(Claude Opus 5.5·GPT-6 Astra)이 표준 LLM보다 에이전시에 나은 이유는?

**좋은 답변:**
표준 LLM(System 1)은 패턴 매칭으로 *바로 다음 토큰*을 예측. 도구 호출 오류를 만나면 실패 인정 대신 흔히 수정을 환각. 추론 모델은 추론 중 **사고 사슬(CoT)**을 쓰고 현 세대는 첫 호출 전뿐 아니라 도구 호출 사이에 생각한다. 에이전트엔 더 높은 **경로 신뢰성**을 뜻함: 모델이 다음 단계 선택 전 실패를 추론하므로 무한 루프나 같은 실패 행동 재시도 가능성이 낮다. 하네스 가드의 대체는 아니다. 추론 모델도 여전히 루프하니 하네스가 무관하게 반복 탐지기·예산 유지([루프 엔지니어링](12-loop-engineering.md) 참고).

### Q: 장기 과제의 "에이전트 드리프트"를 어떻게 방지하나?

**좋은 답변:**
에이전트 드리프트는 하위 단계가 에이전트를 원 목표에서 너무 멀리 데려가 문맥을 잃을 때 발생. 표준 해법은 **목표 앵커링**: "원 목표"를 핀된 시스템 메시지로 포함하고 **보조 관찰 모델**(더 작고 싼 모델)로 모든 에이전트 행동을 원 목표 대비 점수. 점수가 임계 아래로 떨어지면 에이전트가 루트에서 "재계획"하도록 강제.
