# 멀티에이전트 오케스트레이션

복잡한 시스템은 에이전트 하나인 경우가 드물다. 전문 에이전트 팀이다. 오케스트레이션이 "눈먼 매니저"에서 **계층 수퍼바이저**·**동적 스웜**·A2A 같은 상호운용 프로토콜이 가능케 한 **크로스 벤더 에이전트 네트워크**로 성숙했다. Gartner는 2025년 8월, 2026년 말까지 엔터프라이즈 앱의 40%가 과제별 AI 에이전트를 탑재하리라 예측(2025년 5% 미만에서).

## 왜 멀티에이전트?

도구 50개의 단일 에이전트는 **인지 부하**를 겪는다.
1. **전문화**: "코드 에이전트"는 Python 최적화 모델, "검색 에이전트"는 RAG 최적화 모델.
2. **병렬성**: 여러 에이전트가 독립 하위 과제를 동시 작업.
3. **분리된 평가**: "작가 에이전트"를 "연구자 에이전트"와 따로 평가 가능.

---

## 수퍼바이저 패턴(계층)

2026년 가장 흔한 엔터프라이즈 패턴.

- **수퍼바이저**: 사용자 프롬프트를 분해하고 워커에 위임하는 고추론 모델(Claude Opus 5.5·Fable 5.1, GPT-6 Astra·GPT-6.1 Sol).
- **워커**: 일을 수행하는 빠르고 비용 효율적 모델(Claude Sonnet 5.5·Haiku 4.5, GPT-6 Luna, Gemini 3.8 Flash).
- **리뷰어**: 통합 출력을 수퍼바이저 원 계획 대비 검증하는 별도 에이전트.

**아키텍처**: LangGraph가 이 상태 인식 계층 루프 구현의 지배 프레임워크로 남음. Claude Agent SDK·Google ADK·Microsoft Agent Framework 모두 2026년 이 패턴 네이티브 지원.

**지불 전 티어 분할 재점검.** 비싼 수퍼바이저 하 싼 워커를 정당화하던 가격 격차가 좁아짐: Claude Sonnet 5.5·GPT-6 Sol·GPT-6.1 Sol 모두 1M당 $2/$10, Opus 5.5가 $4/$20로 하락, Anthropic 자체(벤더) 에이전트 평가가 Sonnet 5.5를 Opus 5.5의 몇 점 이내로. 워커 티어가 거의 유능하고 2배만 싸면 수퍼바이저 트리의 조정 오버헤드가 절감보다 비쌀 수 있다. 각 모델 세대마다 라우팅 평가 재실행.

**수퍼바이저도 이제 제품.** 코딩 제품·관리형 런타임이 코디네이터를 대신 출시: Cursor Projects 베타(2026-09-10)가 코디네이터 에이전트로 일을 계획하고 필요한 만큼 병렬 서브에이전트에 위임, Cursor는 새 Projects 사용자가 PR을 30% 더 머지한다 보고(벤더, 내부); OpenAI Agents API가 `max_concurrent_subagents`(기본 6)로 팬아웃 제한; Claude Managed Agents가 주 스레드가 턴 중간 상담할 `advisor` 항목을 멀티에이전트 로스터에 추가. 플랫폼 수준 동시성 상한이 수퍼바이저 패턴이 늘 필요하던 예산 통제이니 기본값을 물려받지 말고 의도적으로 설정.

## 스웜(OpenAI 패턴)

2024년 말 OpenAI 실험 Swarm 라이브러리가 대중화하고 OpenAI Agents SDK로 이어진 **스웜**은 "핸드오프"에 집중.

- 한 에이전트가 대화를 다른 에이전트에 "핸드오프".
- **핵심 개념**: `Handoff(TargetAgent)`.
- **이점**: 중앙 "매니저" 병목 없음. 대화가 전문 엔티티 간 자연히 흐름.

---

## 파이프라인 패턴(코드로서의 워크플로)

파이프라인은 단계를 코드에 고정하고 에이전트가 채우게 함: 1단계 수집, 2단계 초안, 3단계 검증, 단계 간 구조화 결과 전달과 명시 체크포인트. 모델이 각 단계를 *어떻게* 할지 결정; 코드가 *어느* 단계가 어떤 순서로 돌지 결정.

중요한 구별은 **제어 흐름 소유자**:

| 접근 | 제어 흐름 소유 | 강점 | 약점 | 출시 예(2026) |
|----------|----------------------|----------|----------|-------------------------|
| **코드로서의 워크플로** | 프로그램 | 결정적·감사 가능·테스트 가능 단계; 고정점 인간 체크포인트 | 과제 형태 변하면 경직 | GitHub Copilot 동적 워크플로(10/1 공개 프리뷰): 순차·병렬 단계, 단계 간 구조화 결과, 서로 검증하는 서브에이전트, 인간 검토 일시정지 |
| **모델 주도 위임** | 코디네이터 모델 | 사전에 형태 모르는 과제에 적응 | 비용 경계·감사 어려움 | GitHub `/fleet`, Cursor Projects |
| **품질 게이트 캐스케이드** | 코드 + 모델 점수 게이트 | 싼 모델 초안; 게이트 실패 시만 에스컬레이션 | 게이트 보정이 결정적 구성요소 | GitHub HydraFusion "cascade" 모드(연구 프리뷰 9/30) |

단계가 알려지고 감사 추적이 중요하면 코드로서의 워크플로; 아니면 모델 주도 위임; 대부분 입력이 쉬우면 어느 쪽 앞에든 캐스케이드.

## 그래프 기반 오케스트레이션(2026 지배 패턴)

2026년 아키텍처 모멘텀이 에이전트 워크플로를 타입 상태의 방향 그래프로 모델링하는 **그래프 기반 오케스트레이션**으로 결정적으로 이동.

### 왜 그래프가 이겼나

- **명시적 제어 흐름**: 노드가 에이전트·함수; 엣지가 조건 분기·루프 포함 전이 정의
- **시각화 가능**: 팀이 워크플로를 다이어그램으로 검사·디버그
- **상태 인식**: 타입 상태 객체가 그래프를 통과해 체크포인팅·재개 가능

### 프레임워크 지원

| 프레임워크 | 그래프 모델 | 핵심 차별점 |
|-----------|-------------|-------------------|
| **LangGraph**(약 42.6k 스타) | 타입 상태 명령형 DAG | 가장 성숙, 가장 넓은 커뮤니티 |
| **Google ADK**(약 21.7k 스타) | A2A 내장 그래프 워크플로(2.x) | 네이티브 Google Cloud 통합; ADK TypeScript 2.0이 Sequential·Parallel·Loop 에이전트를 그래프 위해 폐기 |
| **Microsoft Agent Framework** | 워크플로 그래프(순차·동시·핸드오프) | 통합 .NET+Python, 엔터프라이즈 거버넌스 |
| **Claude Agent SDK** | 수퍼바이저 기반 계층 트리 | 내장 도구(bash, editor), 프로덕션 준비 |

### Paperclip 패턴(대규모 계층 에이전트)

주목할 2026 전개는 **Paperclip**(2026년 3월 출시 3주 내 GitHub 스타 44,900). CEO 에이전트가 최상위 목표를 받아 분해하고 매니저 에이전트에 위임하고 매니저가 워커 에이전트를 스폰·조정하는 계층 모델 사용. 깊이 계층화된 멀티에이전트 트리가 복잡한 실세계 과제를 어떻게 다루는지 보임.

## A2A 통한 크로스 벤더 오케스트레이션

**에이전트 간(A2A) 프로토콜**([도구 사용과 MCP](03-tool-use-and-mcp.md) 참고)이 새 멀티에이전트 패턴을 가능케: **크로스 벤더 오케스트레이션**. A2A 전엔 멀티에이전트 시스템이 모든 에이전트가 같은 프레임워크·런타임 공유를 요구. 이제:

1. **에이전트 발견**: 오케스트레이터가 **Agent Card**(`/.well-known/agent-card.json`에 서빙되는 역량 기술 JSON 메타데이터)로 전문 에이전트 찾음
2. **과제 위임**: 오케스트레이터가 메시지 전송(`SendMessage`, JSON-RPC·gRPC·REST `POST /message:send`), 원격 에이전트가 직접 답할지 과제 열지 결정
3. **비동기 진행**: 원격 에이전트가 상태 업데이트 스트리밍, 오케스트레이터가 다른 에이전트에 병렬 위임 가능
4. **결과 수집**: 최종 아티팩트 반환·오케스트레이터 상태에 통합

**프로덕션 예**: 오케스트레이터(LangGraph)가 컴플라이언스 검사를 전문 에이전트(Google ADK), 재고 조회를 MCP 연결 도구, 계약 생성을 CrewAI 크루에 위임, 모두 각각 A2A·MCP로 통신하는 조달 시스템.

**여러 클라이언트가 한 원격 과제를 조종할 때** 손실 업데이트가 실패 모드. 미출시 A2A v1.1 작업이 클라이언트가 놓친 이벤트를 탐지하고 compare-and-set(`if_generation_match`, 낡은 generation에 HTTP 412 거부)하도록 단조 증가 `Task.generation` 추가. 출시 전엔 조종을 한 소유자로 직렬화. A2A v1.0.1(2026-05-28)이 현 스펙 릴리스; A2A가 2026년 8월 Agentic AI Foundation 합류.

## 멀티에이전트의 2026 프레임워크 지형

모든 주요 AI 랩이 이제 에이전트 프레임워크 출시. 2026년 10월 멀티에이전트 오케스트레이션 지형(스타 수 10/1 기준):

| 프레임워크 | 공급자 | 멀티에이전트 모델 | 상태 |
|-----------|----------|-------------------|--------|
| **LangGraph** | LangChain | 그래프 기반, 가장 유연 | 프로덕션; LangGraph 1.2.12(약 42.6k 스타) |
| **Claude Agent SDK** | Anthropic | 내장 도구 수퍼바이저 트리 | GA(Python+TypeScript) |

| **Microsoft Agent Framework** | Microsoft | 워크플로+그룹 챗, A2A·MCP 상호운용 | 2026-04-02 GA; Python 1.19.0, .NET 1.23.0; AutoGen 유지보수 모드 |

## 상태 관리

멀티에이전트 시스템의 최대 과제는 **공유 블랙보드**.

1. **로컬 상태**: 특정 에이전트만 보이는 문맥.
2. **전역 상태**: 모두에게 보이는 공유 메모리(예: 최종 초안).
3. **쓰기 충돌**: 두 에이전트가 같은 전역 상태를 수정하려 할 때.
   - **베스트 프랙티스**: **트랜잭션 핸드오프** 사용. 에이전트가 락을 "소유"할 때만 전역 상태에 쓸 수 있음. 락이 너무 거칠면 낙관적 동시성: 상태 버전 관리·낡은 버전 쓰기 거부, A2A v1.1이 원격 과제에 적용하는 같은 compare-and-set 아이디어.

## 피어 투 피어(P2P) 토론

고정확도 과제(예: 법률·의료)엔 **에이전트 토론** 사용.
- **에이전트 A**: 답 제안.
- **에이전트 B**: A 답의 결함 찾기 시도.
- **에이전트 A**: B 비평 기반 답 정제.
- **결과**: 단일 에이전트가 낼 수 있는 것보다 높은 품질 결과로 수렴.

**크리틱엔 다른 모델 계열 사용.** 같은 계열 크리틱은 맹점 공유. GitHub HydraFusion "critique" 모드(연구 프리뷰, 2026-09-30)가 이를 내장: 다른 모델 계열 크리틱이 초안을 검토하고 드래퍼가 한 번 수정. 교환을 1회 수정으로 상한하는 게 교훈의 다른 반쪽; 무제한 토론은 두 에이전트의 loopmaxxing.

## 면접 질문

### Q: "수퍼바이저" 멀티에이전트 아키텍처의 주 실패 모드는?

**좋은 답변:**
주 실패 모드는 **분해 실패**. 수퍼바이저가 과제를 논리적으로 비일관적이거나 숨은 의존이 있는 하위 과제로 쪼개면 워커가 *잘못된 질문*에 올바른 답을 낸다. 표준 수정은 **반복 계획**: 수퍼바이저가 실행 시작 전 워커에게서 "하위 과제 실행 가능성 확인"을 받아야. 다른 실패는 **문맥 희석**, 전역 상태가 워커 로그로 너무 부풀어 수퍼바이저가 "큰 그림"을 잃음.

### Q: "체인 시퀀스"와 "멀티에이전트 그래프" 중 어떻게 고르나?

**좋은 답변:**
과제가 선형·결정적(예: 추출 → 번역 → 요약)이면 **체인 시퀀스**. **비선형**이거나 **조건 루프**가 필요하면 **멀티에이전트 그래프**(LangGraph 등). 예로 "번역" 단계가 실패해 더 많은 문맥을 위해 "추출"로 돌아가야 하면 정적 체인은 깨지나 그래프는 이전 노드로 라우팅 백해 자기교정 가능.

### Q: 언제 모든 에이전트를 단일 프레임워크에 두기보다 A2A를 멀티에이전트 오케스트레이션에 쓰나?

**좋은 답변:**
팀이 모든 에이전트를 소유하고 같은 런타임을 공유하고 에이전트 호출 간 저지연이 임계면 단일 프레임워크. **조직·벤더 경계**를 넘을 때 A2A 도입, 예로 오케스트레이터가 다른 팀이 유지하는 컴플라이언스 에이전트에 위임하거나 제3자 전문 에이전트(예: 법률 검토 서비스) 통합. A2A는 HTTP 오버헤드를 더하나 **벤더 중립성**·**독립 확장**·Agent Card 통한 **역량 발견** 제공. 어림 규칙: 같은 팀 같은 프레임워크; 다른 팀·벤더 A2A.

### Q: 언제 멀티에이전트 워크플로를 코드로 정의하고 언제 코디네이터 모델이 위임하게 하나?

**좋은 답변:**
시작 전 일의 형태를 아는지에 달림. 단계가 알려지면(수집·초안·검증·승인) 코드로 작성: 고정 순서, 구조화 결과 전달, 인간 체크포인트에서 멈춤 — 비용 경계·모든 실행 감사 가능. GitHub 동적 워크플로가 이 패턴의 제품. 과제 형태가 해봐야만 발견되면(대형 리팩터, 개방형 리서치) 코디네이터 모델이 위임(Cursor Projects·GitHub `/fleet`), 밖에서 경계: 서브에이전트 동시성 상한, 팬아웃 총 예산, 코디네이터가 아닌 검증기. 실무상 혼합: "일 수행" 단계가 모델 주도 코디네이터인 코드 정의 외부 파이프라인 — 적응성은 값하는 곳, 결정성은 나머지 전부.
