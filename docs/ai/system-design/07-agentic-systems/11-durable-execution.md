# 장기 에이전트의 내구 실행

에이전트 실행은 요청/응답 핸들러가 아니다. 도구를 호출하고 문서를 읽고 행동을 트리거하고 승인을 기다리며, 분·시간·일 돌 수 있는 단계에 걸쳐 상태를 나른다. 그것이 평범한 인프라와 충돌한다: 프로세스가 종료되고 노드가 재활용되고 배포가 파드를 롤. 메모리에 상태를 쥔 나이브 에이전트 루프는 그중 어느 이벤트에도 전부 잃고, 나이브 재시도는 부작용을 재실행한다. **내구 실행**은 장기 에이전트가 그 모두를 살아남게 하는 규율이다. 이 장은 모델·도구·에이전트 루프 매핑·복잡성 값어치를 다룬다.

## 에이전트가 정상 실패 모델을 깨는 이유

에이전트는 장기·상태 저장·부작용 프로세스라 세 가정을 깬다:

- **정확히 한 번 부작용.** 도구 호출이 성공하나 에이전트가 기록 전 크래시하면 재개 실행이 호출을 재시도할 수 있어 중복 결제·티켓·배포. 핵심 모호성은 활동 중간 크래시 후 부작용이 커밋됐는지 승인만 잃었는지 알 수 없어 나이브 재시도가 두 번 보낸다는 것.
- **재시작을 버티는 휴먼 인 더 루프 일시정지.** 에이전트가 진행 손실·컴퓨트 소모 없이 수 시간·하루 승인에 블록해야 할 수 있음. 프로세스 메모리의 일시정지는 다음 배포에 죽음.
- **기록된 비결정성.** LLM 호출을 리플레이하고 같은 이벤트인 척할 수 없음; 같은 프롬프트가 다른 응답. 출력을 처음에 기록하고 복구 중 재사용해야.

나이브 재시도는 부작용 재실행; 단계 사이에만 상태 저장하는 나이브 체크포인트도 부작용 실행과 결과 기록 사이 안전치 않은 윈도를 남김. 가르칠 구별: **체크포인트는 상태를 포착하나 내구 실행은 단계의 저널을 포착**, 상태 스냅샷만으로 부작용 중간에서 안전히 재개 불가.

## 내구 실행 모델

핵심 패턴은 **코드로서의 워크플로 + 추가 전용 이벤트 히스토리 + 결정적 리플레이**. Temporal 같은 시스템이 각 워크플로에 불변 이벤트 히스토리 기록; 워커가 10단계 중 5에서 크래시하면 다른 워커가 히스토리를 리플레이해 인메모리 상태 재구성·6단계 재개.

결정성 제약이 어디서 오는지가 하중 지지 개념: 복구가 *리플레이로* 작동하니, 리플레이 중 실행 단계가 로그 단계와 맞아야 시스템이 복구를 보장. 즉 **워크플로 코드 자체가 결정적이어야**: 현재 시간 직접 호출 없음, 난수·UUID 없음, 직접 네트워크 호출 없음, 워크플로 코드 내 비결정적 스레드 인터리빙 없음. 비결정성·부작용은 결과를 한 번 기록하고 이후 로그에서 리플레이하는 **활동**(단계)으로 밀어냄.

구성 블록:
- **활동**은 부작용·비결정성이 사는 유일한 곳; 각각 독립 재시도.
- **정확히 한 번 활동**은 흔히 워크플로·단계 ID에서 파생한 멱등 키 사용해 재시도 도구 호출이 이중 실행 안 함.
- **내구 타이머**는 영속돼 워커 재시작·배포를 버팀, 워크플로가 프로세스를 안 열고 며칠 대기 가능.
- **시그널**이 외부 이벤트(승인, 취소)를 실행 중 워크플로에 밀어넣음; 짝 **쿼리**가 변경 없이 현 상태 읽음(상태, 모니터링). 워크플로가 시그널·타이머를 기다리는 동안 워커가 유휴·컴퓨트 0 소비, 이벤트 도착 시 히스토리 리플레이·재개.

리플레이 기반 결정성의 비용은 **버전 관리**: 장기 워크플로가 옛 히스토리를 리플레이하므로, 워크플로 코드 변경이 신중히 버전 관리 안 하면 리플레이를 깨고 사고 유발 가능. 가장 많이 인용되는 운영 위험.

## 도구

| 도구 | 상태 위치 | 풋프린트 | 비고 |
|------|-------------------|-----------|-------|
| **Temporal**(참조) | 별도 클러스터(또는 Temporal Cloud) | 높음 | 이벤트 히스토리 + 결정적 리플레이; 다언어; 대규모 검증; 가장 깊은 에이전트 프레임워크 통합. |
| **Restate** | 경량 엔진, 사이드카·임베디드 | 낮음 | 각 단계 저널; Virtual Objects(자동 동시성 제어의 사용자/세션 키 상태 세션) 추가. |
| **DBOS** | Postgres 행 | 최저 | 임포트하는 라이브러리; 워크플로 상태·트랜잭션 부작용이 DB 단계 정확히 한 번에 한 Postgres 트랜잭션 공유 가능; 별도 클러스터 없음. |
| **Inngest** | 관리형, 이벤트 주도 | 낮음 | AI 특화 프리미티브의 독립 재시도 단계, LLM 레이트 리밋용 내장 동시성·스로틀. |
| **AWS Step Functions** | AWS 관리형 | 관리형 | 선언적 상태 기계 워크플로(일반 코드 아님); 최근 에이전트 런타임 통합 추가. |

접근들이 내구성 경계를 어디 두느냐로 다름. Temporal은 운영 오버헤드를 규모와 교환; DBOS는 내구성을 기존 DB에 접음; Restate는 내구 세션의 HTTP/gRPC 네이티브; Inngest는 이벤트 주도 TS 우선; Step Functions는 AWS 네이티브이나 일반 목적 코드가 아닌 선언적.

## 내구 실행을 에이전트 루프에 매핑

핵심 매핑: **에이전트 루프가 워크플로가 되고 각 모델 호출·도구 호출이 내구 활동이 됨.** 크래시 시 완료된 모델 호출·도구 호출이 재실행이 아니라 로그에서 리플레이돼, 토큰 재지불·부작용 재발화 안 하고 버그를 고쳐 실행 중 앱을 재개할 수도.

2026 통합 지형:
- **Temporal + OpenAI Agents SDK**가 2026년 초 GA, 각 에이전트 호출·도구 호출을 내구 활동으로 래핑.
- **Temporal + Google ADK**는 실험적, LLM 호출을 활동으로 재라우팅, 최소 코드 변경이 주목(래퍼가 워크플로 안에서 도는지 감지·아니면 직접 실행 폴백).
- **LangGraph**가 각 슈퍼스텝 그래프 상태를 영속 스토리지에 저장하는 **체크포인터**로 더 가벼운 프레임워크 네이티브 내구성 제공, 선택 가능 내구 모드(종료 시·비동기·각 단계 전 동기 체크포인트). 지침이 결정성 규칙을 반영: 워크플로를 결정적·멱등으로 유지하고 부작용을 task로 래핑.
- **DBOS·Restate**가 라이브러리 수준에서 에이전트 프레임워크와 통합, 에이전트 실행·서브에이전트 호출을 내구 워크플로·자식 워크플로로 래핑.
- **Temporal + Amazon Bedrock AgentCore Runtime**가 2026-09-21 프리릴리스: Temporal 워크플로가 내구 에이전트 루프 실행, 모델·도구 호출이 재시도 정책 활동, Strands Agents가 프로그래밍 모델 공급, AgentCore Runtime이 Temporal Serverless Workers 뒤 컴퓨트.

가르칠 솔직한 긴장: **프레임워크 네이티브 체크포인팅은 *상태*를 복구하나, 완전 내구 실행 엔진은 추가로 정확히 한 번 부작용·내구 타이머·시그널·배포 간 리플레이 시맨틱을 준다.** 간극이 도구 호출에 되돌릴 수 없는 외부 효과가 있을 때 가장 중요. 대부분 LLM 추론 + 복구 가능·멱등 도구인 에이전트엔 프레임워크 체크포인팅 + 비멱등 도구 소수의 멱등 키로 충분한 경우가 많다.

이를 엮는 정규 패턴: 제안 행동이 위험하면 워크플로가 시그널 통해 인간 승인을 일시정지·대기, 대기 중 컴퓨트 0 소비, 그다음 내구 재개 — 바로 [휴먼 인 더 루프](08-human-in-the-loop-patterns.md) 승인 게이트를 크래시 방지로.

## 관리형 에이전트 런타임: 내구 루프 빌리기

2026년 9월 기준 Anthropic·OpenAI 모두 에이전트 하네스 자체를 내구 세션 내장 관리형 런타임으로 판매(OpenAI Agents API가 9/10 Claude Managed Agents에 합류), AWS가 OpenAI 것을 자기 클라우드에 제공. "프레임워크 체크포인팅"·"내구 실행 엔진 운영" 옆 셋째 옵션 추가: 루프 빌리기.

| 플랫폼 | 상태(2026-10-01) | 내구성·통제 기능 | 확인할 제약 |
|----------|--------------------------|---------------------------------|----------------------|
| **Claude Managed Agents** | 출시 | 내구 세션; `budget_reached`로 일시정지 하드 세션 예산(8/7); cron 스케줄 배포(6/9부터); 커밋된 `claude-lock.json`의 코드로서 에이전트(ant CLI 1.30.0, 9/3); 서버 평가 자동 권한 정책·라이브 터미널 연결(9/10) | 토큰 + 실행 세션시간당 $0.08 과금(유휴 무료); Batch 할인 없음 |
| **OpenAI Agents API** | 공개 베타(9/10) | 관리형 Codex 하네스: 내구 세션, 문맥 컴팩션, 복구, 서브에이전트 위임, HTTP MCP 서버, 실행 중 조종; OpenAI 호스팅·자체 호스팅 샌드박스; 호스팅 브라우저 컴퓨터 사용(9/29) | 미국 데이터 레지던시만·출시 시 ZDR 없음; 모델·도구·컨테이너 요율 과금(샌드박스 20분 세션당 $0.03-0.48) |
| **Amazon Bedrock Managed Agents**(OpenAI 기반) | 프리뷰(9/29) | AWS 내 커스텀 OpenAI Agents API: 에이전트별 IAM 역할, CloudTrail 로깅, 내구 세션, 중대 행동 전 인간 승인 | us-east-1·us-east-2·us-west-2만; 프리뷰 중 추가 요금 없음 |
| **AWS AgentCore Runtime V2** | 9/18 발표 | 초기화된 에이전트 스냅샷에서 각 인스턴스 복원; P75 콜드 스타트 약 2초(원 런타임 약 5.4-30초, AWS 보고) | `platformVersion` V2 옵트인; 훨씬 적은 GB시에 높은 요율 |
| **Microsoft Foundry Agent Service** | Routines GA(9/24) | 발행 에이전트의 반복·일회 타이머·이벤트 기반 트리거 | 네트워크 이그레스 통제 여전히 프리뷰 |

빌리기가 사는 것: 클러스터 운영 없이 크래시 복구·컴팩션·트리거·예산·승인. 안 사는 것: **자기 부작용 도구의 정확히 한 번 시맨틱**. 관리형 런타임이 세션을 재개할 수 있으나 결제 API가 크래시 전 커밋됐는지 모르니, 비멱등 도구는 여전히 멱등 키가, 다단계 부작용엔 도구 뒤 자기 내구 워크플로가 필요. 다른 비용은 하네스 계층 종속(코드로서 에이전트 파일·세션 시맨틱·이벤트 포맷이 벤더 특화)과 레지던시·보존 간극, 기술 비교 전 규제 데이터에 플랫폼을 배제할 수 있음. OpenAI 하네스를 AWS 내에서 돌리는 Bedrock Managed Agents가 모델 엔드포인트가 아니라 하네스가 통합 단위가 되고 있다는 가장 명확한 신호.

## 언제 필요한가

내구 실행은 *프로덕션* 에이전트 신뢰성의 부상하는 답이고 2026 견인이 실제: Temporal이 이전 Series D 후 2026-09-14 $12.55B 밸류에 $550M Series E, 8월 청구 가능 액션 1.9조(전년비 350%+ 증가), 유료 고객 4,300+, OpenAI의 Temporal 사용 1년 미만 60배 증가 보고(회사 수치). 널리 인용되는 벤더 케이스 스터디가 경쟁 조건·취약 커스텀 재시도 로직·낡은 상태 버그가 지원에 비싸진 후 **프레임워크 프로토타입에서 내구 실행 엔진으로 마이그레이션**한 딥 리서치 에이전트 기술(벤더 발행이라 방향은 실제, 프레이밍은 그들 것).

그러나 신중한 복잡성 교환이다. 제약(결정성, 버전 위험, 새 테스트·모니터링 모델)이 실제이고, 대부분 읽기 전용·단명·단발 에이전트엔 **프레임워크 네이티브 체크포인팅이나 큐 + 멱등 키로 충분**하고 운영이 훨씬 싸다. DBOS·Restate가 완전 클러스터 대비 진입 비용을 상당히 낮추니, 반론이 운영 오버헤드면 라이브러리+Postgres 접근이 가치 대부분을 얻을 수 있다.

## 내구 실행이 필요한가?

순서대로:

1. **어떤 도구 호출이 되돌릴 수 없는 외부 부작용**(결제·이메일·배포·티켓·시스템 간 쓰기)을 가지나? 아니오: 프레임워크 체크포인팅·재시도/큐로 충분. 예: 계속.
2. **단일 실행이 프로세스·배포 주기를 넘을 수 있거나 재시작 간 인간 승인에 멈춰야 하나?** 아니오: 인메모리 + 완료 시 체크포인트로 충분. 예: 내구 타이머·내구 일시정지 필요.
3. **크래시 시 전체 에이전트 재실행이 수용 불가**한가(비용·중복 효과·수 시간 진행 손실)? 예: 리플레이·정확히 한 번 필요, 내구 실행 정당화.
4. **체급 선택:** 부작용이 대부분 자기 Postgres 쓰기고 한 배포를 원하면 DBOS; 저운영·HTTP 네이티브·상태 세션엔 Restate; 이벤트 주도·TS 우선·AI 네이티브 레이트 리밋 통제엔 Inngest; AWS 올인이고 선언적 상태 기계 OK면 Step Functions; 대규모·복잡 장기 프로세스·가장 깊은 에이전트 프레임워크 통합엔 Temporal; 레지던시·보존·가격이 맞고 루프를 운영보다 빌리고 싶으면 관리형 에이전트 런타임(Claude Managed Agents, OpenAI Agents API, Bedrock Managed Agents); 에이전트가 대부분 복구 가능 도구의 추론이면 프레임워크 네이티브 내구성(LangGraph 체크포인터) + 멱등 키 유지.

단순 CRUD·밀리초 미만 핫 패스·순수 고처리량 스트리밍·데드레터 핸들러 큐로 이미 커버되는 소규모 팀엔 과함.

## 면접 질문

### Q: 부작용 있는 프로덕션 에이전트에 나이브 재시도·체크포인트가 불충분한 이유는?

**좋은 답변:**
에이전트 크래시가 재시도로 안전히 못 푸는 모호성을 만들기 때문. 에이전트가 카드를 청구하는 도구를 호출하고 크래시하면, 상태 스냅샷에서 청구가 크래시 전 커밋됐는지 승인만 잃었는지 알 수 없어 나이브 재시도가 두 번 청구 위험. 단계 사이 상태 저장하는 평이한 체크포인트도 부작용 실행과 일어났다 기록 사이 안전치 않은 윈도를 남김. 내구 실행이 최신 상태만이 아니라 단계 저널을 포착해 이를 닫음: 각 부작용 단계가 멱등 키의 기록된 활동이라 리플레이 시 완료 활동이 재실행 대신 기록된 결과 반환. 부작용에 정확히 한 번을 주고 처음이 아니라 실패한 정확한 지점에서 워크플로 재개.

### Q: 내구 실행이 과한 때와 대신 뭘 쓰나?

**좋은 답변:**
에이전트에 되돌릴 수 없는 부작용이 없고 프로세스·배포 주기 안에 맞을 만큼 짧게 돌고 실패 시 그냥 재실행해도 되면 과함, 예로 멱등 도구의 읽기 전용 리서치·요약 에이전트. 거기선 LangGraph 체크포인터 같은 프레임워크 네이티브 내구성으로 상태 복구 + 비멱등 호출 소수의 멱등 키 + 데드레터 핸들러 재시도 큐. Temporal 같은 완전 엔진의 결정성 제약·버전 위험이 실제 비용이니, 에이전트가 되돌릴 수 없는 효과를 갖거나 재시작 간 인간 승인에 멈춰야 하거나 크래시 재실행이 수용 불가할 만큼 길 때만 떠안음. 운영 오버헤드가 블로커이나 여전히 내구성이 필요하면 기존 Postgres를 쓰는 DBOS 같은 라이브러리 접근이 클러스터 운영 없이 가치 대부분을 얻음.

### Q: 에이전트를 Temporal에 짓나 OpenAI Agents API·Claude Managed Agents 같은 관리형 런타임을 빌리나?

**좋은 답변:**
에이전트 루프를 부작용에서 분리한다. 루프 빌리기는 매력적: 내구 세션·컴팩션·트리거·세션 지출 상한·정책 평가 승인이 클러스터 없이 오고 벤더가 하네스를 모델에 튜닝. 그러나 먼저 셋 확인. 컴플라이언스: OpenAI Agents API가 미국만 레지던시·ZDR 없이 출시, 규제 데이터엔 대화 끝낼 수. 시맨틱: 관리형 런타임이 세션 재개하나 내 결제·티켓 도구에 정확히 한 번을 못 주니, 그것은 여전히 멱등 키나 도구 인터페이스 뒤 자기 내구 워크플로 필요. 종속: 코드로서 에이전트 파일·이벤트 포맷·세션 시맨틱이 벤더 특화라 나중 이전이 재작성이고 모델 선택이 하네스 선택에 결합. 보통 답은 하이브리드: 대부분 추론 + 멱등 도구 에이전트엔 루프 빌리고, 되돌릴 수 없는 다단계 작업(환불, 프로비저닝)은 에이전트에 단일 도구로 노출된 Temporal·DBOS 워크플로에 유지해, 정확히 한 번이어야 하는 부분이 내가 통제하는 곳에 살게.
