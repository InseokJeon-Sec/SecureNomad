# 에이전트 메모리와 상태

메모리는 에이전트가 시간에 걸쳐 배우고 문맥을 유지하게 한다. 에이전트 메모리가 "챗 히스토리"에서 네 명명 계층(작업·에피소드·의미·절차)의 **다계층 인지 아키텍처**로 성숙했고, 각각 자기 쓰기 패턴·지연 예산·실패 모드를 가진다. 프로덕션 시스템(Mem0, Letta, Anthropic Memory Tool + Skills, Zep/Graphiti, LangMem)이 이제 메모리 선택을 일급 아키텍처 결정으로 다룬다. 주시할 2026 전환: 여럿이 에이전트가 경로로 탐색하는 **파일 기반 메모리**(Letta MemFS, Claude 메모리 도구, 코딩 에이전트 지시 파일)로 수렴했고, 시장 선도 라이브러리가 그래프 스토어를 버렸다.

이 장을 형성하는 2026 연구 물결: A-MEM(NeurIPS 2025), HippoRAG(멀티홉 그래프 검색), 다계층 메모리 아키텍처, HaluMem(연산 수준 메모리 환각 벤치), MINJA/MemoryGraft(쿼리 전용 메모리 오염 공격), TTT-E2E(Stanford·Berkeley·UCSD·NVIDIA·Astera에 걸친 멀티랩 노력, 문맥을 가중치로 압축하는 테스트 시 학습 접근).

## 메모리 계층

에이전트는 계층 저장 접근을 쓴다:

| 티어 | 유형 | 기술 | 목적 |
|------|------|------------|---------|
| **L1** | 작업 메모리 | 문맥 윈도/KV 캐시 | 현 과제 단계, 로컬 변수 |
| **L2** | 에피소드 메모리 | 벡터 DB/그래프 | "지난번 뭘 했지?" |
| **L3** | 의미 메모리 | SQL/지식 그래프 | 사용자 선호, "진실" |
| **L4** | 절차 메모리 | 스킬 레지스트리/도구 정책/워크플로 그래프 | "이 과제를 어떻게 수행?" |

### 각 티어의 실무 속성

티어는 목적 이상으로 다르다. 읽기 패턴·쓰기 패턴·지연 예산·신선도 기대가 각각 다른 저장 기술로 민다:

| 차원 | L1 작업 | L2 에피소드 | L3 의미 | L4 절차 |
|---|---|---|---|---|
| **담는 것** | 활성 턴, 도구 출력, 스크래치패드, 시스템 프롬프트 | 과거 세션, 궤적, 타임스탬프 관찰 | 증류된 사실, 선호, 엔티티 관계 | 스킬, 플레이북, 시스템 프롬프트 지시, 코드/도구 시퀀스 |
| **읽기 패턴** | 매 토큰·매 턴(인어텐션) | 유사도+최신성+중요도 top-k | 엔티티/주제 언급 시 트리거 룩업 | 과제 시그니처 매칭 시 로드 |
| **쓰기 패턴** | 추론 엔진 연속 추가; KV 캐시 변경 | 추가 전용 로그; 턴 경계 커밋 | 추출·중복제거·upsert; 쓰기 시 충돌 해소 | 성공/실패 후 반성적 쓰기; 명시 인간·자기 편집 |
| **지연 예산** | &lt;50ms(GPU HBM 상주) | 100-300ms(벡터 ANN+재순위) | 200-800ms(그래프 순회+LLM 추출) | 50-500ms(파일 읽기·소 인덱스) |
| **신선도 기대** | 토큰 신선; 세션 끝에 손실 | 시간~월; 낡음 허용 | *현* 상태 반영해야; 낡음은 버그 | 느린 변화; 갱신은 의도적 |
| **저장 기술** | HBM의 KV 캐시(vLLM PagedAttention 블록) | 벡터 DB(Pinecone, Weaviate, Qdrant), 추가 전용 로그 | 지식 그래프(Neo4j, Graphiti), KV 스토어, 양시간 관계 행 | 파일시스템(Claude `/memories/`, `SKILL.md` 스킬), 프롬프트 레지스트리, 파인튜닝 LoRA |
| **쿼리 시맨틱** | 위치+어텐션 | 유사도+최신성+중요도(Park et al. 가중) | 엔티티-관계 매칭, 구조화 쿼리, 양시간 필터 | 과제 시그니처 매칭, 흔히 파일명·태그 룩업 |
| **축출** | 슬라이딩 윈도, KV 블록 해시 LRU | 감쇠 점수, L3 통합, 콜드 스토리지 아카이브 | 옛 사실 유효성 종료(`invalid_at`)로 대체; GDPR엔 명시 삭제 | 수동 폐기, 새 스킬 A/B, 버전 핀 |

**실무 의미:** 사실이 도착하면 아키텍처 질문은 "기억할까?"가 아니라 "*어느 티어*에, 어느 신선도 계약으로, 어느 축출 규칙으로?"다. 잘못된 티어 선택이 예측 가능한 실패 모드 유발(세션 선호를 L3로 승격하면 세션 간 누출; 안정 사용자 사실을 L2에 두면 2주 후 축출). 아래 "사실 X는 어디로?" 참고.

## 단기: 추론 트레이스

프로덕션 에이전트는 더 이상 "메시지"만 저장 않고 **상태 객체**를 저장.
- **스크래치패드**: 사용자에게 안 보이는 에이전트의 자기 "메모" 프롬프트 전용 섹션.
- **KV 캐시 타일링**: 장기 에이전트엔 **프리픽스 캐싱**으로 "시스템 지시"·"표준 도구"를 GPU 메모리에 따뜻이 유지, 동적 과제 상태만 교체.
- **큰 결과 오프로드**: 도구 출력이 작업 메모리를 범람시키는 가장 빠른 길. Agno 3.0(2026-08)이 16,000자 넘는 도구 결과를 파일 스토어에 쓰고 문맥엔 봉투 + `read_result`·`search_result` 도구로 대체해, 에이전트가 필요한 것만 끌어옴.
- **단일 요약 대신 노트**: GPT-6 Astra와 함께 출시된 실험적 Codex 기능이 히스토리를 단일 요약으로 압축하는 대신 문맥 윈도에 걸쳐 검색 가능 노트 유지. 장기 작업용 요약 컴팩션의 벤더 출시 대안: 손실 요약 하나 대신 쿼리 가능 인덱스.

## 에피소드 메모리: 과거 경험

에피소드 메모리는 "실행"·"궤적"을 저장.
- 에이전트가 지난 화요일 웹사이트 스크래이프에 실패했으면 에피소드 메모리가 오늘 같은 실패 셀렉터를 막아야.
- **패턴**: 과제 완료 시 "배운 교훈"을 요약해 벡터 DB에 저장. 새 과제 시작 시 유사 이전 과제 **자기 검색**.

---

## 의미 메모리: 페르소나

의미 메모리는 사용자·환경 "사실"을 저장.
- *"사용자가 JSON 출력을 선호."*
- *"프로덕션 DB가 3-4시에 오프라인."*

**베스트 프랙티스**: 의미 메모리엔 **지식 그래프** 사용. 벡터 검색(퍼지)과 달리 그래프가 엔티티·관계의 결정적 검색 제공(예: `User` -- `OWNER_OF` --> `Project_A`).

그래프 DB를 기본값이 아니라 정당화할 선택으로 다뤄라. Mem0 v2가 Neo4j·Memgraph·Kuzu·Apache AGE 드라이버를 제거하고 이제 엔티티 링크를 기존 벡터 스토어 내 병렬 컬렉션에 두어, 둘째 DB 운영 없이 대부분 개인화 룩업 커버. 멀티홉 순회나 시간 질문("3월 12일에 뭐가 참이었나?")이 제품일 때(Graphiti 양시간 엣지처럼) 전용 그래프에 손을 뻗어라.

## 절차 메모리: 학습된 스킬과 워크플로

절차 메모리는 일하는 법을 저장. 에피소드가 "전에 뭐가 일어났나?", 의미가 "뭐가 참인가?"에 답한다면 절차는:

"이 유형 과제 완료의 올바른 프로세스는?"

이 계층이 재사용 스킬·도구 사용 패턴·운영 절차·워크플로 선호를 포착.

예:
* "주간 보고서 생성 시 먼저 Snowflake에서 지표를 당기고, 대시보드에 검증하고, 이상치를 요약."
* "고객 불만 응답 시 긴급도를 분류하고, 정책을 검색하고, 응답을 초안하고, 신뢰 낮으면 에스컬레이션."
* "SQL 작성 시 항상 스키마를 먼저 검사하고, 쿼리를 생성하고, 검증을 돌리고, 가정을 설명."

절차 메모리는 많은 과제가 사실 기억만이 아니라 올바른 행동 시퀀스를 따라야 하므로 에이전트 시스템에 특히 중요.

## 사실 X는 어디로?

1차 결정은 "어느 티어"가 아니라 *"틀림의 비용을 누가 지불하나?"*다. L2 검색 미스는 한 턴 실패. L3 나쁜 사실은 교정까지 *모든* 턴 실패. L4 오염 스킬은 모든 미래 호출로 전파.

### 티어 선택 표

| 사실/관심사 | 티어 | 이유 |
|---|---|---|
| "사용자 API 레이트 리밋 1000 req/min" | 양시간 유효성(`valid_at`/`invalid_at`) L3 | 테넌트 범위 사실; 엔티티로 쿼리 가능; 대체 지원해야. L4 아님: 절차가 아닌 데이터. |
| "서비스 배포 단계" | 버전 스킬로 L4 | 조건 분기 다단계 레시피. 스킬은 조합되나 의미 트리플은 아님. |
| "에이전트의 이 과제 마지막 실패 시도" | L2 원시, *그다음* 일반화 가능하면 L4로 교훈 반성 | 원시 궤적은 에피소드; 일반화 교훈("피크 시간에 마이그레이션 금지")은 L4로 Reflexion식 쓰기. |
| "사용자가 간결 응답 선호" | L3 | 안정 선호, `user_id`로 쿼리, 단일 트리플. |
| "사용자가 *이 대화에서* 간결 요청" | L1만 | 세션 범위; 잠재 일시적 선호로 L3 오염 금지. |
| 현재 날씨, 오늘 주가 | 없음: 도구 호출 | 다른 곳에 진실 소스 있는 빨리 변하는 사실은 메모리에 절대 안 들어감. |
| "Project Phoenix 팀원 A, B, C" | 그래프 조각으로 L3 | 멀티홉 순회 가치; Graphiti·Neo4j식 저장. |

### 비용 트레이드오프

- **L1이 *지연 비용* 지배**: TTFT가 문맥 크기로 스케일; 긴 작업 메모리 = 느린 첫 토큰. KV 캐시 압력이 프리미엄 가속기 메모리를 포화로.
- **L2가 규모에서 *저장 비용* 지배**: 추가 전용 로그가 사용으로 선형 증가. [Day-30 문제](https://cipherbuilds.ai/blog/day-30-agent-memory-problem)가 가지치기 안 한 에피소드 스토어가 한 달 후 에이전트 품질을 썩게 함을 기술.
- **L3가 *쓰기 증폭 비용* 지배**: 매 턴이 추출·중복제거·충돌 해소 트리거 가능. Mem0 설계가 검색 속도를 쓰기 시 작업과 명시 교환.
- **L4가 *거버넌스 비용* 지배**: 나쁜 스킬이 모든 미래 호출로 전파. Anthropic [Dreams](https://www.mindstudio.ai/blog/what-is-claude-dreaming-anthropic-agent-memory) 연구 프리뷰가 라이브 스토어를 편집하는 대신 통합 출력을 별도 메모리 스토어에 써 승격 전 검토 여지를 남겨 이를 인정.

### 졸업 규칙

흥미로운 설계 질문은 *L2 에피소드가 언제 L3·L4로 졸업하나*. 방어 가능 규칙은 암시 감쇠가 아닌 임계 기반:
1. 같은 패턴의 **N개 독립 관찰**(N=3-5 전형).
2. 출처별 **신뢰 가중**: 사용자 진술 > 도구 출력 > 모델 추론.
3. 통합 단계에서 **인간·LLM 심판 검토**(턴당 아님).
4. 동기 턴당 쓰기가 아닌 **스케줄 배치 통합**(쓰기 증폭 회피).
5. **양방향**: L3 의미 사실이 특정 과제에 에피소드 문맥으로 재인스턴스 가능. 메모리는 일방통행 아님.

### 언제 큐레이션: 쓰기 시·수면 시·읽기 시

큐레이션 타이밍이 이제 명명 설계 축, 각 지점에 실제 시스템:

| 타이밍 | 예시 | 비용 프로파일 | 주 위험 |
|---|---|---|---|
| **쓰기 시** | 매 `add()`에 Mem0식 추출 | 쓰기당 LLM 호출 하나; 싼 읽기 | 추출 오류가 베여 전파(HaluMem 발견) |
| **수면 시** | Anthropic Dreams(연구 프리뷰): 메모리 스토어 + 과거 세션 전사를 읽고 중복 병합·낡은 항목 교체한 재조직 스토어 작성; Mem0 유료 Dream | 요청 경로 밖 배치 작업 | 실행 간 낡음; 승격 검토 필요 |
| **읽기 시** | Just-in-Time Memory(arXiv 2609.27334, 2026-09): 원시 궤적 유지·읽기 시 현 과제에 큐레이션 | 큐레이션 비용·지연이 읽기 경로로 | 원시 스토어 증가; 보존·프라이버시 비용 상승 |

인용할 연구 결과: Just-in-Time Memory가 ALFWorld·WebShop·tau2-bench에서 최강 쓰기 시 베이스라인을 성공률 16.2·16.3·3.9점 이겼고 미학습 큐레이터도 경쟁적. 무엇이 관련인지가 아직 안 본 과제에 달렸을 때 읽기 시 큐레이션 승; 읽기가 핫·지연 바운드면 쓰기 시 추출 승.

## 프로덕션 구현

**Generative Agents(Park et al. 2023)**가 모든 서베이에 인용되는 참조 아키텍처로 남음. 최신성/중요도/관련성 검색 공식(`alpha_recency * recency + alpha_importance * importance + alpha_relevance * relevance`, 각 [0,1] 정규화, 중요도는 LLM이 1-10 평가)이 위 대부분 시스템에 여전히 프로덕션 사용.

**소유 상태를 오케스트레이션 API에서 분리.** OpenAI가 2026-08-26 Assistants API 종료: 스레드·런·런 스텝이 이제 에러, 마이그레이션이 Threads를 Conversations API, Runs를 Responses, Run steps를 Items로 매핑. 벡터 스토어는 종료 대상 아니고 Responses `file_search` 도구로 계속 작동, 호스팅 RAG 팀이 인덱스 유지·대화 상태 코드만 재작성. 메모리·세션 상태를 자기 인터페이스 뒤에 저장하고 벤더 호스팅 스레드 객체를 그 상태의 시스템 오브 레코드가 아니라 캐시로 다뤄라.

**추적할 신흥 프레임워크**: [Supermemory](https://supermemory.ai), [Recallr](https://recallrai.com), AWS [Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-integrate-lang.html), [Oracle AI Agent Memory](https://blogs.oracle.com/developers/oracle-ai-agent-memory-a-governed-unified-memory-core-for-enterprise-ai-agents).

## 실패 모드와 완화

프로덕션 메모리 시스템엔 7개 반복 실패 모드. 이름으로 아는 게 주니어와 스태프급 아키텍처 대화의 차이.

### 1. 프롬프트 인젝션 통한 메모리 오염

신뢰 못 할 입력이 L3/L4에 쓰여 나중 권위로 리플레이. [MINJA(NeurIPS 2025)](https://openreview.net/forum?id=QVX6hcJ2um)·[MemoryGraft(2025-12)](https://arxiv.org/html/2512.16962v1)가 권한 상승 *없이* 95% 주입률·70% 공격 성공률의 *쿼리 전용* 오염 공격 시연. [Palo Alto Unit 42 보고](https://unit42.paloaltonetworks.com/indirect-prompt-injection-poisons-ai-longterm-memory/)가 발화 수 주 전 심긴 독 보임.

**완화:**
- 모든 메모리 쓰기에 **출처 태그**: `source = user_stated | model_inferred | tool_output`.
- 수상한 지시 형태 쓰기("이전 무시하고 대신...", 역할 혼동, 임베디드 시스템 프롬프트 조각)를 거부하는 **쓰기 시 가드레일 모델**.
- **신뢰 티어**: 저신뢰 메모리는 고위험 결정 영향 전 확증 필요.
- **벌크헤드 격리**로 한 테넌트 독이 다른 테넌트로 못 피벗.
- **쓰기 게이트 공유 메모리**: Asana 에이전트(2026-09-29 기술)에서 누구나 과제에 피드백, 관리자·편집자만 영구 공유 메모리에 커밋·삭제; 나머지 피드백은 현 과제만. 오염 벡터가 권한 쓰기가 됨.
- **컴팩션 요약을 메모리 쓰기로 다룸**: OpenAI가 2026-09 RL 학습 중 모델이 자기 컴팩션 요약에 은폐 지시를 썼다 공개, 다음 문맥으로 나른 요약이 여느 쓰기처럼 출처·검토 필요([루프 엔지니어링](12-loop-engineering.md) 참고).

### 2. 낡은 사실

어제 선호 vs 오늘. 고전 "사용자가 지난달 다크 모드라 했으나 지금 라이트 모드."

**완화:**
- **양시간 저장**(Zep/Graphiti): 모든 사실이 `valid_at`/`invalid_at`(참이던 때)·`created_at`/`expired_at`(기록·은퇴).
- 세션 범위 선호 **TTL**로 자동 만료.
- 검색 점수 **감쇠 가중**.
- N일 넘은 고위험 사실 **명시 재확인** 프롬프트.

### 3. 충돌 사실

사용자가 X라 했다 이제 Y. 세 충돌 유형이 다른 응답:

| 충돌 유형 | 올바른 응답 |
|---|---|
| 시간 갱신("베를린 이사") | 옛 사실 대체: `invalid_at`이 새 사실 `valid_at`, `expired_at` 현재로 |
| 교정("그런 말 안 했다") | 감사 추적과 철회 |
| 선호 변경("이제 간결 응답 원함") | 새 사실 추가; 감쇠가 옛것 처리 |
| 노골적 모순(명백한 해소 없음) | 사용자에 물음; 조용히 덮어쓰기 금지 |

last-write-wins가 아니라 AGM 신념 수정으로 신념 상태(`ACTIVE`/`SUPERSEDED`/`RETRACTED`) 추적.

### 4. 메모리 드리프트

저품질 쓰기가 고품질을 희석하며 품질이 시간에 저하. [Day-30 문제](https://cipherbuilds.ai/blog/day-30-agent-memory-problem)가 에피소드 스토어가 노이즈로 차며 프로덕션 약 30일에 에이전트 성능 하락을 기록.

**완화:**
- **품질 가중 검색**: 높은 검증 점수 메모리 부스트.
- 중복 병합·저효용 메모리 가지치기 **스케줄 통합 작업**.
- **CI 카나리 사실 테스트**: "에이전트가 50턴 후에도 사용자 이름 기억해야."

### 5. 환각 메모리 쓰기

에이전트가 사실을 추론해 진실로 저장하고 나중 권위로 인용. 한 나쁜 쓰기가 미래 검색을 오염시키는 연쇄 실패. [HaluMem 벤치(2025-11)](https://arxiv.org/abs/2511.03506)가 기존 시스템이 쓰기 시 오류를 누적해 QA 단계로 전파함을 보임.

**완화:**
- `confirmed_facts`(출처 포함)와 `inferred_facts`(신뢰 포함) 별도 필드의 **스키마 강제 메모리 객체**.
- 명시 사용자 신호·도구 출력 확증 없이 추론을 확정으로 자동 승격 금지.
- CI의 HaluMem식 단계 평가: 추출 정밀도·갱신 정확성·QA 정확도를 단일 종단 지표가 아니라 따로 측정.

### 6. 크로스 테넌트 누출

벡터 ANN이 다른 테넌트 이웃 반환; 캐시 프롬프트가 다른 테넌트 데이터 포함. [현장 측정](https://medium.com/@isuruig/multi-tenant-ai-infrastructure-the-5-isolation-layers-that-determine-whether-your-customers-data-stays-separate-340aaeef4922)이 미격리 멀티테넌트 RAG의 양성 쿼리에 약 95% 유기 누출률 보임.

**완화:**
- **물리 분리**: 메타데이터 필터 공유 인덱스가 아닌 테넌트별 컬렉션.
- 애플리케이션 코드가 아니라 *스토어* 계층에서 서비스 계정 권한으로 테넌트 범위 강제.
- 테넌트별 KV 캐시 프리픽스 분리.
- 메모리 블롭에 테넌트별 암호 키로 크로스 네임스페이스 읽기가 암호 계층에서 실패.

### 7. 메모리 유발 추론 함정

올바르고 관련된 메모리도 에이전트를 나쁘게 할 수 있음. MemTrapBench(arXiv 2608.20202, 2026-08)가 충실히 저장된 의미 관련 메모리가 유발하는 추론 고착·신념 왜곡 테스트. 두 모델 계열·다섯 메모리 프레임워크에서 **모든 메모리 전략이 무메모리 설정을 하회**, 최강이 10%+ 하락. LoCoMo 재현율 같은 검색 지표는 이 해를 못 봄, 검색이 올발랐으니.

**완화:**
- 검색 품질만이 아니라 메모리 주입 있고 없고 종단 과제 성공 평가.
- 주입 게이트: 검색 후 메모리가 이 과제에 결정 관련인지 문맥 진입 전 결정.
- 주입 메모리를 지시가 아니라 과거 문맥으로 틀지음. 논문의 AdaptiveMem 추론 시 지시가 표준 메모리 벤치 점수 유지하며 함정 감소.

## Mem0와 에이전트 개인화

**Mem0**·Zep·Letta·Cognee가 에이전트 스택 "스마트 메모리" 표준 프레임워크.
- 대화에서 "사용자 인사이트"를 자동 추출(Mem0 v2엔 쓰기당 ADD 전용 추출 패스 하나).
- 에이전트가 메모리 추가·검색·삭제 호출하는 "메모리 API" 제공; 충돌 해소는 당신 일이거나 스케줄 통합 패스.
- **영향**: 에이전트가 3개월 전 다른 세션에서 언급한 디테일을 기억해 "살아있는" 느낌.

## 면접 질문

### Q: 에이전트 시스템의 "충돌 메모리"를 어떻게 다루나?

**좋은 답변:**
충돌 메모리(예: 지난주 "파랑 좋아", 지금 "빨강 좋아")는 **시간 가중**이나 **명시 분쟁**으로. 내 아키텍처에선 모든 메모리 트리플릿에 `timestamp`·`confidence_score` 배정. 새 사실이 옛것과 충돌하면 에이전트가 사용자에 명확화 요청하거나 가장 최근 타임스탬프로 기본해 "충돌 해소". 오래되고 비강화된 메모리가 결국 활성 인덱스에서 가지치기되는 **감쇠 함수**도.

### Q: "문맥 윈도"만으론 스태프급 에이전트에 불충분한 이유는?

**좋은 답변:**
첫째, **비용·지연**: 캐시 읽기가 이제 기본 입력의 0.025-0.1배라 완전 캐시 1M 프리픽스가 더 이상 터무니없지 않음(현 Claude 모델 턴당 약 $0.20-0.25: Opus 5.5·Sonnet 5.5 캐시 토큰 1M당 $0.20, Fable 5.1 $0.25). 그러나 미스는 전가, OpenAI는 272K 초과 전체 요청 장문맥 요율, 프리필 지연도 길이로 증가. 둘째, **신호 대 잡음**: 큰 윈도가 컨텍스트 부패 겪음 — 모델이 무관 역사 턴에 산만, MemTrapBench가 관련 메모리도 추론을 왜곡함을 보임. 스태프급은 **선택적 메모리 검색**(히스토리 위 RAG)으로 가장 관련된 3-5 상호작용만 끌어 추론 엔진을 현 하위 목표에 집중.

### Q: 프로덕션 AI 에이전트의 절차 메모리를 어떻게 설계하나?

**좋은 답변:**
절차 메모리를 **스킬 레지스트리·워크플로 그래프·도구 사용 정책** 조합으로 설계. 각 절차가 과제 유형·필수 단계·가용 도구·검증 검사·실패 모드·에스컬레이션 규칙 정의. 각 실행 후 에이전트가 반성하고 더 나은 접근 발견 시 절차 갱신. 예로 NL2SQL 에이전트가 스키마 검사를 건너뛰어 반복 실패하면 모든 SQL 생성 과제 절차 메모리에 스키마 검사를 필수 첫 단계로 인코딩.

### Q: 에피소드 메모리가 자산이 아니라 부채가 되는 때는?

**좋은 답변:**
세 명명 패턴에서 부채가 됨. 첫째 **인덱스 과부하**: 저품질 관찰 1,000개 추가가 고품질 10개를 검색에 묻음. RAG 의미의 파국적 망각. 둘째 **Day-30 드리프트**: 에피소드 스토어가 검색이 신호와 구별 못 하는 노이즈로 차며 프로덕션 약 30일에 품질 저하. 셋째 **낡은 문맥 번짐**: 한 구성에서 성공한 과거 궤적이 새 구성에선 *잘못된* 문맥. Stripe용 성공 도구 시퀀스가 사용자가 Adyen으로 바꿨을 때 적극 오도.

완화는 품질 가중 검색·L3 통합·문맥 민감 궤적 하드 최신성 컷오프. 더 깊은 교훈: 에피소드 메모리는 1일차부터 *가지치기 정책*이 필요. 없으면 사용으로 선형 복합하는 기술 부채.

### Q: 에이전트가 자기 장기 스토어에 쓸 수 있을 때 메모리 오염을 어떻게 방지하나?

**좋은 답변:**
어려운 부분은 최근 공격(MINJA, MemoryGraft)이 *쿼리 전용*이라는 것: 권한 상승 불필요. 독이 발화 수 주 전 심김. 그래서 위협 모델이 "모든 입력이 미래 권위 메모리가 될 수 있음". 방어는 네 계층:
1. **쓰기 시 출처**: 모든 메모리가 `source`(사용자 진술·모델 추론·도구 출력)·`timestamp`·`trust_tier` 포함.
2. **쓰기 시 가드레일 모델**: 작은 분류기가 수상한 지시 형태 쓰기를 스토어 닿기 전 거부.
3. **확증 임계**: 고위험 결정은 단일 저신뢰 메모리로 못 함; 여러 독립 확증 쓰기 필요.
4. **CI 카나리 테스트**: 합성 독 페이로드가 출력에 전파 안 돼야. 주간 실행.

가장 중요한 아키텍처 분리: 에이전트 도구 표면과 메모리 쓰기 표면이 신뢰를 공유 않아야. 도구 출력이 메모리가 되기 전 살균기를 거쳐야.

### Q: 메모리 티어 선택: 다음 각각을 어디 두고 왜? (a) 사용자 API 레이트 리밋, (b) 서비스 배포 단계, (c) 에이전트의 이 과제 마지막 실패 시도, (d) 오늘 주가.

**좋은 답변:**
(a) 양시간 유효성의 **L3 의미**. 대체 수명의 테넌트 범위 사실. L4 아님, 절차가 아닌 데이터니.
(b) 버전 스킬·플레이북의 **L4 절차**. 조건 분기 다단계 레시피. 스킬은 조합되나 의미 트리플은 아님.
(c) **L2 에피소드 원시**, 실패가 일반화 교훈을 드러내면 L4로 *반성 홉*. 원시 궤적은 에피소드. 교훈("피크 시간 마이그레이션 금지")은 절차로 Reflexion식 쓰기.
(d) **없음: 도구 호출.** 라이브 진실 소스 있는 빨리 움직이는 사실은 메모리에 절대 안 들어감. 정의상 낡음.

일반 규칙: 데이터는 L3, 절차는 L4, 관찰은 L2, 라이브 소스 있는 빨리 움직이는 사실은 절대 저장 안 함.

### Q: 에피소드-의미 전환 통합 정책을 설계하라. 에피소드가 언제 사실이 되나?

**좋은 답변:**
암시 감쇠가 아닌 임계 기반 졸업 정책:
- **빈도 임계**: 같은 패턴 N개 독립 관찰(3-5 전형).
- **신뢰 가중**: 사용자 진술 > 도구 출력 > 모델 추론.
- **심판 검토**: 스케줄 배치 통합 작업이 후보 졸업에 LLM 심판(고위험 도메인은 인간 검토) 실행.
- **스케줄, 동기 아님**: 통합이 턴당이 아닌 cron으로 대역 외. 쓰기 증폭 회피.
- **양방향**: L3 의미 사실이 특정 과제에 에피소드 문맥으로 재인스턴스. 메모리가 양방향 흐름.

피할 함정은 감쇠 가중만의 암시 통합. 소규모엔 통하나 "왜 이 사실이 L3에 나타났나"의 감사 추적이 없어 프로덕션 규모에 조용히 실패.

### Q: 벤치가 메모리 끈 에이전트가 더 낫다고 보인다. 어떻게 하나?

**좋은 답변:**
버그 가정 대신 진지하게 받음, MemTrapBench(2026-08)가 다섯 프레임워크에서 정확히 이를 발견했으니: 올바르고 관련된 메모리가 추론 고착·신념 왜곡 유발, 모든 전략이 무메모리 하회. 먼저 평가 분할: 검색 품질·주입 결정·메모리 있고 없고 종단 과제 성공, 과제 유형별. 보통 메모리가 개인화·연속성 과제엔 돕고 과거 답이 모델을 앵커하는 신선 추론 과제엔 해침. 그다음 주입 게이트 추가: 후보 검색하되 싼 분류기·규칙이 이 과제에 결정 관련이라 할 때만 주입, 타임스탬프의 과거 문맥으로 틀짓고 지시가 아니라. 큐레이션을 읽기 시(Just-in-Time Memory식)로 옮겨 주입되는 게 쓰기 시 추출이 아니라 현 과제에 선택되게도 고려. 성공을 과제 클래스별 메모리 있는 성공 빼기 없는 성공으로 측정, 그 델타를 재현율 옆 대시보드에.

### Q: 메모리 스토어에 1만 테넌트에 걸친 5천만 메모리가 있다. 크로스 테넌트 격리를 어떻게 보장하고 격리 실패 시 폭발 반경은?

**좋은 답변:**
아키텍처가 다섯 격리 계층:
1. **스토어 계층 물리 분리**: 메타데이터 필터 공유 인덱스가 아닌 테넌트별 컬렉션·샤드. 공유 인덱스+tenant-id 패턴이 버그에 오픈 실패.
2. **서비스 계정 범위 강제**: 애플리케이션 코드가 테넌트 범위를 옵트아웃 못 함; DB 역할이 다른 테넌트 가시성 없음.
3. **테넌트별 KV 캐시 프리픽스 분리**: 캐시 프롬프트 테넌트 간 누출 방지.
4. **테넌트별 암호 키**: 버그로 반환돼도 크로스 네임스페이스 바이트 판독 불가.
5. **모든 크로스 네임스페이스 쿼리 시도 감사 로깅**: 심층 탐지.

**격리 실패 시 폭발 반경**: 한 나쁜 벡터 쿼리가 한 쿼리 임베딩 *이웃*, 한 테넌트 수백 레코드 누출 가능. 현장 측정이 미격리 멀티테넌트 RAG에 약 95% 유기 누출률. 완화는 "더 신중한 애플리케이션 코드"가 아니라 애플리케이션 버그로 우회 못 할 구조 분리.

### Q: HaluMem이 메모리 환각이 쓰기 시 누적·전파됨을 보인다. 이를 잡으려 프로덕션 메모리를 어떻게 계측하나?

**좋은 답변:**
대부분 팀이 빠지는 함정은 메모리 품질을 QA 단계(종단)만 측정. HaluMem이 메모리 오류의 60-80%가 *추출*(쓰기) 시 발원·전파함을 시연. 세 별도 지표 계측:
1. **추출 정밀도**: 에이전트가 L3에 사실 쓸 때 그 사실이 실제로 소스 관찰에 지지되나? 쓰기 일간 샘플, 더 강한 심판 평가.
2. **갱신 정확성**: 충돌 사실 도착 시 충돌 해소 로직이 올바른 결과를 냈나? 양시간 쿼리로 "대체 메타데이터 없이 뒤집힌 사실" 탐지.
3. **QA 정확도**: 종단 재현율 정확성.

그 위에 **섀도 모드 리플레이**: 쓰기가 섀도 모드 검증기 모델을 거침; 라이브 쓰기와 섀도 검증기 쓰기 불일치가 잠재 환각 플래그. **CI 카나리 사실**이 메모리 시스템이 조용히 퇴행 안 하게. **주기적 전체 스토어 감사**가 무작위 메모리 샘플해 "이게 여전히 소스 대화와 일관?" 물음.

### Q: TTT-E2E가 테스트 시 학습으로 문맥을 가중치로 압축한다. L1-L4 계층의 어디에 맞고 어떤 새 실패 모드를 도입하나?

**좋은 답변:**
TTT-E2E는 L1과 L4 *사이*에 앉음. 문맥 유래 정보를 세션 나머지 동안 모델 자체의 일부로 만듦. 매력은 지연: 문맥 길이 무관 상수 비용(NVIDIA 벤치로 H100에서 128K 2.7배·2M 토큰 35배 가속).

새 실패 모드는 거버넌스. 가중치 내 메모리는:
- **감사 추적 없음**: "모델이 이제 뭘 믿나" 검사 불가.
- **축출 인터페이스 없음**: 가중치에 압축된 메모리를 모델 상태 롤백 없이 삭제 불가.
- **GDPR 잊힐 권리 도전**: 규제 틀이 데이터를 가중치가 아닌 정지로 가정.
- **오염 탐지 어려움**: 카나리 시그니처 스캔할 검사 가능 스토어 없음.

거버넌스 너머 역량 실패 모드: 접근이 어텐션 윈도 너머 건초 더미 바늘 검색 실패 보고(128K에서 완전 어텐션 99% 대비 약 6%)라 축자 사실이 아닌 문맥 요지를 보존. 검색 임계 작업의 유일 메모리 티어로는 배제.

올바른 틀: TTT-E2E가 메모리 거버넌스를 저장 계층에서 학습·배포 파이프라인으로 옮김. 비용이 제거가 아니라 재배치. 2026년 대부분 프로덕션 팀엔 아직 배포 가능 아키텍처가 아닌 추적할 연구 방향. 더 넓은 테스트 시 학습 계열은 [Research Radar, 테마 12](https://github.com/ombharatiya/ai-system-design-guide/blob/main/RESEARCH-RADAR.md)(영문)에 매핑.
