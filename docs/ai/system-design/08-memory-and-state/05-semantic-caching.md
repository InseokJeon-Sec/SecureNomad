# 의미 캐싱

캐싱이 정확 문자열 매칭에서 **의미 매칭(Semantic Matching)**으로 진화했다. 의미 캐싱은 "동등" 쿼리의 완성을 재사용해 적중 시 지연을 초에서 밀리초로 줄인다. 절감은 전적으로 트래픽이 얼마나 반복적이냐에 달렸다: FAQ 스타일 지원 트래픽은 큰 감소를 보나, 개방형 에이전트 작업은 드물게 반복된다. 또 반복 *입력*을 할인하되 호출을 건너뛰지 않는 제공자 프롬프트 캐싱과 구별된다.

---

## 정확 캐시 vs. 의미 캐시

| 특성 | 정확 캐시(Redis/Memcached) | 의미 캐시(RedisVL/Qdrant) |
|---------|-------------------------------|---------------------------------|
| **키** | 해시된 쿼리 문자열 | 쿼리 임베딩 벡터 |
| **매칭**| 100% 문자열 동일 | 코사인 유사도 > 임계 |
| **효율**| 낮음(사소한 오타가 캐시 깸) | 높음(의도 이해) |
| **위험** | 제로 | 의미 드리프트(틀린 답 반환) |

---

## 의미 캐시 vs. 제공자 프롬프트 캐시

둘은 다른 문제 풀고 잘 쌓임:

| | 의미 캐시(당신) | 제공자 프롬프트 캐시 |
|---|------------------------|-----------------------|
| **재사용되는 것** | 전체 응답 | 반복 입력 프리픽스의 KV 캐시 |
| **절감** | 전체 LLM 호출: 입력·출력·지연 | 입력 비용·프리필 시간만 |
| **할인** | 적중 시 100% | 캐시 읽기 대부분 모델 입력 0.1배, Claude Opus 5.5·GPT-6.1 Sol 0.05배, Claude Fable 5.1 0.025배 |
| **정확성 위험** | 근사 매칭이 틀린 답 반환 가능 | 없음: 모델이 여전히 fresh 답 생성 |
| **적합** | 안정 답의 반복 질문 | 긴 공유 프리픽스: 시스템 프롬프트·도구·문서 |

깊은 프롬프트 캐시 할인이 입력 무거운 워크로드의 의미 캐싱 명분을 줄임: 요청 비용 대부분이 긴 공유 프리픽스면 제공자 캐시가 이미 드리프트 위험 없이 90% 이상 제거. 의미 캐싱은 **출력 토큰이나 지연**이 지배할 때 여전히 승, 응답 캐시만 생성을 완전 건너뛰니.

---

## 의미 매칭 파이프라인

1. **임베드**: 들어오는 쿼리를 벡터로 변환(예: `text-embedding-3-small`).
2. **검색**: 테넌트·권한 범위로 필터해 캐시서 최근접 이웃 검색.
3. **임계 검사**: `distance < 0.05`(매우 유사)면 캐시 결과 반환.
4. **LLM 검증**: 고위험 쿼리엔 작은 "검증기 모델"(예: GPT-6 Luna·Claude Haiku 4.5·Gemini 3.8 Flash)이 캐시 응답이 실제 새 쿼리에 답하는지 검사.
5. **갱신**: 미적중 시 LLM 호출해 새 결과를 벡터 캐시 저장.

**캐시 키가 범위를 포함해야.** 사용자 A의 문서·권한·메모리서 생성된 응답이 질문 아무리 유사해도 사용자 B에게 절대 안 제공돼야. 캐시를 테넌트별(답이 접근에 의존하면 권한 세트별로도) 파티션, 파티션이 사용자별 아니면 개인 데이터 임베드 응답을 절대 캐시 말 것.

## RedisVL와 GPTCache

표준 스택:
- **RedisVL**: Redis 인스턴스 내 직접 저지연 벡터 검색 제공.
- **하이브리드 캐싱**: 메타데이터(키)·벡터 페이로드 둘 다에 Redis 사용.
- **TTL**: 의미 캐시는 TTL(Time-To-Live) 가져야. 흔한 패턴은 **동적 TTL**: 인기 답이 더 오래 살고 "낡은" 정보는 정기 축출.
- **변경 시 무효화**: 캐시를 모델 ID·시스템 프롬프트 버전·소스 데이터 버전으로 버전, 프롬프트 변경·문서 업데이트가 옛것 하 생성 답을 못 제공하게.

## 평가: 적중률 vs. 의미 드리프트

모든 적중이 두 쿼리가 동등하다는 예측이니 캐시를 분류기처럼 측정:

| 지표 | 알려주는 것 |
|--------|-------------------|
| **적중률** | 캐시서 제공된 요청 비율(절감 측) |
| **거짓 적중률** | 캐시 답이 새 쿼리에 틀린 적중 비율, 적중 샘플해 심판·인간 채점으로 측정 |
| **적중·미적중 시 지연** | 미적중이 LLM 호출 위에 임베딩 + 벡터 검색 지불 |
| **낡음** | 바탕 데이터 변경 후 제공된 적중 비율 |

임계를 레이블된 쿼리 쌍 세트(동등·비동등)에 제품이 감내할 거짓 적중률로 튜닝, 그다음 적중률이 떨어지는 대로 둠. 적중률 40%·거짓 적중률 0.1% 캐시가 적중 70%·틀린 답 5%보다 나은 제품.

---

## 멀티모달 의미 캐싱

네이티브 멀티모달 프런티어 모델(Gemini 3.8 Flash·GPT-6.1 Sol·Claude Opus 5.5)로 이제 **이미지·오디오 쿼리** 캐시.
- **시각 유사도**: 의미 유사 이미지가 전에 처리됐으면 이미지 설명 캐시.
- **오디오 핑거프린팅**: 유사 음성 명령 전사 캐시.

## 면접 질문

### Q: 캐싱의 "의미 드리프트"란 뭐고 어떻게 막나?

**좋은 답변:**
의미 드리프트는 유사도 임계가 너무 느슨할 때(예: 0.95 대신 0.8) 발생. *"차를 어떻게 고치나?"* 쿼리가 *"차를 어떻게 씻나?"* 캐시 응답에 매칭 가능. 막으려 **다단계 검증** 사용: 1) 벡터 유사도 검사, 2) **엔티티 매칭 검사**(둘 다 "차"와 같은 "동사" 포함 보장), 3) **임계 강화**: 기술·의료 쿼리엔 캐시 결과 반환에 $>0.98$ 유사도 요구. 적중을 지속 샘플해 채점도 해, 거짓 적중률이 가정이 아니라 추적 지표.

### Q: 왜 의미 캐시가 저볼륨서 때로 원시 LLM 호출보다 *더* 비싼가?

**좋은 답변:**
모든 요청이 적중·미적중 관계없이 캐시 오버헤드 지불하니: 임베딩 호출·벡터 검색. 임베딩 자체는 거의 공짜(`text-embedding-3-small`이 1M 토큰당 $0.02, 50 토큰 쿼리가 약 백만분의 1달러)나, 검색이 지연 추가, 흔히 인프로세스 5-20ms·네트워크 걸치면 더, 플러스 캐시 실행·유지 비용. 낮은 적중률서 대부분 요청이 그 오버헤드 지불하고 여전히 LLM 호출, 그래서 중앙값 지연 나빠지고 절감 작음. 거짓 적중 위험·엔지니어링 비용 더하면, 의미 캐싱은 적중률이 "임베딩 세금" 상쇄할 만큼 높은 반복 트래픽의 **고규모**서만 명확 승.

### Q: 이미 제공자 프롬프트 캐싱 사용. 의미 캐시도 추가해야?

**좋은 답변:**
비용이 어디 있냐에 달림. 프롬프트 캐싱이 반복 입력 프리픽스를 정확성 위험 없이 할인(입력가 0.1배 이하 읽기), 그래서 입력 지배 에이전트 워크로드엔 이미 절감 대부분 포착. 의미 캐시는 호출을 완전 건너뛰니 출력 토큰·지연 지배하고 질문 반복할 때 보상: 지원 FAQ·제품 룩업·문서 답. 트래픽 먼저 확인: 일주일 쿼리 클러스터해 수용 가능 거짓 적중률 튜닝 임계서 적중률 추정, 투영 절감을 드리프트 위험·테넌트별 파티셔닝 작업과 비교. 흔히 답은 좁고 고볼륨 의도엔 의미 캐시, 나머지 전부엔 프롬프트 캐싱.
