# 메모리 아키텍처

LLM 메모리는 "히스토리 버퍼"에서 **3계층 인지 아키텍처(Three-Tiered Cognitive Architecture)**로 진화했다. 이 계층은 인간 인지 시스템(L1-L3)을 모방해 속도·비용·회상 용량을 균형 잡는다. 프로덕션 에이전트 스택은 이제 자체 제작보다 전용 메모리 계층(Mem0·Zep·Letta·Cognee)이나 관리형 에이전트 플랫폼의 메모리 기능에 기댄다, 그리고 2026에 벡터·그래프에 셋째 기질이 합류: **평범한 파일**, git에 버전되고 경로로 탐색. 절차 메모리를 더한 에이전트 중심 4계층 관점은 [에이전트 메모리와 상태](https://github.com/ombharatiya/ai-system-design-guide/blob/main/07-agentic-systems/05-agent-memory-and-state.md)(영문) 참고.

---

## 3계층 위계

| 티어 | 유형 | 인간 비유 | 기술 | 지연 |
|------|------|---------------|------------|---------|
| **L1** | 작업 메모리 | 즉각 초점 | 문맥 윈도 / KV 캐시 | &lt;50ms |
| **L2** | 에피소드 메모리 | 과거 경험 | 벡터 DB / 원시 궤적 로그 | 100-300ms |
| **L3** | 의미 메모리 | 일반 지식 | 사실 스토어(Mem0), 시간 그래프(Zep/Graphiti), SQL, 메모리 파일 | &gt;500ms |

---

## 티어 1: 작업 메모리 (L1)

L1은 모델의 **활성 초점**.
- **문맥 윈도**: 현 프런티어 모델 약 1M 토큰(Claude Opus 5.5·Sonnet 5.5가 1M, GPT-6.1 Sol이 1.05M, Gemini 3.8 Flash가 1,048,576); 오픈 웨이트 모델은 128K-1M.
- **KV 캐시**: 사전 계산 키·값 저장하는 GPU "RAM".
- **관리 전략**: **슬라이딩 윈도**·**컴팩션**·**프리픽스 캐싱**(vLLM/PagedAttention, SGLang RadixAttention).
- **중복 노트**: 가장 최근 턴과 핵심 시스템 지시만 L1에 유지.

---

## 티어 2: 에피소드 메모리 (L2)

L2는 이 세션이나 이 사용자와의 과거 세션서 "전에 뭐가 일어났나"를 저장.
- **저장**: 벡터 데이터베이스(Pinecone·Weaviate·Qdrant), 원시 로그는 오브젝트 스토리지에.
- **검색**: 의미 검색. 사용자가 "지난 화요일 뭘 얘기했지?" 물으면 L2가 답 제공.
- **패턴**: **경험 리플레이(Experience Replay)**. 에이전트가 성공한 과거 궤적을 검색해 현 결정 유도.

---

## 티어 3: 의미 메모리 (L3)

L3는 뭔가 대체할 때까지 유지돼야 할 **내구 사실**과 **학습 규칙** 저장.
- **지식 그래프**: 관계 저장(예: `User` -- `WORKS_FOR` --> `Company_X`), "언제 참이 됐나"가 중요할 때 유효 구간과 함께(Zep/Graphiti).
- **Mem0**: 사실(예: "사용자가 다크 모드 선호") 추출해 세션 간 가용케 하는 오픈소스 라이브러리·관리형 플랫폼. v2.0.0(2026-04)부터 그래프 데이터베이스가 아니라 당신 벡터 스토어에 병렬 엔티티 인덱스로 저장.
- **진실 앵커링**: L1·L2가 충돌 정보 제공 시 L3가 "그라운드 트루스" 역할, 이는 충돌이 어딘가(쓰기 시·스케줄 통합 작업·읽기 시)서 해소돼야만 작동.

---

## 파일 기반 메모리: 경로로 검색

2026의 가장 큰 아키텍처 전환은 임베딩 유사도로 검색되는 행이 아니라 **에이전트가 평범한 도구로 읽고 편집하는 파일**로 저장되는 메모리.

| 시스템 | 작동 방식 |
|--------|--------------|
| **Letta MemFS** | Letta가 2026-08-16 MemGPT 시대 서버 아카이브. 모든 에이전트가 이제 MemFS 사용: 장기 메모리가 YAML 프런트매터 Markdown 파일의 git 저장소. 메모리 루트 파일이 매 턴 시스템 프롬프트 로드; 자기 `MEMORY.md` 인덱스의 디렉터리는 문맥 밖에 표지. 기본 벡터 인덱스 없음. |
| **Claude 메모리 도구·Managed Agents 메모리 스토어** | 모델이 도구로 읽고 쓰는 `/memories` 디렉터리; Managed Agents가 세션당 스토어 마운트, 자체 호스팅 샌드박스가 2026-08-19 메모리 스토어 획득. |
| **코딩 에이전트** | `CLAUDE.md`·`AGENTS.md`·스킬 파일: 인간이 PR서 검토 가능한 프로젝트 메모리. |

**에이전트에 이기는 이유**: 인간이 읽고 diff하고 검토 가능; git이 버전·롤백을 공짜로; 에이전트가 올바른 청크가 최고 점수 나길 바라는 대신 구조(인덱스 파일·디렉터리)로 탐색. **지는 곳**: 크거나 고변동 사실 세트·크로스 유저 집계·수천 에피소드의 퍼지 회상, 여전히 벡터 영역.

---

## 메모리 통합 패턴

메모리는 **통합(Consolidation)**으로 티어 간 이동:
1. **추출**: LLM "검토기"가 세션 끝에 L1서 사실 추출.
2. **인덱싱**: 사실이 L2(벡터로)·L3(사실·그래프 엣지·메모리 파일로) 저장.
3. **감쇠**: 오래되고 비강화된 에피소드 메모리가 콜드 스토리지로 아카이브되거나 삭제; L3 승격 사실은 대체되지 조용히 안 감쇠.

면접관이 이제 탐침하는 설계 축은 통합이 **언제** 도나:

| 타이밍 | 예시 | 트레이드오프 |
|--------|---------|----------|
| **쓰기 시** | Mem0 v2: `add()`당 ADD 전용 추출 호출 하나 | 싼 읽기; 추출 오류가 베임 |
| **수면 시** | Anthropic Dreams(연구 프리뷰), Mem0 Dream(유료 플랜) | 요청 경로 밖; 실행 간 낡음 |
| **읽기 시** | Just-in-Time Memory(arXiv 2609.27334): 원시 궤적 유지, 과제별 큐레이션 | 최강 쓰기 시 베이스라인을 3.9-16.3 성공률점 이김; 큐레이션 비용이 읽기로 이동 |

더 많은 메모리가 자동 더 나음 아님: MemTrapBench(arXiv 2608.20202)의 메모리 함정 유발 과제서 테스트한 모든 메모리 전략이 무메모리 설정 하회, 올바르고 관련된 메모리도 추론 고착 유발하니. 메모리 주입 게이트하고, 메모리 있고 없고 과제 성공 평가.

## 면접 질문

### Q: 모든 메모리(L1-L3)에 그냥 1M 토큰 문맥 윈도를 쓰면 안 되나?

**좋은 답변:**
가능하나 **경제·인지적으로 비효율**.
1. **비용**: Claude Opus 5.5에 1M 토큰 호출이 미캐시 입력 $4.00, 완전 캐시라도 $0.20, 매 턴. 검색 문맥의 10K 토큰 호출은 $0.04. 캐싱이 격차 좁혔으나 안 닫았고, OpenAI는 입력 272K 넘으면 전 요청을 장문맥 요율 청구.
2. **어텐션 희석**: "장문맥" 모델이라도 "Lost in the Middle"·컨텍스트 부패가 요인. 문맥이 무관 역사 턴으로 어수선하면 *현* 과제 추론 저하.
3. **지연**: TTFT(첫 토큰까지 시간)가 미캐시 문맥 크기로 스케일, 장문맥 디코딩이 토큰당 느림.
스태프급 아키텍처는 **전략적 검색**으로 문맥 윈도를 린하고 집중되게 유지.

### Q: 티어 3(전역 의미 메모리)의 "프라이버시 누출"을 어떻게 다루나?

**좋은 답변:**
티어 3(의미 메모리)는 **네임스페이스로 샤딩**돼야. 각 사용자·조직이 벡터 DB·지식 그래프서 고유 `namespace_id`. DB 계층서 **RLS(Row Level Security)** 구현. 더해 통합 단계에 **PII 스크러빙 계층** 써 민감 데이터(비밀번호·PII)가 일시 L1 문맥서 영속 L3 지식 스토어로 결코 안 가게. 운영자조차 메모리 못 읽어야 하는 요구면 참조 설계는 클라이언트 보유 키 + 하드웨어 엔클레이브 처리: Google이 (2026-09-23, 제품 날짜 없는 계획으로) Private AI Compute용 서버 측 메모리 기술, 스토리지 키가 사용자 기기에만 살고, 어테스트 엔클레이브가 요청당 복호·재암호, 서버 소프트웨어가 변조 불가 공개 기록에 발행돼 기기가 데이터 전송 전 검증 가능. Apple Private Cloud Compute와 같은 패턴.

### Q: 에이전트 메모리를 벡터 데이터베이스 대신 파일로 저장할 때는?

**좋은 답변:**
메모리가 **작고 큐레이트되고 인간 감독 필요**할 때 파일: 프로젝트 관례·사용자 선호·절차·결정. 인덱스 있는 수백 Markdown 파일이 에이전트 탐색 스타일에 맞고, 모든 변경이 검토 가능 git diff, 롤백이 revert. 그래서 Letta가 모든 에이전트를 git 기반 MemFS로 옮기고 코딩 에이전트가 `CLAUDE.md`·`AGENTS.md`로 수렴. 메모리가 **크고 추가 중심이고 퍼지 회상**될 때 벡터: 어느 게 중요한지 미리 모를 수천 과거 대화·궤적. 대부분 프로덕션 시스템이 둘 다로 끝남: 의미·절차 계층은 파일, 에피소드 계층은 벡터(또는 읽기 시 큐레이션의 원시 로그). 파일의 운영 함정 하나: GDPR 하 사용자 데이터 삭제가 현 커밋뿐 아니라 git 히스토리 정화를 의미.
