# KV 캐시와 컨텍스트 캐싱

KV 캐시는 장문맥 AI 시스템에서 가장 큰 메모리 소비처다. 이 캐시를 효과적으로 관리하는 것이, 1M+ 토큰으로 확장되는 시스템과 10k에서 터지는 시스템을 가른다.

## KV 캐시 문제

생성 중 모델은 이전 모든 토큰의 Key(K)·Value(V) 텐서가 필요하다. 이를 메모리에 저장하는 건 비싸다.

**VRAM 계산(Llama 3.3 70B, 표준 GQA):**
- **토큰**: 128,000
- **정밀도**: BF16(값당 2바이트)
- **메모리**: `2(KV) × layers(80) × context(128k) × kv_heads(8) × head_dim(128) × 2 bytes`
- **토큰당**: 320 KiB
- **총**: 128k 문맥에서 **사용자당 약 42 GB**.

이 공식은 표준 멀티헤드/그룹 쿼리 어텐션에만 성립한다. 많은 2026 오픈 플래그십은 잠재·희소·슬라이딩 윈도·선형 어텐션을 써서 토큰당 KV가 2자릿수 이상 다르다(아래 KV 압축 참고). 모델마다 자체 아키텍처로 산정하라.

---

## GQA: 그룹 쿼리 어텐션

GQA는 전통적 트랜스포머에서 성능 손실 없이 KV 캐시를 줄이는 표준 방법이다.

| 방법 | 비율 | KV 캐시 감소 | 품질 손실 |
|--------|-------|-------------------|--------------|
| **멀티헤드(MHA)** | 1:1 | 1배(기준) | 0% |
| **그룹 쿼리(GQA)** | 8:1 | **8배** | &lt; 0.2% |
| **멀티쿼리(MQA)** | 전체:1 | 64-128배 | 2-3% |
| **멀티헤드 잠재(MLA)** | 토큰당 압축 잠재 | DeepSeek-V2는 67B MHA 선대보다 KV 93.3% 감소 보고 | 작음(DeepSeek 보고) |

**뉘앙스**: GQA는 여러 "추론" 헤드가 같은 KV "메모리"에 주의하게 해, 디코드 단계에 필요한 메모리 대역폭을 크게 줄인다.

## 컨텍스트 캐싱(셀프호스트)

프로덕션 시스템은 공통 프리픽스를 가진 프롬프트(예: 1,000명이 공유하는 100쪽 지식 베이스)에 **공유 KV 캐시**를 쓴다.

### 계층형 KV 저장
- **GPU HBM**: 즉시 접근, 엄격히 제한된 크기.
- **호스트 DRAM**: 더 큼, PCIe·NVLink-C2C 한 홉.
- **디스크·공유 스토리지·피어 노드**: 느림, 거의 무제한.

양대 오픈 엔진이 이제 이 계층을 구현한다. **SGLang HiCache**는 3계층(GPU, CPU 호스트 메모리, Mooncake·3FS·NIXL 백엔드 스토리지). **vLLM 계층형 KV 오프로딩**은 호스트 중심: 모든 KV가 고정 호스트 DRAM을 거치고, 복사 완료 즉시 GPU 메모리 해제, 2차 계층(파일시스템·오브젝트 스토어·원격 피어)은 호스트에서 공급; v0.28.0이 디스크 계층 추가. 정형 호스트 레이아웃 덕분에 텐서 병렬 크기가 다른 노드들이 캐시 청크를 공유할 수 있다. NVIDIA Dynamo는 별도 KV 블록 관리자(KVBM, v1.6.0 제거 목표)를 폐기하고 이 엔진 네이티브 오프로드를 택했다.

두 설계 결과:
- **하이브리드 어텐션엔 더 똑똑한 프리픽스 캐시가 필요하다.** SGLang v0.5.20은 프리픽스 분기점에서 슬라이딩 윈도 상태를 캐시; 공유 시스템 프롬프트의 DeepSeek-V4-Flash에서 토큰 적중률 43.8%→60.8%, 평균 TTFT 1.57초→1.07초.
- **호스트 DRAM은 공짜 용량이 아니다.** 메모리 제조사는 2028년까지 수요 초과를 예상하고(Micron, The Register), 일부 모델은 이제 파라미터도 거기 둔다: Qwen3.8-Flash-Next는 비동기 프리페치로 호스트 메모리에 오프로드되도록 설계된 51B 파라미터 N-gram 임베딩을 더해, KV 계층과 같은 DRAM을 두고 경쟁한다.

**멀티테넌트 유의점: 프리픽스 캐시는 사이드 채널이다.** 테넌트가 캐시를 공유하면, 한 테넌트가 캐시 적중 타이밍으로 다른 테넌트가 특정 프리픽스를 보냈는지 감지할 수 있다. 엔진은 테넌트별 `cache_salt`로 완화하지만, 모든 코드 경로에서 유지돼야 한다: vLLM은 한 API 경로의 도구 연속 턴이 솔트를 떨어뜨려 테넌트 간 오라클을 다시 연 버그(GHSA-935w-9g4m-p28p, v0.30.0 수정)를 고쳤다. 테넌트별 솔트, 엔드포인트별 테스트, 패치된 엔진 유지.

## API 수준 컨텍스트 캐싱(프롬프트 캐싱)

주요 공급사(OpenAI, Anthropic, Google, DeepSeek)는 **프롬프트 캐싱** 할인을 제공하며, 배수가 이제 벤더만이 아니라 모델별로 다르다.

| 공급사 | 기능명 | 가격(100만 토큰당) | 비고 |
|----------|--------------|------------------------|----------|
| **Anthropic** | 프롬프트 캐싱(명시 중단점) | 읽기 대부분 모델 0.1배(Sonnet 5.5 $0.20), Opus 5.5 0.05배($0.20), Fable 5.1 0.025배($0.25). 쓰기 1.25배(5분 TTL)/2배(1시간) | Opus 5.5는 512토큰부터 캐시; 베타로 캐시 무효화 없이 대화 중 도구 추가 |
| **OpenAI** | 프롬프트 캐싱(자동) | GPT-5.6 이후: 쓰기 1.25배, 읽기 0.1배(GPT-6 Sol $0.20), GPT-6.1 Sol 0.05배($0.10). 구형: 쓰기 비용 없음 | 최소 1,024토큰; GPT-5.6+ 고정 30분 TTL |
| **Google** | 컨텍스트 캐싱(암묵·명시) | Gemini 3.8 Flash: 읽기 $0.075(0.1배, 2026-12-31까지 프로모; 2027-01-01 $0.15) + 저장 시간당 1M 토큰당 $0.50($1.00 2027-01-01); Gemini 3.1 Pro Preview 200K 미만 읽기 $0.20 | 저장은 시간당 과금이라 장수명 명시 캐시엔 충분한 트래픽 필요 |
| **DeepSeek** | 컨텍스트 캐싱(자동) | V4.1-Flash 캐시 적중 피크 $0.006 / 오프피크 $0.003; V4-Pro $0.044 / $0.022 | 피크는 평일 UTC 01:00-04:00·06:00-10:00, 중국 공휴일 제외 |

**손익분기 뉘앙스**: 쓰기 1.25배·읽기 0.1배(Anthropic, GPT-5.6+ OpenAI)면, 캐싱은 **첫 적중**(TTL 내 둘째 요청)에 본전이다: 1.25 + 0.1 &lt; 2. Anthropic 1시간 쓰기 2배는 둘째 적중이 필요(2 + 0.1 > 2이나 2 + 0.2 &lt; 3). 진짜 실패 모드는 손익분기 산수가 아니라 **적중률**이다: 에이전트 턴 사이 TTL 만료, 바뀌는 프리픽스(타임스탬프, 재정렬 도구, 상단 근처 사용자 ID), 최소 캐시 길이 미만 프롬프트. OpenAI(Responses API, 2026-09-08)와 Anthropic(9/23) 모두 캐시 진단을 노출하니, 적중률을 SLO로 다루고 경보하라.

**가격 격차**: DeepSeek V4.1-Flash 피크 캐시 적중가($0.006)는 GPT-6 Sol 캐시 입력($0.20)보다 약 33배 아래지만 GPT-6 Luna($0.01)보다는 2배 미만 아래다. DeepSeek은 2026년 여러 번 재가격했으니(8/16 피크·오프피크, 9/10 V4.1-Flash), 이 수치 기반 비용 모델엔 날짜를 찍어라.

## KV 압축과 컴팩트 아키텍처

dtype(FP8·4비트 KV, [양자화 심층 분석](https://github.com/ombharatiya/ai-system-design-guide/blob/main/03-training-and-adaptation/07-quantization-deep-dive.md)) 너머로, KV를 줄이는 두 계열이 있다.

**1. 아키텍처적(모델에 학습, 그 모델 기준 무손실).** 2026 오픈 플래그십은 모두 비표준 어텐션·KV 방식을 낸다:

| 모델 | 방식 | KV 함의 |
|-------|--------|----------------|
| Llama 3.3 70B | GQA, BF16 | 토큰당 320 KiB(기준) |
| DeepSeek V4.1-Flash | 인과 인코더-디코더; 디코더 전역 KV를 인코더 상태에서 투영; Compressed Sparse Attention 2; FP4 메인 KV | 토큰당 전역 KV 약 890바이트, V4-Flash보다 약 4배 아래(DeepSeek 보고) |
| MiMo-V2.6-Pro | 슬라이딩 윈도 60개(128토큰 창) + 전역 10개 | 전역 10개 레이어만 문맥에 따라 증가 |
| Qwen3.8-Flash-Next | 네 레이어 중 세 개 Gated DeltaNet 선형, 넷째 Qwen Sparse Attention | 선형 레이어는 고정 상태; 네 번째마다만 증가 KV 캐시 |
| GLM-5.3-Flash | 선형(KDA)과 DeepSeek식 희소 어텐션 하이브리드 | 선형 레이어 고정 상태; 희소 레이어는 KV 크기보다 어텐션 연산을 더 줄임 |
| Tencent Hy4 preview | 인덱스 캐시의 게이트형 DeepSeek식 희소 어텐션 | 희소 경로용 엔진 커널 필요, 없으면 dense 비용 |

**2. 런타임 압축(서빙 시 적용, 손실).** 몇 개 "어텐션 싱크" 토큰 + 최근 창 유지(StreamingLLM), 또는 누적 어텐션이 낮은 토큰 축출(H2O, SnapKV). 긴 챗 세션엔 도움되나, 검색 집약 프롬프트가 필요한 사실 하나를 조용히 떨굴 수 있으니, 활성화 전 니들·과제 평가를 돌려라.

실무 결과: "노드에 1M 토큰 동시 세션 몇 개가 맞나"는 이제 GPU 수보다 아키텍처와 엔진의 지원(슬라이딩 윈도 인식 프리픽스 캐싱, 희소 어텐션 커널, vLLM HiSparse 같은 호스트 상주 희소 KV 계층)에 더 달렸다.

## 면접 질문

### Q: PagedAttention은 KV 캐시 관리에 어떻게 도움되나? (간단히)

**좋은 답변:**
표준 KV 캐시는 연속 메모리 할당(하나의 거대 RAM 블록)이 필요하다. 이는 **외부 단편화**(메모리는 있으나 쓸 수 없는 틈)로 이어진다. PagedAttention(vLLM)은 KV 캐시를 작고 고정 크기인 "페이지"(OS 가상 메모리처럼)로 쪼갠다. 이로써 캐시가 비연속일 수 있어, 필요할 때 정확히 할당하고 같은 프리픽스를 가진 다른 요청 간 페이지를 공유할 수 있다. vLLM 논문은 이전 시스템이 단편화·과예약으로 KV 메모리의 60-80%를 낭비했고 페이징은 4% 미만임을 측정했는데, 여기서 2-4배 처리량 이득이 나왔다.

### Q: 5만 토큰 문서에 컨텍스트 캐싱이 RAG보다 나은 이유는?

**좋은 답변:**
저렴한 컨텍스트 캐싱(DeepSeek, Gemini, Anthropic)에선, 중간 크기 문서에 RAG가 종종 "과잉"이다.
1. **회상**: 컨텍스트 캐싱은 100% 검색 회상(전체 문서가 창 안)을 주지만 RAG는 검색 정확도에 의존. 긴 창에서도 세부를 놓칠 수 있으니 문서 길이에서 니들 평가로 테스트하라.
2. **일관성**: 모델이 문서 전체의 교차 참조를 볼 수 있다.
3. **경제성**: 5만 토큰에선 캐시 입력 비용이 벡터 DB·검색 파이프라인 유지의 복잡성보다 종종 낮다.

### Q: 용량 계획에 모든 모델에 토큰당 `2 × layers × kv_heads × head_dim × bytes`를 썼다. 무엇이 깨지나?

**좋은 답변:**
그 공식은 표준 MHA·GQA에만 맞다. 2026 오픈 플래그십은 대부분 아니다: DeepSeek은 FP4 메인 KV의 잠재·압축 희소 어텐션(V4.1-Flash 토큰당 전역 KV 약 890바이트 vs BF16 Llama-3.3-70B 320 KiB), MiMo는 대부분 슬라이딩 윈도 레이어, Qwen 최신은 네 레이어 중 세 개 선형 어텐션(고정 상태 유지). 그래서 토큰당 KV가 모델 간 300배 이상 차이 나고, 공식은 일부를 자릿수만큼 과대 추정하며 다른 일부의 고정 상태·슬라이딩 윈도 비용을 무시한다. 나는 모델별로 config에서 KV를 계산하고, 엔진이 실제로 컴팩트 방식을 구현하는지 확인하며(아니면 풀사이즈 KV를 냄), 프리픽스 캐시 동작을 포함하고(슬라이딩 윈도 모델은 분기점 인식 캐싱이 필요), 대상 문맥 길이에서 부하 테스트로 검증한다. 이제 프리필·디코드가 다른 활성 파라미터 수를 가질 수도 있으니 그 풀도 따로 산정한다.
