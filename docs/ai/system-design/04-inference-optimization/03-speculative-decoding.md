# 추측 디코딩

추측 디코딩(speculative decoding)은 이제 표준이 된 기법으로, LLM이 순전파당 여러 토큰을 생성하게 해 순차 디코딩의 메모리 대역폭 병목을 사실상 깬다. 2026년에는 선택적 서빙 트릭이라기보다 모델 배포사가 체크포인트와 함께 제공하는 것이 되고 있다.

## 핵심 개념

LLM 디코딩은 메모리 바운드다: 2바이트 토큰 하나를 내려고 140GB 가중치(70B 모델)를 로드하는 건 비효율적이다.
**추측 디코딩**은 더 싼 방법으로 다음 $N$ 토큰을 "추측"하고, 큰 모델로 한 번의 병렬 "프리필식" 패스에서 모두 검증한다.

---

## 드래프트-검증 패러다임

1. **드래프팅**: 싼 드래프터(소형 모델, 타깃의 추가 헤드, 번들 모듈)가 $K$개 후보 토큰 제안.
2. **검증**: 큰 "타깃 모델"이 $K$개를 한 번에 처리.
3. **수락**: 타깃 로짓으로 후보를 수락/기각. 토큰 $i$가 기각되면 그 뒤 모두 폐기.

고전적 별도 드래프트 설정의 예시 수치:

| 모델 | 크기 | 속도 | 토큰당 지연 |
|-------|------|-------|-------------------|
| **드래프트** | 1B | 빠름 | 5ms |
| **타깃** | 70B | 느림 | 50ms |
| **추측** | - | **빠름** | **15ms-25ms** |

**순 결과**: 낮은 동시성에서 **품질 손실 0**으로 실제 시간 2-3배 속도. 보장은 정확하다: 표준 추측 샘플링에선 출력 분포가 증명 가능하게 타깃과 같고, 그리디 디코딩에선 토큰 단위로 동일하다. 달라지는 건 속도이며, **수락 길이**(검증 스텝당 수락 토큰)에 달렸다.

---

## 2026년 드래프터: 헤드, MTP, 확산, DSpark

업계는 VRAM·둘째 KV 캐시·토크나이저 매칭 고통을 더하는 별도 학습 드래프트 모델에서, 타깃에 묶인 드래프터로 옮겨갔다. Medusa 헤드가 그 이동을 시작했고; vLLM에 더 이상 문서화되지 않으며(`medusa` 메서드는 허용), 아래 방법들이 대체했다.

| 방법 | 무엇이 드래프트 | 비고 |
|--------|-------------|-------|
| **EAGLE-3** | 여러 레이어의 타깃 은닉 특성을 받는 경량 헤드 | 논문은 SGLang 배치 64에서 최대 6.5배 속도·1.38배 처리량 보고; 네이티브 MTP 없는 오픈 모델의 흔한 기본 |
| **네이티브 MTP** | 모델과 함께 학습된 멀티토큰 예측 헤드(DeepSeek-V3 이후) | MiMo-V2.6, Qwen3.8-Flash-Next(4B MTP 모듈)가 내장 제공 |
| **DFlash / DFlash 2** | 블록 전체를 병렬 제안하는 소형 블록 확산 모델 | DFlash 2(Inco AI, 2026-08-18)는 Qwen3.8-27B에서 2.7-3.4배 처리량 보고(벤더); 8/19~27 SGLang·vLLM·llama.cpp 병합 |
| **DSpark** | 체크포인트에 포함된 DeepSeek 추측 모듈 | DeepSeek-V4-Flash-DSpark(6/27, MIT)는 동일 체크포인트 + 모듈; Kimi K3(RadixArk)·MiniMax-M3(NVIDIA)용 DSpark도 있고, Nemotron 3.5(NVIDIA)·LFM2.5(Liquid)도 자체 제공 |
| **별도 드래프트 모델** | 같은 계열의 소형 모델 | 위가 없을 때 유용; PARD(병렬 드래프트) 변형이 드래프팅 지연 감소 |

시스템 설계 결과 둘:
- **셀프호스트 추정은 배포사 드래프터가 켜진 것으로 가정해야.** vLLM에서 DSpark 켜기는 플래그 하나: `--speculative-config '{"method":"dspark","num_speculative_tokens":7}'`. RadixArk의 2.25B Kimi-K3-DSpark 드래프트는 GSM8K·HumanEval에서 수락 길이 약 5.4-5.5를 보고해, 디코드 스텝 상당수가 여러 토큰을 낸다.
- **평가 동등성은 추측 경로를 포함해야.** 추측 디코딩은 출력 보존이어야 하나, 커널·샘플링 설정·엔진 버그는 아니다. 프로덕션처럼 추측을 켠 채 평가하라. 업계 벤치마크가 따라잡았다: MLPerf Inference v6.1은 gpt-oss-120b Interactive에서 추측 디코딩 허용.

## 룩어헤드, N-gram, 서픽스 디코딩

모델 없는 대안은 시스템이 이미 본 텍스트에서 후보 연속을 찾는다: 룩어헤드는 모델 자신의 최근 n-gram, n-gram(프롬프트 룩업)·서픽스 디코딩은 프롬프트·이전 출력과 매칭.
- **적합**: 구조화 데이터, 코드 편집, 문맥을 인용하는 RAG 답, 반복적 기술 문서. 빗나가도 비용이 거의 없어, 파일을 재작성하는 에이전트 루프의 좋은 기본값.

## 부하 인식 추측(적응형 검증)

고전적 반론: 추측은 여유 연산을 쓰는데 큰 배치엔 여유가 없으니, 고정 드래프트 길이 $K$는 처리량을 해친다. 2026년 답은 요청별 부하 인식 검증 예산이다.

**vLLM 적응형 검증**(2026-08-14 DSpark용 도입)은 각 (요청, 위치) 드래프트 슬롯을 생존 확률(드래프터 위치별 신뢰도의 누적곱)로 점수화하고, 시작 시 프로파일된 스텝 비용 모델에서 나온 전역 상위 B개 슬롯만 검증한다. 데이터가 고정 $K$가 왜 연산을 낭비하는지 보인다: DeepSeek-V4-Pro-0813에서 7토큰 드래프트의 첫 토큰은 70% 이상, 마지막은 10% 미만 생존. 적응형 검증으로 vLLM은 낮은 동시성의 긴 드래프트 이득을 유지하며 동시성 256까지 추측이 유익하다고 보고한다(벤더).

알아둘 제약:
- 출시 시 DSpark 전용, 완전 CUDA 그래프 필요, LoRA·파이프라인 병렬 미지원.
- v0.29.0이 응답에 요청별 수락 통계 추가(`--per-request-spec-decode-metrics`), 테넌트·프롬프트 유형별로 로깅할 것.
- v0.30.0이 Model Runner V2 하에서 온라인 수락 추정기로 모든 드래프트 모델 추측기(MTP, EAGLE-3, DFlash)로 확장, 타깃 어텐션 백엔드가 가변 길이 검증을 지원하는 한.

하드웨어도 같은 아이디어를 따른다: NVIDIA는 Vera Rubin GPU 옆에서 Groq 3 LPX 랙을 외부 추측 드래프터로 돌리는 것을 지원 서빙 모드로 명시한다.

## 면접 질문

### Q: 추측 디코딩은 왜 고온도 창작에 잘 안 되나?

**좋은 답변:**
추측 디코딩은 "드래프트 모델"이 "타깃 모델"이 할 말을 정확히 예측할 수 있음에 의존한다. 고온도 창작에선 확률 분포가 "평탄"해지고 모델이 덜 가능한 토큰을 고르도록 유도된다. 이는 매우 낮은 **수락률**(드래프트 추측이 자주 기각)로 이어진다. 기각이 정확성을 해치진 않지만(검증 패스가 여전히 교정된 토큰 하나를 냄), 낮은 수락에선 사실상 순차 디코딩 + 드래퍼 지연 + 낭비된 검증 연산을 하게 되어 추측 끈 것보다 느려진다.

### Q: 드래프트 헤드(Medusa, EAGLE-3, 네이티브 MTP)는 별도 드래프트 모델과 어떻게 다른가?

**좋은 답변:**
별도 드래프트 모델은 추가 VRAM을 쓰고 자체 KV 캐시가 필요하며 토크나이저를 공유해야 하고 타깃 업데이트 시 동기화가 어긋난다. 드래프트 헤드는 타깃에 붙는다: Medusa는 각각 최종 은닉 상태에서 고정 오프셋을 예측하는 헤드를 더하고, EAGLE-3는 여러 타깃 레이어의 은닉 특성에 경량 헤드를 돌리며(Medusa보다 높은 수락), 네이티브 MTP 헤드는 모델 자체와 학습돼 분포에 가장 잘 맞는다. 모두 타깃의 순전파·KV를 재사용해 둘째 모델 오버헤드를 없앤다. 2026년 실무 차이는 소유권이다: DeepSeek·Xiaomi·Qwen 같은 배포사가 체크포인트에 드래퍼를 제공하므로, 기본은 "번들 MTP·DSpark 모듈을 쓰고, EAGLE-3나 확산 드래퍼로 폴백하며, 둘 다 없을 때만 자체 학습"이어야 한다.

### Q: "추측 디코딩은 큰 배치에서 처리량을 해치니 프로덕션에선 꺼라." 동의하나?

**좋은 답변:**
고정 드래프트 길이엔 맞았다: 높은 동시성에선 GPU가 이미 연산 포화라, 요청당 7개 추측 토큰 검증이 대부분 기각될 토큰에 연산을 태운다(수락이 위치에 따라 급락). 현재 답은 추측을 끄는 게 아니라 검증 예산을 부하 인식으로 만드는 것이다. vLLM 적응형 검증은 각 드래프트 위치를 생존 확률로 점수화해 스텝 예산 내 전역 최선 슬롯만 검증하므로, 낮은 부하엔 긴 드래프트, 높은 부하엔 고신뢰 초기 위치만 검사하며; vLLM은 동시성 256까지 순이득을 보고한다. 엔진이 지원하는 곳에서 켜고, 요청별 수락을 로깅하며, 기능 상호작용을 확인한다(출시 시 LoRA·파이프라인 병렬 미지원). 고온도 생성처럼 수락이 매우 낮은 워크로드는 경로별로 여전히 끈다.
