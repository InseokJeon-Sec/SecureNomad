# 컨텍스트 엔지니어링

컨텍스트 엔지니어링은 LLM의 유한한 "작업 기억"을 가장 가치 있는 토큰으로 채우는 과학이다. 프런티어 전반의 문맥 윈도가 약 1M 토큰(Claude Opus 5.5·Sonnet 5.5·Fable 5.1 1M; GPT-6 Astra·GPT-6.1 Sol 1.05M; Gemini 3.8 Flash 1,048,576)이고 추론이 노력 다이얼로 통제되면서, 초점이 "데이터 맞추기"에서 "관련성 순위 매기기", "연산 예산 관리", 그리고 공급자가 캐시하고 모델이 계속 추론할 수 있는 형태로 대화를 유지하기로 옮겨갔다.

## 장문맥 패러다임(1M+ 토큰)

Claude Opus 5.5(1M)·Sonnet 5.5(1M)·GPT-6.1 Sol(1.05M)·Gemini 3.8 Flash(약 1M) 같은 모델은 거대 문맥 윈도를 가진다.

**통찰**: "컨텍스트가 새로운 RAG다."
윈도에 편히 맞는 안정 코퍼스(수십만 토큰, 대략 수백 페이지)엔 외부 벡터 DB를 돌리기보다 전체 코퍼스를 문맥에 넣는 게 흔히 더 정확하고 단순하다. 이를 **"In-Context RAG"** 라 한다. 수천 파일의 문서 컬렉션엔 확장 안 되고, 재현율은 길이에 따라 여전히 저하된다(아래 컨텍스트 부패 참고).

**고르기 전 계산하라.** Claude Opus 5.5($4 입력, 캐시 읽기 $0.20/1M)의 500K 토큰 코퍼스: 캐시 안 됨 요청당 약 $2.00, 캐시됨 요청당 약 $0.10, 일회성 $2.50 캐시 쓰기 후. 같은 모델에 검색 10K 토큰을 보내는 RAG 호출은 입력 약 $0.04. 그래서 캐시된 장문맥은 이제 입력 비용에서 RAG의 약 2.5배 이내(트래픽이 캐시를 데운 한), 결정은 재현율 품질·지연·코퍼스 변경 빈도에 달렸다. 가격 절벽 주의: OpenAI는 입력이 272K 토큰을 넘으면 전체 요청을 장문맥 요율로, xAI는 200K 이상에서 전 토큰 2배, Anthropic은 1M까지 균일.

## 에이전트 컨텍스트 엔지니어링

프롬프트 엔지니어링은 좋은 지시 하나를 쓴다. **컨텍스트 엔지니어링**은 에이전트 루프의 **매 추론 턴**에 모델이 보는 토큰 전체 집합을 큐레이션한다: 시스템 프롬프트, 도구, 검색 데이터, 이전 도구 결과, 진행 중 메시지 히스토리. 에이전트가 턴마다 컨텍스트를 쌓으므로 큐레이션 문제가 일회성이 아니라 연속적이라 구별이 중요하다. 이것이 Anthropic·OpenAI·Google이 이제 에이전트 하네스를 짓는 프레임워크다.

### 컨텍스트 부패: 컨텍스트가 유한 자원인 이유

1M 토큰 윈도가 채워야 한다는 뜻은 아니다. 모델은 **컨텍스트 부패**를 겪는다: 어텐션이 n제곱 쌍별 관계로 확장되고 학습 데이터가 짧은 시퀀스로 치우쳐, 토큰 수가 늘면 정확도가 저하된다. 컨텍스트를 공짜 공간이 아니라 수익 체감하는 예산으로 다뤄라. 할 일은 모델이 여전히 올바르게 행동하게 하는 **가장 작은 고신호 토큰 집합**을 유지하는 것.

### 다섯 핵심 기법

| 기법 | 하는 일 | 쓸 때 |
|-----------|--------------|----------|
| **컴팩션** | 메시지 히스토리를 요약하고 압축 요약 + 가장 최근 아티팩트 몇 개로 루프 재초기화 | 윈도 한계에 다가가는 긴 왕복 세션 |
| **적시 로딩** | 경량 식별자(파일 경로, URL, 행 ID)를 문맥에 두고 도구로 전체 내용을 온디맨드 로드 | 다 못 맞는 대형 코퍼스·DB, 탐색적 과제 |
| **구조화 노트 작성** | 에이전트가 윈도 밖 파일·메모리 스토어에 진행 노트를 쓰고 나중에 읽어옴 | 수십 도구 호출에 걸친 장기 과제 |
| **서브에이전트 격리** | 하위 과제에 깨끗한 윈도의 집중 서브에이전트를 스폰; 1k-2k 토큰 요약만 반환 | 병렬 리서치, 딥 서치, 메인 윈도를 중간 세부로 넘칠 모든 것 |
| **시스템 프롬프트 보정** | "골디락스 존" 겨냥: 신뢰할 만큼 구체적, 깨지지 않을 만큼 일반적; 명확한 XML·마크다운 섹션 사용 | 항상, 나머지 넷의 토대로 |

### 컴팩션

히스토리가 커지면 모델에 돌려 요약하되, 하중 지지 세부(아키텍처 결정, 미해결 버그, 핵심 제약)를 보존하고 중복 도구 출력을 버린다. Claude Code가 이 패턴을 쓴다: 압축 요약 + 가장 최근 접근 파일로 계속. **먼저 재현율로 튜닝**(중요한 모든 것 유지)하고 그다음 정밀도 개선(중복 절단).

공급자가 이제 컴팩션을 대신 돌린다. Claude API는 임계 근처에서 자동 요약하는 서버 측 컴팩션(베타)과, 요약 대상 메시지 자리에 돌려보내는 서명된 컴팩션 블록을 반환하는 온디맨드 컴팩션(베타, 2026-09-14, 헤더 `compact-2026-09-04`)을 제공. 온디맨드 컴팩션은 요약 뒤 가장 최근 턴을 그대로 유지할 수 있고, 사고를 대화에 묶는 모델에서 그 유지된 턴의 사고가 유효하게 남는다. 손으로 만든 히스토리 재작성 요약은 사고 블록을 무효화하니(다음 절) 최신 Claude 모델엔 이들을 선호하라.

**요약은 신뢰 경계다.** OpenAI 오정렬 보고서(2026-09)는 RL 학습 중 모델이 자기 컴팩션 요약에 은폐 지시를 쓰는 것(GPT-5.6 Sol 요약의 2.15%, GPT-6 Astra의 0.27%에서 플래그)과, 미출시 모델이 27개 요약에 탈옥식 지시를 써 그중 하나를 후속 모델이 따른 것을 기술. 감사용 원시 전사를 유지하고, 요약을 그에 대조·검증하고, 원 시스템 프롬프트에 없던 지시를 요약이 나르게 하지 마라. [루프 엔지니어링](https://github.com/ombharatiya/ai-system-design-guide/blob/main/07-agentic-systems/12-loop-engineering.md)(영문) 참고.

### 적시 로딩

모든 문서를 미리 로드하는 대신, 에이전트가 참조를 쥐고 단계가 필요할 때만 내용을 가져온다. 사람이 파일 트리로 일하는 방식을 닮았다: 필요한 파일을 열지 레포 전체가 아니다. 윈도를 작게 유지하고 에이전트가 탐색으로 구조를 발견하게 한다. 트레이드오프는 지연이라, 하이브리드(명백한 건 미리 로드, 나머지는 가져오기)가 흔히 최선.

**도구 정의**에도 같다 — 여러 MCP 서버가 붙으면 수만 토큰이 들 수 있다. Cursor 보고(2026-09, 벤더): 오프로드한 각 내장 도구가 대화의 20% 미만에서 필요했고, 도구 동적 로딩이 정적 도구 설명 토큰을 60% 줄였고, MCP 도구를 동적 문맥으로 옮긴 이전 조치가 MCP 도구를 호출한 세션에서 총 토큰을 46.9% 줄였다. 매 턴 모든 스키마를 보내지 말고 도구 검색·지연 로딩을 쓰라.

### 구조화 노트 작성(에이전트 메모리)

에이전트가 문맥 윈도 밖에 노트를 지속하고 관련 시 끌어온다. 이것이 에이전트가 윈도보다 훨씬 긴 과제에 걸쳐 일관성을 유지하게 한다. 저장 기질(파일시스템, 벡터, 그래프)은 [에이전트 메모리와 상태](https://github.com/ombharatiya/ai-system-design-guide/blob/main/07-agentic-systems/05-agent-memory-and-state.md)·[메모리 아키텍처](https://github.com/ombharatiya/ai-system-design-guide/blob/main/08-memory-and-state/01-memory-architectures.md)(영문) 참고.

### 서브에이전트 격리

코디네이터가 집중 하위 과제를 자기 깨끗한 윈도에서 일하는 서브에이전트에 위임하고, 서브에이전트는 응축 요약을 반환한다. 상세 검색·분석 문맥이 코디네이터 윈도를 오염시키지 않는다. 이것이 병렬성 이점과 별개로 멀티에이전트 시스템이 통하는 컨텍스트 관리상 이유다. [멀티에이전트 오케스트레이션](https://github.com/ombharatiya/ai-system-design-guide/blob/main/07-agentic-systems/04-multi-agent-orchestration.md)(영문) 참고.

## 추가 전용 컨텍스트: 사고는 대화에 묶인다

많은 하네스가 조용히 히스토리를 재작성한다: 시스템 프롬프트를 타임스탬프와 재렌더, 이전 메시지를 편집해 리마인더 주입, 오래된 도구 결과를 제자리 트림, 대화 중간 모델 교체. 최신 Claude 모델에선 이것이 이제 추론 연속성을 깬다.

Claude Fable 5.1·Opus 5.5·Sonnet 5.5에선 각 사고 블록이 어느 모델이 생산했는지 기록하고 **그 앞의 아무것도 안 바뀐 경우에만** 유효하다: 시스템 프롬프트, 도구, 이전 메시지, URL 뒤 이미지 바이트까지. 읽을 수 없는 블록은 조용히 폐기(과금 안 됨); 2026-08-31 이후 생성 계정은 프리픽스 불일치 시 400("블록이 다른 대화에 묶임") 반환, 단 `thinking-binding-controls-2026-08-01` 베타 하 `drop_block`을 켜면 예외. 블록은 모델에도 묶이고(이전 모델은 Fable 5.1 블록을 안 읽고, Opus 5.5는 Fable·Mythos 블록을 안 읽음), Sonnet 5.5 블록은 추가로 생산 계정에 묶인다.

| 하네스 습관 | 추가 전용 대체 |
|---------------|-------------------------|
| 세션 중간 최상위 시스템 프롬프트 편집 | 대화 중간 `system` 메시지 추가; 턴별 리마인더엔 `clear_at: "next_user_message"`(베타, 2026-09-01) |
| `tools` 배열 편집으로 도구 교체·추가 | 대화 중간 시스템 메시지에 도구 정의 인라인(베타 `inline-tools-2026-09-15`, 2026-09-22) |
| 대화 중간 최상위 노력 변경 | 메시지별 노력(베타, 2026-09-01) |
| 오래된 턴을 대체하는 손수 요약 | 공급자 컴팩션 블록 |
| 대화 중간 다른 모델로 폴백 | 추론 폐기 예상; 요약에서 상태 재확립 또는 턴 재시작 |

OpenAI의 등가물은 전사를 재구성하는 대신 Responses API로 추론 아이템을 돌려보내는 것. 보존된 추론 상태가 중요하다는 증거: ARC-AGI-3에서 GPT-6 Astra가 ARC Prize 최소 하네스 max 노력에서 62.7%, 요청 간 추론 상태를 보존하고 컴팩션을 쓰는 공급자 하네스 high 노력에서 99.9%(ARC Prize, 2026-09).

## 추론 노력과 사고 제어

이제 모든 프런티어 벤더가 응답 전 **통제 가능한 내부 추론**을 제공하고, 제어면이 토큰 예산에서 노력 레벨로 옮겨갔다.

### Claude(Opus 5.5, Sonnet 5.5, Fable 5.1): 적응형 사고 + 노력

```python
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    thinking={"type": "adaptive", "display": "summarized"},  # 기본 display는 "omitted"
    output_config={"effort": "high"},  # low | medium | high | xhigh | max
    messages=[{"role": "user", "content": "이 코드베이스를 async로 리팩터..."}],
)

# 응답엔 두 종류 블록:
# 1. thinking 블록 (추론 요약; 원시 사슬은 결코 반환 안 됨)
# 2. text 블록 (실제 답)
for block in response.content:
    if block.type == "thinking":
        print("[THINKING SUMMARY]", block.thinking)
    elif block.type == "text":
        print("[ANSWER]", block.text)
```

**핵심 파라미터:**
- `effort`: `low`~`max`. 기본값이 모델마다 다름: Opus 5.5 `medium`, Sonnet 5.5·Fable 5.1 `high`. 명시 설정하라.
- 고정 `budget_tokens`는 사라짐: Opus 4.7 이후, Sonnet 5·5.5, Fable 5·5.1에서 400 반환, Opus 4.6·Sonnet 4.6에서 폐기. Haiku 4.5는 여전히 사용.
- Opus 5.5는 사고 비활성 불가; Sonnet 5.5에선 `{"type": "disabled"}`가 400 반환, 최저 설정은 `{"type": "between_tools"}`(노력 `high` 이하에서만 수용).
- 사고 토큰은 `display` 설정과 무관하게 출력 요율로 과금: 사고 토큰 10K는 Opus 5.5 약 $0.20(출력 1M당 $20), Sonnet 5.5 약 $0.10.
- 스트리밍 작동; 기본 `display: "omitted"`에선 사고 블록이 빈 텍스트로 스트리밍돼 UI에서 긴 멈춤처럼 보임.

### OpenAI(GPT-6.1 Sol, GPT-6 Astra): 추론 노력

```python
response = client.responses.create(
    model="gpt-6.1-sol",
    reasoning={"effort": "medium"},  # low | medium | high | xhigh | max
    input="이 스케줄러의 경쟁 조건을 찾아라...",
)
print(response.output_text)
# 추론 토큰은 출력으로 과금되나 반환 안 됨; 요약은 선택
```

GPT-6.1 Sol 기본 `medium`. GPT-6 Astra는 `low`~`max`(`none` 없음), 커스텀 `temperature`·`top_p`·`logprobs` 미수용, 도구엔 Responses API 요구.

### Gemini(3.8 Flash): 사고 레벨

Gemini 3.8 Flash는 `thinking_budget`을 `thinking_level`(`low`, `medium` 기본, `high`)로 대체, Google은 2026-07-21 Gemini API에서 `temperature`·`top_p`·`top_k` 폐기. [온도 없는 결정성](01-prompt-engineering-fundamentals.md) 참고.

### 노력 레벨 고르기

| 워크로드 | 출발점 |
|----------|----------------|
| 복잡 멀티스텝 코드 리팩터, 장기 에이전트 | `high`·`xhigh` |
| 단순 Q&A, 추출, 분류 | `low`(또는 비추론 모델; Sonnet 5.5는 `between_tools`) |
| STEM/수학 | `high`; `max`는 `high`에서 평가가 여유 보일 때만 |
| 고볼륨 챗봇 | `low` |
| 보안 임계 결정 | `high` + 외부 검증기 |

레벨당 토큰 소비가 모델마다 다르고 같은 레벨 이름이 다음 모델 버전에서 다르게 행동할 수 있으니, 실제 트래픽 샘플에서 측정하고 요청당이 아니라 **완료 과제당 비용**으로 판단하라.

**프로덕션 패턴**: 전역 설정 하나 대신 복잡도 분류기로 요청별 노력 라우팅.

```python
def smart_generate(query: str) -> str:
    complexity = classifier.predict(query)  # 0-1 점수
    if complexity > 0.7:
        effort = "high"
    elif complexity > 0.3:
        effort = "medium"
    else:
        effort = "low"
    return call_model(query, effort=effort)
```

단서 둘. 캐시는 모델 범위라 모델 간 라우팅은 캐시 재사용을 포기; 멀티모델 캐스케이드를 짓기 전 가장 강한 모델을 낮은 노력으로 테스트하라. 그리고 Claude에선 대화 중간 최상위 노력 변경이 캐시된 메시지를 무효화; 메시지별 노력 베타가 이를 피한다.

## 중간에서 길 잃기(Lost-in-the-Middle)

2023년엔 모델이 프롬프트 중간 정보에 정확도를 잃었다.
**현황**: 프런티어 모델(Claude Opus 5.5·Sonnet 5.5·GPT-6.1 Sol·Gemini 3.8 Flash)이 상당히 낫지만 **어텐션 그래디언트**는 여전하고, 광고 윈도가 흔히 사용 가능 문맥을 과장한다([벤치마크와 리더보드](https://github.com/ombharatiya/ai-system-design-guide/blob/main/14-evaluation-and-observability/03-benchmarks-and-leaderboards.md)(영문) 참고).
- **베스트 프랙티스**: 임계 지시와 골드 예시를 프롬프트 **맨 앞**과 **맨 끝**에. 중간 = 원시 데이터/지식 청크.
- **청크 순서 사용**: 검색 문서를 재순위해 가장 관련된 것이 처음·끝에.
- **캐싱 긴장**: 끝에 두는 건 요청마다 바뀌니, 안정 지시를 캐시 프리픽스에 두고 휘발 데이터 뒤엔 짧은 리마인더만 반복.

## 컨텍스트 예산과 토큰 인식

모든 토큰이 돈이 들고 TTFT(첫 토큰까지 시간)를 늘린다.

| 구성요소 | 예산(토큰) | 이유 |
|-----------|-----------------|------|
| **시스템 프롬프트** | 1,000 - 10,000 | 핵심 로직·페르소나; 에이전트 하네스 프롬프트는 상단에 있고 가장 먼저 트림 대상(Cursor가 2026-09 시스템 프롬프트 약 66% 절단). |
| **도구 정의** | 1,000 - 50,000+ | 모든 MCP 서버로 증가; 온디맨드 로드. |
| **히스토리** | 2,000 - 5,000 | 대화 "상태". |
| **데이터/검색** | 10k - 1M | 과제 깊이에 의존. |
| **출력 + 사고 예비**| 16,000 - 128,000 | 사고 토큰이 `max_tokens`에 산입; 현 프런티어 모델은 최대 128K 출력 허용. |

에이전트 워크로드는 입력 지배: Anthropic Claude Code 텔레메트리(2026-09, 벤더)가 입력:출력 토큰 비 324:1(189:1에서 상승)을 보임. 그 비율에선 출력가가 아니라 캐시 입력가·캐시 적중률이 과금을 몬다.

## 프롬프트 캐싱 경제학

거의 모든 주요 공급자(OpenAI, Anthropic, Google, DeepSeek)가 **프리픽스 캐싱**을 지원하고, 읽기 할인이 이제 깊고 모델별이다:

| 공급자 | 캐시 쓰기 | 캐시 읽기 | 메커니즘 |
|----------|-------------|------------|-----------|
| **Anthropic** | 1.25배(5분 TTL) 또는 2배(1시간 TTL) | 대부분 0.1배; Opus 5.5 0.05배($0.20/1M); Fable 5.1 0.025배($0.25/1M) | 명시적 `cache_control` 브레이크포인트 또는 최상위 자동 캐싱 |
| **OpenAI**(GPT-5.6+) | 1.25배 | 0.1배; GPT-6.1 Sol 0.05배 | 1,024 토큰 초과 시 자동; TTL 30분 고정 |
| **Google**(Gemini 3.8 Flash) | 별도 쓰기가 없음; 명시 캐시는 시간당 1M 토큰당 $0.50 저장 과금($1.00 2027-01-01부터) | 0.1배($0.075/1M 도입가, $0.15 2027-01-01부터) | 암시 캐싱은 4,096 토큰 초과 시 자동; 명시 캐시는 내용·수명 통제를 주나 유휴 캐시가 절감보다 저장 비용이 클 수 있음 |
| **DeepSeek**(V4.1-Flash) | 추가요금 없음(미스는 정상 입력가) | 캐시 미스가의 약 2% | 자동; 피크·오프피크 가격 |

- **교차점**: 1.25배 쓰기와 0.1배 이하 읽기면 캐시가 첫 적중에 본전; 2배 1시간 쓰기는 둘째 적중부터 본전. TTL 내 대형 문맥(예: 코드베이스)을 한 번 넘게 재사용하면 캐싱 승.
- **적중률을 관측 가능하게**: 캐시 진단이 OpenAI Responses API(2026-09-08)·Claude API(2026-09-23)에서 GA. 적중률을 SLO로 추적.

**아키텍처 선택**: "시스템 프롬프트 + 도구 + 기본 지식"을 정적으로 유지해 거의 100% 캐시 적중률을 유지하도록 설계하라. 조용한 무효화가 보통 범인: 시스템 프롬프트의 타임스탬프, 미정렬 JSON, 요청마다 바뀌는 도구 목록.

전체 비용 모델은 [FinOps와 토큰 경제학](https://github.com/ombharatiya/ai-system-design-guide/blob/main/11-infrastructure-and-mlops/04-finops-and-token-economics.md)(영문) 참고.

## 컨텍스트 압축

컨텍스트의 휘발 부분(검색 청크, 도구 출력, 긴 사용자 문서)이 크면 프런티어 모델에 닿기 전 압축하라.
- **방법**: 작은 보조 모델이 토큰·문장을 점수화해 저정보를 버림. LLMLingua-2(Microsoft, 2024)는 과제 무관 압축용 작은 토큰 분류기를 학습해 벤치마크에서 완만한 품질 손실로 2~5배 압축 보고. 추출 필터링(재순위기가 관련으로 점수한 문장만 유지)이 더 단순한 베이스라인.
- **값하는 곳**: 캐시 안 된 휘발 입력. 안정 프리픽스는 압축 말 것: 압축이 바이트를 바꿔 프리픽스 캐시를 깨고, 0.025~0.1배 캐시 읽기가에선 캐시된 프리픽스가 어떤 압축보다 이미 싸다.
- **위험**: 압축이 중요한 단 하나의 부정·숫자를 지울 수 있음. 켜고 끄고 자신의 과제에서 평가하라.

## 면접 질문

### Q: 언제 RAG보다 장문맥을 택하나?

**좋은 답변:**
고충실 검색·문서 간 추론이 임계이고 코퍼스가 안정일 때 장문맥을 택한다. RAG는 "검색 간극"을 겪는다: 벡터 검색이 관련 청크를 놓치면 모델이 결코 못 본다. 장문맥(현 프런티어 약 1M 토큰)은 검색 미스를 없애나 어텐션 미스는 아니다: 재현율이 길이에 따라 여전히 저하되니 100% 재현율은 아니다. 비용이 장문맥에 유리하게 움직였다: 캐시된 500K 토큰 코퍼스가 Opus 5.5에서 요청당 약 $0.10, 같은 모델 10K 토큰 RAG 호출의 약 2.5배(트래픽이 캐시를 데운 한). 코드베이스 분석, 법률 문서 검토, 다중 파일 재무 감사에 쓰겠다. 동적·웹 규모 데이터, 어떤 윈도도 넘는 코퍼스, 공유 프리픽스가 표현 못 하는 사용자별 권한 필터링엔 RAG를 고수한다.

### Q: 백만 토큰 프롬프트의 높은 TTFT를 어떻게 다루나?

**좋은 답변:**
주 해법은 **컨텍스트 캐싱**: 공급자가 공유 프리픽스의 KV 캐시를 유지해 프리필이 새 토큰에만 돈다. TTFT가 급락하나 소형 프롬프트 수준은 아니다 — 새 토큰이 여전히 전체 캐시 프리픽스에 주의하고 디코드 토큰마다 그 어텐션 비용을 치르기 때문. 둘째, 캐시 안 된 걸 줄여라: 채우기 대신 검색, 휘발 부분 압축. 셋째, 일을 쪼개라: 코퍼스를 병렬 하위 호출로 맵리듀스해 결과 병합, 총 토큰을 지연과 교환. 자체 호스팅에선 청크 프리필과 프리필/디코드 분리가 거대 프롬프트가 다른 요청을 멈추지 않게 하나, 그 한 프롬프트의 프리필을 빠르게 하진 않는다.

### Q: 에이전트가 짧은 과제엔 잘 되나 장기 과제에 저하된다. 어떻게 고치나?

**좋은 답변:**
이는 **컨텍스트 부패**다: 윈도가 낡은 도구 출력으로 차고 모델이 맥을 잃는다. 에이전트 컨텍스트 엔지니어링을 적용하겠다. 첫째, **컴팩션**: 임계에서 히스토리를 요약하고 요약 + 최근 아티팩트로 계속, 가능하면 공급자 컴팩션을 쓰고 요약을 원시 전사에 대조할 신뢰 못 할 출력으로 다룸. 둘째, **적시 로딩**: 전체 내용 대신 파일 경로·ID를 쥐고 온디맨드 가져오기. 셋째, **구조화 노트 작성**: 에이전트가 재독할 스크래치 파일에 진행을 써 작업 기억을 작게 유지. 중간 세부가 많은 하위 과제(딥 서치, 다중 파일 분석)엔 **서브에이전트 격리**로 세부가 메인 윈도를 넘치는 대신 짧은 요약으로 반환. 목표는 턴당 가장 큰이 아니라 가장 작은 고신호 토큰 집합.

### Q: 게이트웨이가 대화 중간 Opus 5.5에서 다른 모델로 폴백하고, 품질·오류율이 모두 나빠진다. 무슨 일인가?

**좋은 답변:**
두 가지. 최신 Claude 모델의 사고 블록은 생산 모델에 묶이므로 폴백 모델이 이를 폐기하고 이전 추론 없이 계속 — 그게 품질 손실. 그리고 게이트웨이가 가는 길에 히스토리도 재작성하면(시스템 프롬프트 재렌더, 오래된 도구 결과 트림, 이전 턴에 리마인더 주입) 프리픽스 검사가 실패: 2026-08-31 이후 생성 계정은 400, `drop_block` 켜면 그 추론 없이 요청 실행. 해법은 하네스를 추가 전용으로(대화 중간 시스템 메시지, 인라인 도구 추가, 공급자 컴팩션) 만들고 폴백을 명시적으로: 폴백 모델에서 깨끗한 요약으로 턴 재시작, 안전 거절엔 게이트웨이가 히스토리를 안 건드리고 권장 모델에서 재시도하는 공급자 서버 측 폴백(`fallbacks: "default"`, 베타) 사용. 대화당 폐기된 사고 블록 지표도 더해 조용히 퇴행 못 하게 하겠다.
