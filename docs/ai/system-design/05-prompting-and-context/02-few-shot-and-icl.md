# 퓨샷과 인컨텍스트 러닝(ICL)

인컨텍스트 러닝(ICL)은 LLM이 가중치 갱신 없이 프롬프트의 예시를 보는 것만으로 새 과제를 배우는 능력이다. ICL 효율을 최대화하는 것이 프롬프트 안정성의 핵심 레버다.

## 퓨샷 예시의 해부

고품질 예시는 세 부분으로 이뤄진다:
1. **입력**: 잠재 사용자 데이터의 현실적 샘플.
2. **추론(선택)**: 출력이 왜 그런지에 대한 짧은 설명.
3. **출력**: "골드 스탠더드" 결과.

```markdown
User: "날씨는 괜찮았지만 항공편이 늦었어요."
Reasoning: 사용자는 날씨엔 중립이나 서비스엔 부정적.
Sentiment: Mixed
```

---

## 예시는 몇 개?

| 모델 크기 | 스위트스팟 | 확장 거동 |
|------------|------------|------------------|
| **소형(8B)** | 5 - 10 | 약 20개까지 이득 지속. |
| **중형(70B급 dense 또는 약 30B 활성 MoE)**| 3 - 5 | 일찍 정체; 예시 늘면 지연 증가. |
| **프런티어(폐쇄 또는 1T급 MoE)**| 0 - 2 | 고역량; "지시 따르기"로 대개 충분. 예시는 주로 출력 포맷 고정. |

**어림 규칙**: 짧은 문맥 예산에서 안정적 출력에 20개 넘는 예시가 필요하면, 과제가 모델에 너무 복잡할 가능성이 크다. 고전적 다음 단계는 **파인튜닝**이었으나; 1M 토큰 윈도와 싼 캐시 읽기로 이제 **메니샷 ICL**이 진짜 대안이다.

---

## 메니샷 ICL vs 파인튜닝

메니샷 ICL은 수백~수천 예시를 프롬프트에 넣는다. Google DeepMind 연구(Agarwal et al., 2024)는 많은 과제에서 퓨샷 영역을 훨씬 지나서도 이득이 지속하고, 일부 경우 메니샷 프롬프트가 퓨샷이 못 넘던 사전학습 편향을 뒤집음을 발견했다.

2026년 경제학이 바뀐 건 예시 블록이 **안정 프리픽스**이고 캐시 읽기가 싸기 때문:

| 설정(요청당, 정가) | 50K 토큰 예시 블록의 입력 비용 |
|----------------------------------|------------------------------------------|
| Claude Sonnet 5.5, 캐시 안 됨($2/1M) | $0.10 |
| Claude Sonnet 5.5·Opus 5.5, 캐시 읽기($0.20/1M) | $0.01 |
| GPT-6.1 Sol, 캐시 읽기($0.10/1M) | $0.005 |

그 가격에서 메니샷 ICL은 반복 속도(학습 실행이 아니라 예시 변경)와 이식성(다음 모델로 변경 없이 이동)에서 파인튜닝을 이긴다. 파인튜닝은 요청당 지연, 예시가 안 맞는 과제, 예시를 배포하지 않고 동작이 필요할 때 여전히 이긴다. 플랫폼 위험도 중요: OpenAI가 셀프서브 파인튜닝을 접는 중이고, 활성 고객도 2027-01-06부터 새 파인튜닝 작업을 못 만든다. [파인튜닝 전략](../03-training-and-adaptation/02-fine-tuning-strategies.md) 참고.

## 동적 예시 선택

프로덕션 RAG·분류에선 모든 사용자에 같은 정적 예시를 쓰지 말 것.
**동적 패턴:**
1. 사용자가 쿼리 제공.
2. "골드 예시 벡터 DB"에서 가장 **의미적으로 유사한** 3개 케이스 검색.
3. 그 특정 3개 케이스를 프롬프트에 주입.

**결과**: 모델이 현 사용자에 관련된 "국소" 패턴을 봐서 정확도가 급격히 상승.

**트레이드오프**: 동적 예시는 요청마다 바뀌어 캐시 프리픽스에 못 앉는다. 마지막 캐시 브레이크포인트 뒤에 두거나, 캐시 절감이 쿼리별 선택의 정확도 이득을 넘을 때 정적 메니샷 블록을 쓰라.

## 라벨링 뉘앙스의 중요성

프런티어 모델은 예시의 **분포 편향**에 민감하다.
- "긍정" 예시 5개와 "부정" 1개를 주면 모델이 "긍정"으로 편향.
- **해법**: 항상 **라벨 균형**을 쓰라. 퓨샷 예시가 예상 출력 분포를 대략 반영하거나 완전 균형(1:1)이게 하라.

## 고급 ICL: 유추와 "퓨샷 CoT"

**유추 프롬프팅**: "X를 하라" 대신 유추를 제공.
"번역가가 시를 프랑스어에서 영어로 옮기듯 이 코드를 번역하라: 영혼(로직)은 보존하되 구문은 바꿔라."

**퓨샷 CoT**: 추론이 명시적인 예시 2개 제공. 이는 모델의 주의를 출력 문자열 모방이 아니라 로직에 집중하도록 "프라이밍"한다. 추론 모델에선 어차피 답 전에 추론하므로 덜 중요하다; 거기선 적용받길 원하는 *결정 기준*을 보이려 작동 예시를 쓰되 사고 스크립트는 쓰지 마라. 예시 속 추론은 짧은 근거로 유지하라: 최신 Claude 모델에선 출력에 모델의 전체 추론을 요청하는 것이 거절될 수 있음([사고 사슬](03-chain-of-thought.md) 참고).

## 면접 질문

### Q: 가진 50개 예시를 그냥 다 프롬프트에 넣으면 안 되나?

**좋은 답변:**
주요 이유 셋:
1. **문맥 윈도 지연**: 모든 예시가 토큰을 더해 "프리필" 시간과 요청당 비용 증가.
2. **주의 희석**: 1M 토큰 윈도에도 너무 많은 무관 데이터에 묻히면 모델이 특정 제약을 "잃을" 수 있음("중간에서 길 잃기" 효과와 컨텍스트 부패).
3. **과적합**: 너무 많은 좁은 예시는 모델이 예시 *포맷*을 지나치게 엄격히 모방하게 해, 그 집합 밖 엣지 케이스를 다룰 일반 역량을 잃게 함.

반론: 50개 예시가 안정적이면 캐시 프리픽스가 되고, 1M 캐시 토큰당 $0.10~$0.20에선 비용 논거가 대개 사라진다. 그럼 질문이 경험적으로 된다: 동적 예시 3개, 전체 50개, 메니샷으로 평가를 돌리고, 품질 기준을 만족하는 가장 싼 구성을 유지하라.

### Q: 인컨텍스트 러닝의 "라벨 편향"이란?

**좋은 답변:**
라벨 편향은 모델이 특정 라벨을 단지 퓨샷 예시에 더 자주 나오거나 목록 끝에 나왔다는 이유로 더 자주 예측할 때 발생한다(다수 라벨·최신성 편향, Zhao et al., 2021). 표준 완화책:
1. 요청마다 예시 순서 섞기. 요청별 셔플은 프리픽스 캐싱을 깨니, 캐시 예시 블록엔 프롬프트 버전당 균형 순서를 한 번 고르고 순열 테스트로 검증하라.
2. 긍정/부정/중립 샘플 수를 균등하게.
3. 프롬프트 개발 중 "순열 테스트"로 모델이 순서가 아닌 내용에 반응하게.
4. 내용 없는 입력("N/A")으로 보정해 사전확률을 측정·차감.
