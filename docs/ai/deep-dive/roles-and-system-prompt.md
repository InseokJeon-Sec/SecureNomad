## 1. 대화의 세 역할

LLM과의 대화는 세 역할의 메시지 열로 구성됩니다.

| 역할 | 무엇인가 | 특징 |
|---|---|---|
| **시스템(system)** | 개발자가 미리 정하는 지침·규칙·페르소나 | 사용자에겐 대개 보이지 않음 |
| **사용자(user)** | 실제 사용자가 입력하는 질문·요청 | 외부 문서·도구 결과가 섞이기도 함 |
| **어시스턴트(assistant)** | 모델이 생성하는 답변 | 앞의 맥락을 모두 참고해 만듦 |

대화가 길어지면 이 메시지들이 순서대로 쌓입니다. 그런데 모델은 이 구조를 **어떻게 받아들일까요?** 그것이 이 글의 핵심입니다.

## 2. 역할은 결국 하나의 토큰 열로 합쳐진다

왼쪽의 시스템·사용자·어시스턴트 세 역할은, 모델에 들어갈 때 오른쪽처럼 **하나의 연속된 토큰 열**로 쭉 이어집니다.

```text
[<|system|>]  너는 고객상담 봇이다 …
[<|user|>]    환불 어떻게 하나요?
[<|assistant|>] 환불은 …

      │  (모델 입력 직전)
      ▼
<|system|> 너는 … <|user|> 환불 … <|assistant|> …
└──────────── 하나의 토큰 열 ────────────┘
```

각 역할 앞에 **특수한 표시 토큰**(chat template의 역할 마커)이 붙어 구분될 뿐입니다. 즉, 역할 구분은 물리적인 칸막이가 아니라 **특수 토큰과 학습된 약속**으로 표시된 것입니다.

:::caution 핵심
모델 내부에는 "이건 시스템이고 저건 사용자"라고 가르는 **하드웨어적 격벽이 없습니다.** 역할은 벽이 아니라 표식입니다.
:::

## 3. 시스템 프롬프트가 하는 일

시스템 프롬프트는 한마디로 **앱의 설정값**에 가깝습니다. 예:

```text
너는 어떤 회사의 고객상담 봇이다.
정중하고 간결하게 답한다.
환불 규정은 7일 이내, 내부 가격표는 공개하지 않는다.
```

사용자 눈엔 보이지 않지만 동작을 좌우합니다. 담는 내용은 대체로 다음과 같습니다.

- **역할·페르소나** — 누구처럼 행동할지
- **규칙·정책** — 해도 되는 것과 안 되는 것
- **형식·어조** — 답변의 톤과 출력 형식
- **도구 사용 지침** — 어떤 도구를 언제 쓰는가
- **경계 설정** — 공개 금지·범위 제한 같은 가드

## 4. 역할 경계는 환상이다

여기에 함정이 있습니다. **역할 경계는 사실 환상에 가깝습니다.**

2장에서 봤듯 시스템 지시·사용자 입력·외부 문서는 결국 하나의 연속된 토큰 열에 들어가고, 역할 표식이 붙어 있을 뿐입니다. 모델은 보통 시스템을 더 따르도록 학습되지만, **그건 경향이지 보장이 아닙니다.**

그래서 사용자나 외부 입력이 시스템 지시를 덮어쓰려는 시도가 통할 수 있습니다. 바로 **프롬프트 인젝션**의 연장입니다. 외부 문서(웹 페이지, 메일, 검색 결과)가 같은 맥락에 섞여 들어오면, 그 안의 문장이 지시처럼 작동하는 **간접 프롬프트 인젝션**도 성립합니다.

:::danger 오늘의 교훈
**역할 분리는 편의이지 방어선이 아니다.** 역할 표식은 모델이 시스템을 더 따르도록 돕는 장치일 뿐, 물리적 격벽이 아니다. 역할에 기대 보안을 세우면, 그 경계가 흔들릴 때 보안도 함께 무너진다.
:::

기억할 네 가지:

1. 역할은 학습된 경향인 **소프트 표식**이다.
2. "더 따른다"는 건 보장이 아니라 **경향**이다.
3. 그래서 경계는 **권한·검증·격리**로 세운다.
4. 시스템 프롬프트는 **비밀 저장소가 아니다.**

## 5. 시스템 프롬프트 유출 (OWASP LLM07)

역할 경계가 약속일 뿐이라는 사실의 대표적 결과가 **시스템 프롬프트 유출**입니다. OWASP LLM Top 10의 **LLM07(System Prompt Leakage)**에 해당합니다. 보이지 않아야 할 시스템 지침이 유도나 인젝션으로 **답변에 드러나는** 것이죠.

**왜 위험한가**

- 숨긴 규칙·내부 정보가 노출된다
- 우회(탈옥)의 단서를 제공한다
- 페르소나나 로직을 복제당할 수 있다

**무엇이 새는가**

- 내부 정책·가격·경로
- 연결된 도구와 권한의 힌트
- 최악의 경우 **하드코딩된 비밀**까지

```text
[유출 경로]                        [방어]
역할 경계가 약속일 뿐  →  강하게    민감 정보를 애초에 프롬프트에 두지 않음
유도하면 흔들림                     출력 필터로 시스템 지시 노출 차단
외부 문서가 맥락에 섞여  →  간접     권한 분리로 '새도' 피해 최소화
적으로 끌어냄                       최소 정보 원칙 — 꼭 필요한 지시만
```

핵심은 **애초에 샐 게 없게, 그리고 새도 피해가 없게** 만드는 것입니다.

## 6. 방어 설계 네 가지

| # | 원칙 | 내용 |
|---|---|---|
| 1 | **비밀 미포함** | 키·내부 비밀을 시스템 프롬프트에 하드코딩하지 않는다 |
| 2 | **새도 안전** | 유출을 가정하고, 노출돼도 피해가 없게 설계한다 |
| 3 | **권한으로 경계** | 역할이 아니라 실제 권한·도구 접근을 제한한다 |
| 4 | **입출력 분리·검증·승인** | 외부 입력은 데이터로 격리, 출력에서 시스템 내용 필터링, 되돌리기 어려운 민감 작업은 사람 승인 |

더해서, 시스템 프롬프트를 캐묻는 **유출 시도 패턴을 로깅해 관찰**합니다.

## 정리

1. 대화는 세 역할의 메시지 열이고, 결국 하나의 토큰 열로 합쳐진다.
2. 시스템 프롬프트는 앱의 설정값으로 역할·규칙·형식·도구 지침을 담는다.
3. 역할은 하드웨어 벽이 아니라 소프트 표식이라 경계가 완벽하지 않다.
4. 시스템 프롬프트는 비밀 저장소가 아니니, 새어도 안전하게 설계해야 한다.

> **오늘의 한 줄** — 역할 분리는 편의이지 방어선이 아니다. 방어선은 권한과 검증, 격리로 세운다.
