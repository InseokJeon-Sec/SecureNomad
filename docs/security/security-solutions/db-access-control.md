# DB접근제어 바로 알기

> **대상 독자:** 솔루션을 검토·도입하는 담당자. 숫자는 **출처·기준시점**을 함께 표기합니다.

## 1. 왜 필요한가

DB에는 개인정보·금융정보가 집중돼 있어, DBA·개발자가 **직접 쿼리**하면 흔적 없이 **쿼리 한 줄로 수십만 건**을 조회할 수 있습니다. DB접근제어는 모든 접속을 **게이트웨이**로 모아 기록·마스킹·통제합니다. 개인정보보호법(접근통제·접속기록)·전자금융감독규정·ISMS가 강제합니다.

## 2. 기능 4축

- **접근 통제** — 인증·권한·시간·IP별 차등
- **SQL 감사** — 쿼리 전체 기록·재구성
- **데이터 마스킹** — 결과값 비식별(주민·카드) *— 다른 솔루션과의 결정적 차이*
- **이상행위 차단** — 대량 조회·위험 구문 차단

## 3. 동작 방식

| 방식 | 특징 |
|---|---|
| **프록시(게이트웨이)형** | 모든 접속을 프록시 경유 강제, 차단·마스킹 확실, **우회 불가**(실무 권장) |
| **스니핑(모니터링)형** | 네트워크 미러링, 구성 쉬움, 차단은 TCP reset(사후), **우회 가능성** |

> SAC(서버 OS 접근)와 혼동 금지 — DB접근제어는 **쿼리(DB) 접근**을 본다. 둘은 보완.

## 4. 도입 실무 — 파악 · 생성 · 결정

**① 파악** — DB 종류·수량(Oracle·MySQL·PostgreSQL·MSSQL·**NoSQL**), DB 계정(공유DBA·앱·개인·배치), 접속 경로(직접·**WAS(앱) 경유**·툴), **민감 컬럼 위치 지도**.

**② 생성·준비** — 게이트웨이·이중화, DB별 연동 계정, **마스킹 정책(컬럼별)**, 승인 워크플로, 앱(WAS) 연동, 로그·장기 보관.

**③ 결정** — 프록시 vs 스니핑, 마스킹 범위, 대량조회 임계·승인, **앱 경유 접속의 책임 추적**(공유 앱 계정 뒤 실제 사용자).

> **실제 대량조회는 ‘앱(WAS) 경유’에서 많이 난다.** 사람만 보고 앱 경로를 빼면 못 막습니다.

## 5. 비용·시장 (국내 주도)

- **비용:** DB 수/접속자 기반. 국내 DB접근제어 시장 **~1,000억 원**, 공공·금융은 CC인증. 숨은 비용 = 민감 컬럼 식별·마스킹 설계, 앱 경로 통합, 프록시 성능 영향 검증.
- **시장:** 국산 주도 — **DBSAFER(피앤피시큐어)** 6,000+ 도입·1위 주장, **웨어밸리 Chakra Max**(DB+시스템 통합)와 양강, **신시웨이 DB-i**(DB접근+암호화 통합). 규제·한글 감사·레퍼런스가 진입장벽.

## 6. 어떤 환경에 맞나

| 상황 | 권장 |
|---|---|
| 금융·공공·개인정보 대량 | 필수+마스킹 |
| DBA·개발 직접 접속 다수 | 게이트웨이 통제·감사 |
| 외주 DB 유지보수 | 세션 기록·승인 |
| 앱(WAS) 대량 조회 | 앱 경유 식별·대량 통제 |
| 클라우드 DB·DBaaS | 클라우드 지원·암호화 연계 |

## 흔한 오해와 함정

- **앱(WAS) 경로를 빠뜨린다** → 실제 대량조회 사각지대
- **기록만 하고 마스킹 안 한다** → 권한 있는 사람이 원본 다 봄
- **민감 컬럼 식별 생략** → 마스킹·통제 무의미
- **스니핑만으로 충분** → 우회 가능, 규제엔 프록시
- **성능 검증 생략** → 프록시 지연, 사전 BMT 필수
